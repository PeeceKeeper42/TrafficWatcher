# Документация курса: Qt 6.10 + QML + C++20 + современный CMake

Учебный проект-репозиторий. Каждый урок — это **документ с теорией и заданием**; код пишу я, ассистент
даёт теорию, направление, ревью и список доработок. Файлов минимум, имена — читаемые человеком.

---

## 1. Концепция продукта

> **Общая идея:** сначала на новом стеке повторить функционал старого проекта. Затем допилить его фичами.
> Потом в рамках этого же приложения сделать песочницу по типу RMS — с редактором и эмуляцией работы,
> с имитационным моделированием внутри. Всё по best practice уровня коммерческого продукта / enterprise.

Три вехи — это не «версии приложения», а **разные продукты в одной кодовой базе**: у каждой свой контур
качества, свои виды тестов и свои архитектурные требования.

### M1 — Паритет (повторить функционал на Qt 6.10.2 / C++20 / QML)

**Что:** приложение-светофор из `44ffd1b`: список состояний, редактор режимов каналов, прогон
последовательности по времени, мигание, сохранение/загрузка конфигурации.
**Зачем как отдельная веха:** тренировка стека без проектирования «в пустоту» — функционал уже известен,
внимание уходит на *как сделать правильно*, а не на *что сделать*.
**Критерий готовности:** старый сценарий (3 состояния, жёлтый мигающий ночью) воспроизводится визуально
и по таймингам; CI на 3 ОС; тесты ядра покрывают переходы состояний.
**Сознательный долг:** один перекрёсток, один светофор, никакой сцены. Но то, что помешает M3, закладывать
нельзя (см. § «Мосты в M3»).

### M2 — Фичи

Кандидаты (упорядочены по ценности/учебной нагрузке, уточняется ADR):

1. **Несколько светофоров, фазы и расписания** (день/ночь/час пик) — первый шаг к «сцене».
2. **Persistence по-взрослому:** версионированный формат конфигурации + миграции + ошибки валидации
   (`std::expected`), тесты на битый файл.
3. **Undo/redo, copy/paste, импорт/экспорт** (`QUndoStack`) — без этого чистая архитектура не видна.
4. **Локализация** (ru/en), `lupdate`/`lrelease` в сборке, гейт на untranslated-строки.
5. **Наблюдаемость:** категорированное логирование, метрики цикла, трассировка.
6. **Аппаратная абстракция:** интерфейс «драйвер светодиодов» (сегодня — QML-отрисовка, завтра — UART/CAN),
   `FakeLampDriver` в тестах.

**Критерий готовности:** формат версионирован и мигрирует; есть обратимый редакторский сценарий;
переносимость между ОС без правок в `core`/`ui`.

### M3 — RMS-песочница (редактор + эмуляция + имитационное моделирование)

**Что:** рабочее место проектировщика/оператора: сцена (перекрёстки, направления, фазы), редактор
конфигураций, эмуляция работы светофоров во времени и модель транспортного потока, реагирующая на эту
работу. По сути — дискретно-событийная/тактовая симуляция с GUI поверх ядра.

| Требование | Что значит в коде |
|---|---|
| **Детерминированность** | Никаких `QTimer`/`QDateTime::currentMSecsSinceEpoch()` в ядре. Инжектируемое `IClock`/шаг модельного времени; сценарий + seed → один и тот же результат. Фундамент replay- и golden-тестов |
| **Модель ≠ представление** | Ядро симуляции не знает ни про QML, ни про пиксели. UI читает состояние и шлёт команды |
| **Отделяемое время** | 1× realtime, ускорение ×N, пошаговый режим, запись/проигрывание трассы |
| **Сериализуемая сцена** | Сцена — данные (JSON/CBOR/protobuf), а не граф QObject: иначе нет ни diff-а конфигов, ни сохранений, ни передачи на воркер |
| **Параллелизм и масштаб** | Модель потока считается вне GUI-потока (`QtConcurrent`/`std::thread` + `QPromise`/`QFuture`), позже — отдельный headless-процесс |
| **Профилируемость** | Кадры/сек, время шага модели, аллокации; `QBenchmark` + пороги деградации |
| **Расширяемость** | Типы перекрёстков/поведений — плагины (интерфейс + `QPluginLoader`) или data-driven описание |
| **Скриптинг сценариев** | `QJSEngine`/`QmlEngine` для «авария на полосе в 08:12» |

**Критерий готовности:** 100 перекрёстков × 1 симуляционный час быстрее realtime, детерминированно
(golden-файл совпадает), результат не зависит от наличия GUI.

### Мосты в M3, которые закладываем уже в M1

Дешевле заложить сейчас; каждый пункт — строка в ADR, а не «авось получится»:

1. **Тактовое время с самого начала:** прогон идёт не по `QTimer` внутри класса, а через `TickEngine`,
   который дёргают извне. Иначе M3 = переписать ядро.
2. **`core` без QtQuick и без глобального состояния** — иначе симуляцию не запустить headless на воркере.
3. **Конфигурация = данные** (M2.2), а не «набор свойств QObject» — иначе не будет ни версий, ни сцены.
4. **Именованные события/команды:** критичный путь («пользователь нажал») выражается одним событием,
   которое можно записать и воспроизвести (replay-тест).
5. **Имена на вырост:** продукт — `TrafficWatcher`, в M3 там не один светофор; include-пути и URI QML-модулей
   проектируем как `trafficwatcher/<подмодуль>` (ADR-0002).
6. **Инфраструктура для долгих прогонов** (урок 15): M3-тесты идут минутами → свои лейблы CTest, свои воркеры,
   артефакты-трассы.

### Нецели

- Не делаем реальный контроль дорожной инфраструктуры, сертификацию, работу с «железом» в M1–M2
  (только абстракция из M2.6).
- Не пишем свой движок отрисовки карты и не делаем ГИС/3D: M3 — схематичная 2D-сцена.
- Не тянем web-стек в приложение: вебхуки/n8n — только для инфраструктуры.
- Не поддерживаем Qt5 и C++17: паритет по функционалу, а не совместимость сборки.
- Не уходим в кастомный стайлинг-ад: Qt Quick Controls + своя тема.

## 3. Как устроен урок

```
lessons/07-something.md               answers/07-something.md
├─ шапка: модуль, веха, ADR           ├─ тот же заголовок урока
├─ 0. Чему учит урок: цели, словарь   ├─ Вопрос 1 … (спойлер с подсказкой, ниже — пуст blockquote)
├─ 0.1 Зачем это нужно именно сейчас  ├─ Вопрос 2 … (+ блок «Оценка» под моим ответом)
├─ 0.2 Приложение: вход → выход       └─ «Что осталось непонятным» (мой блок)
│        + таблица усложнения прошлых конструкций
├─ 1..N. Теория: механика → почему сделано так → что будет, если нарушить → мини-практика
│        (внутри разделов — абзацы «Тонкость N.»: неочевидное поведение с проверяемым следствием
│         и карточки-паспорта новых конструкций: сигнатура, аргументы, сценарии, best practice)
├─ Диагностика: симптом → причина
├─ Задание + Definition of Done
├─ Подмеченные ошибки
├─ Контраст с прошлым (≤15% объёма, один раздел)
├─ Вопросы → только ссылкой на answers/
├─ Что читать
└─ Итог урока: ADR, состояние приложения, следующий урок
```

Пять правил формы урока (полностью — [`../AGENTS.md`](../AGENTS.md) §2.1–2.5):

- **Непрерывность.** Урок не тема про стек, а шаг разработки TrafficWatcher: в §0.2 указано, что
  приложение умеет на входе и что в нём появляется на выходе; ≥2/3 пунктов задания правят код
  приложения. В первых уроках допустим **строительный код** — простые классы, нужные чтобы графу CMake и
  первому тесту было на чём существовать; для каждого записан урок, где он удаляется (`Mode.hpp` из
  урока 1 уходит в урок 6.1, `main.cpp` без QML — в 2.1).
- **Спираль.** Цель — уровень middle, поэтому конструкции прошлых уроков возвращаются усложнёнными:
  таблица «конструкция | где появилась | как усложняется здесь» в §0.2 (в уроке 1 она развёрнута вперёд)
  и 3–6 абзацев **Тонкость N.** на урок — неочевидное поведение, у которого есть проверяемое следствие и
  команда, которой оно подтверждается. Тонкости «ради тонкости» в урок не пишутся.
- **Баланс.** История про Qt5 занимает не больше ~15% урока и стоит в конце; каждый тезис «так принято»
  обязан иметь следствие — что сломается, если сделать иначе.
- **Справка.** Кроме объяснения каждая новая конструкция получает карточку-паспорт: полная сигнатура,
  допустимые формы аргументов, 2–3 сценария применения и один случай, где она неприменима, best practice
  со следствием, тонкость уровня middle и команда, которой проверяется точная формула
  (`cmake --help-command`, `ctest --help`, страница Qt-доков). В конце урока — сводная таблица
  «Справка урока: конструкции», по которой урок можно перепробежать за пять минут (`AGENTS.md` §2.5).
- **Тон.** Обучающий, без иронии и оценочных ярлыков.

## 4. Соглашения

- **Голос:** документы пишутся от лица владельца проекта («я делаю так»); в теоретических разделах уроков
  допустимо обращение ассистента к читателю на «ты».
- Один урок = один коммит (или ветка) + рабочие файлы в репозитории.
- **Урок не закрыт, пока не видно, как изменилось приложение**: §0.2 «Приложение: вход → выход» заполнен,
  и ≥2/3 пунктов задания правят код приложения, а не только конфигурацию и документы (§3, `AGENTS.md` §2.3).
- **И пока не названо, что усложнилось из прошлого урока**: строка из таблицы §0.2, показывающая
  конструкцию, которая в этом уроке меняет поведение, — обязательная часть отчёта о закрытии урока
  (`AGENTS.md` §2.4).
- Урок закрыт, когда выполнены все пункты DoD **и** заполнен `answers/NN-*.md`.
- Фича без описанного теста, который упадёт при её поломке, не считается сделанной.
- Нетривиальное решение без ADR не считается принятым.
- Модули поставки и инфраструктуры (11–12, 15) не опережают блоки I–III: сначала стабильный
  `ctest --preset`, потом автоматизация.
- Очередь ADR, гейты качества по вехам и карта модулей — в [`course.md`](course.md) и [`adr/readme.md`](adr/readme.md).

## 5. Обязательства ассистента

Полный список — в [`../AGENTS.md`](../AGENTS.md) (корень репозитория). Ключевое:

- код **не пишет** (только `docs/`, `answers/`, сниппеты в чате/уроке);
- с каждым новым уроком **обязан** создать `answers/NN-<имя-урока>.md` со всеми вопросами урока,
  пустыми местами под ответы и без дублирования вопросов в теле урока;
- урок без §0 «чему учит», без задания с DoD и без файла вопросов не считается оформленным;
- теория ведёт по схеме **механика → почему сделано именно так → что будет, если нарушить →
  мини-практика**; старому Qt5-коду отводится ≤15% объёма и один раздел ближе к концу;
- каждый урок усложняет конструкции предыдущих (таблица в §0.2) и содержит 3–6 тонкостей уровня middle,
  каждая — с проверяемым следствием и командой (`AGENTS.md` §2.4); выдуманных API не бывает: сомнение
  помечается словом «проверь на своей версии»;
- **право на запись по файлам `docs/` ограничено** (`AGENTS.md` §1.1): в ADR — только форматирование;
  в `answers/` — только **оценка**, дописанная под моим ответом (`> **Оценка (урок NN, вопрос M):**` с
  вердиктом «зачтено / с оговоркой / не зачтено»); мой текст не переписывается ни при каких условиях,
  пустой `> Ответ:` остаётся пустым;
  `course.md` — только по отдельному вопросу; `legacy-description.md` и всё остальное в `docs/` —
  только чтение; вне `docs/` — ничего.
- **подсказки в `answers/` — только спойлером** (`AGENTS.md` §3.1): свёрнутый `<details>` между текстом
  вопроса и слотом `> Ответ:`. В открытом тексте остаются только сама проверка и требования к полноте
  ответа — «минимум три», «достаточно двух механизмов» подсказкой не считаются и сворачивать их нельзя.
  Подсказка, которую можно дословно перенести в ответ, считается испорченным вопросом: переписывается
  вопрос, а не добавляется подсказка.
