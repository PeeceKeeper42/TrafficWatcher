# 0000. Вести Architecture Decision Records

Статус: Принято
Дата: 2026-11-19
Замечания: Сгенерировано ИИ.

## Контекст

Курс рассчитан на месяцы, проект проходит три вехи ([`readme.md`](../readme.md) §1), а требования к качеству —
«уровень коммерческого продукта». В таких условиях половина важных решений существует только в переписке
с ассистентом или в моей голове: почему `CMAKE_PREFIX_PATH` в пресете, почему `-Werror` только в CI,
почему время инжектится, а не берётся из `QDateTime`, почему macOS-проверка идёт на GitHub-hosted.
Через месяц я буду спорить сам с собой и, что хуже, молча нарушать принятое.

Кода решение не видно: `PRIVATE` в `target_link_libraries` не объясняет, почему не `PUBLIC`. Нужен
минимальный процесс, который дешевле, чем «разобраться в старом коде».

## Решение

Вести ADR в `docs/adr/` по одному файлу на решение, нумерация сквозная, статус меняется только
новым файлом. Формат — в [`template.md`](template.md), очередь и статусы — в [`readme.md`](readme.md).

### Структура ADR

```
NNNN-kebab-case-имя.md

# NNNN. Короткое название решения как утверждение
Статус: Предложено | Принято | Отклонено | Устарело | Заменено на NNNN
Дата: YYYY-MM-DD

## Контекст        — проблема и почему решение нужно сейчас (3–8 строк, факты, не мнения)
## Решение         — что выбираем, одной фразой + детали
## Аргументы за / против  — минимум 3 «за» и 2 «против», честно про боль
## Отклонённые альтернативы — что не взяли и почему (иначе через год снова попробуем)
## Последствия     — что теперь обязательно, что запрещено, что откладываем
## Проверка        — команда/признак, доказывающий что решение работает
## Связи           — ссылки на уроки, модули, другие ADR
```

### Правила

1. **Один ADR = одно решение.** «Тулчейн и структура каталогов» — два файла.
2. ADR пишет **владелец проекта** (я), ассистент может критиковать формулировки и требовать «Проверку».
3. ADR не редактируется задним числом при смене решения: новый файл со статусом `Заменяет NNNN`,
   в старом — `Заменено на NNNN`.
4. Обязательные поля: `Статус`, `Дата`, `Проверка`. ADR без способа проверить — это мнение, а не решение.
5. «Против» обязателен: выбор без задокументированных недостатков означает, что альтернативы не рассматривались.
6. Объём — 15–50 строк. Больше — значит это либо ТЗ, либо дизайн-док (тогда `docs/design/`).
7. Ссылка из кода: нет — но там, где решение «выдаётся» в код (флаг, политика, имя таргета), допустим
   комментарий `// см. docs/adr/0003`.

## Аргументы «за»

- Решения становятся явными: «почему `PRIVATE`» перестаёт быть вопросом к ассистенту через месяц.
- Запрещает тихие регрессии архитектуры: «M3-детерминированность» — это ADR, и его нарушение видно в ревью.
- Дешёвый вход: 20 строк markdown на решение, без инструментов и процесса.
- Готовый материал для портфолио/собеседований: видно ход мысли, а не только результат.

## Аргументы «против»

- Дисциплина: ADR без очереди превращается в кладбище файлов. Лечится списком в `readme.md` и
  правилом «нет ADR — нет мержа фичи, меняющей границы».
- Соблазн задокументировать всё (в т.ч. тривиальное) и потратить время вместо кода. Лечится порогом:
  ADR только для решений, которые **дорого отменить** или которые **ограничивают других**.
- Дублирование с остальными документами: решение может жить и в уроке (например, в
  [`lessons/08-testing-strategy.md`](../lessons/08-testing-strategy.md)), и в ADR. Правило: в уроке — как устроено,
  в ADR — почему выбрано именно так.

## Отклонённые альтернативы

- **Только комментарии в коде** — не видно принятых, но невыразимых в коде решений (политика CI, выбор ОС).
- **Таблица «Решения» в одном большом README** — при 15+ решениях становится свалкой без истории.
- **ADR-туллинг (`adr-tools`, `log4brains`)** — лишняя зависимость; markdown + git пока достаточно.
  Пересмотрим, когда файл станет длиннее 50 строк или появится команда из >1 человека.
- **RFC-процесс с ревью и голосованием** — для соло-разработки оверхед.

## Последствия

- Перед уроком, где решение «созревает», я заведу `docs/adr/NNNN-*.md` (статус `Предложено`),
  после проверки переношу в `Принято`.
- В `docs/readme.md` и в конце каждого урока — ссылка на ADR, который урок порождает.
- Новые нетривиальные решения без ADR не мержим.

## Проверка

```bash
ls docs/adr/*.md            # есть 0000-adr-process.md и template.md
git log --oneline -- docs/adr/   # статусы меняются коммитами, история решений видна
```

Признак работоспособности: на вопрос «почему у нас так?» я за 30 секунд нахожу файл и показываю ссылку.
