## 0. Чему учит урок и как с ним работать

После урока ты должен уметь:

1. Объяснить, что такое **таргет** и **требование таргета**, и предсказать, какие флаги получит конкретный
   потребитель до того, как запустил сборку.
2. Выбрать `PRIVATE`/`PUBLIC`/`INTERFACE` по признаку «входит ли это в мой API», а не по принципу «чтобы слинковалось».
3. По тексту ошибки определить, **на какой фазе** CMake она возникла, и чинить в правильном месте.
4. Объяснить, почему на MSVC-генераторе `if(CMAKE_BUILD_TYPE STREQUAL "Debug")` молча не работает, и чем его
   заменяет генераторное выражение.
5. Описать, какие знания переезжают в `CMakePresets.json` и почему они должны быть в репозитории.
6. Назвать три блокера своей текущей машины и план их снятия.
7. Для каждого файла, который появится в задании, сказать, в каком уроке он перестаёт быть нужен:
   строительный код (§0.2) без записанного срока жизни — это будущий долг, а не каркас.
8. Назвать неочевидное поведение каждой из разобранных конструкций (`cxx_std_20`, `ALIAS`,
   `INTERFACE`-таргет с флагами, `POSITION_INDEPENDENT_CODE`, генераторное выражение): что именно она
   меняет в команде компиляции или линковки. Эти детали — разница между «работает» и «понимаю, почему
   работает», и их спрашивают на собеседовании на middle (§1.5, §2.4, §4.4).

Как устроен каждый раздел теории: **механика** (как на самом деле работает) → **почему так сделано**
(какую проблему это решает) → **что будет, если нарушить** (конкретный симптом) → **мини-практика**
(2–5 минут в терминале, чтобы проверить утверждение на своей машине). Отдельные абзацы
**Тонкость N.** — неочевидные детали уровня middle: они стоят в конце того раздела, к которому
относятся, и каждая проверяется одной командой.

Термины, которые используются дальше без перевода:

| Термин | Определение |
|---|---|
| **Таргет** | Именованная единица результата: библиотека, исполняемый файл, объектная библиотека, `INTERFACE`-набор свойств. Создаётся `add_library`/`add_executable`/`add_library(... INTERFACE)` |
| **Требование (requirement)** | То, что нужно таргету для компиляции/линковки: include-пути, определения препроцессора, флаги компилятора, другие таргеты |
| **Распространение (propagation)** | Механизм: требование, помеченное `PUBLIC`/`INTERFACE`, автоматически передаётся всем, кто ссылается на таргет в `target_link_libraries` |
| **Генератор** | Программа, которой CMake передаёт управление сборкой: Ninja, Makefiles, MSBuild, Xcode. Определяет, одно- или многоконфигурационным будет проект |
| **Кэш CMake** | Файл `CMakeCache.txt` в build-директории: итоговые значения всех `-D`-переменных. Источник правды при повторных configure |
| **Пресет** | Именованный набор параметров configure/build/test/install в `CMakePresets.json`, вызываемый `cmake --preset <имя>` |

Мини-практика 0 (1 минута). Выполни и запомни ответ — он пригодится в §4:

```bash
cmake --help-presets          # какие версии схемы понимает твой cmake
cmake --help-property-list    # все свойства таргетов; найди INCLUDE_DIRECTORIES и INTERFACE_*
```

### 0.1 Зачем это нужно именно сейчас, если впереди M2 и M3

Требования будущих вех формулируются не классами, а свойствами графа:

| Требование из концепции | Где оно обеспечивается |
|---|---|
| Ядро симуляции работает **headless**, без QtQuick (нужно для прогонов на воркере) | у таргета `tw_core` в `target_link_libraries` нет `Qt::Quick`; граф это показывает за секунду |
| Тест ядра собирается быстрее, чем приложение, и линкует 2 библиотеки, а не весь GUI | у тестового таргета одна зависимость — `TrafficWatcher::Core` |
| Платформозависимый код в одном месте | один таргет `tw_platform`, остальные знают только его интерфейс |
| Sanitizer-прогон не требует правок в коде | ещё один configure-пресет с другими `cacheVariables` |
| Конфигурация сцены — данные, а не граф `QObject` | отдельный сериализуемый слой в `core`; здесь важно, что он не тянет за собой GUI |

Все пять пунктов стоят 20 строк CMake сегодня и переписывания половины файлов через полгода. Поэтому мы
начинаем с графа, а не с QML.

### 0.2 Приложение: вход → выход

Этот урок не про CMake вообще — он про то, чтобы у TrafficWatcher появился граф, в который следующие
уроки добавляют код. Абстрактных тем в курсе нет: каждый урок оставляет после себя работающее
(или хотя бы собираемое) приложение.

| | Состояние приложения |
|---|---|
| **Вход** | Кодов нет. В репозитории только `CMakeLists.txt` из двух строк (`cmake_minimum_required(VERSION 3.16)`, `project(TrafficLight …)`) и `.gitignore`. Собрать и запустить невозможно ничего; это замеры текущего дерева, а не оценка |
| **Выход** | `cmake --preset win-msvc-debug` → `cmake --build` → `ctest` зелёный. Существуют два таргета: `tw_core` (STATIC-библиотека, `cxx_std_20`, публичные заголовки в `include/trafficwatcher/core/`) и `tw_app` (`QGuiApplication`, без QML-модуля). В `tw_core` лежат **строительные** классы (таблица ниже) и на них же — первый тест |
| **Наследство следующему уроку** | Урок 1.2 (матрица пресетов) открывается кодом, который уже собирается: у него есть два таргета с корректно расставленными `PRIVATE`/`PUBLIC`, пресет, в котором живёт `BUILD_TESTING`, и один зелёный тест, который матрица прогонит ×N конфигураций. Никаких классов домена там по-прежнему нет — и это правильно до урока 6 |

**Строительные классы.** Приложения ещё нет, а графу таргетов и первому тесту нужно на чём-то
существовать: `target_compile_features(tw_core PUBLIC cxx_std_20)` проверяется только тогда, когда в
`tw_core` есть хотя бы один компилируемый файл с C++20-конструкцией. Поэтому в уроке 1 допустимы
заглушки — и каждая из них имеет записанный срок жизни:

| Строительный артефакт | Зачем он нужен сегодня | Где он перестаёт быть нужным |
|---|---|---|
| `include/trafficwatcher/core/Mode.hpp`: `enum class Mode { Solid, Flashing }` + `constexpr auto label(Mode) -> std::string_view` | даёт `tw_core` содержимое; `label()` — что утверждать в первом тесте; `constexpr` — заодно проверяет, что `cxx_std_20` действительно применился | **урок 6.1**: реальная стейт-машина M1 (`TrafficLightState`, переходы, `TickEngine`). Удаление файла — пункт задания того урока |
| `src/app/main.cpp`: `QGuiApplication` + пустой `QQmlApplicationEngine` без `.qml` | демонстрирует распространение требований: `tw_app` получает `Qt::Core` бесплатно и не получает `Qt::Concurrent` | **урок 2.1**: `qt_add_qml_module` + `QML_ELEMENT`, появляется `main.qml` и модуль становится настоящим |
| `tests/unit/test_core_smoke.cpp`: проверка, что `label(Mode::Solid)` вернула ожидаемое | первый зелёный лот CTest и первый `add_test` в контейнере из п.9 | **урок 8.2**: QTest-механика, data-driven-таблицы; smoke-тест заменяется тестами домена |

Правило на весь курс: **срок жизни строительного кода записан в момент его появления**. Если через урок
он всё ещё в дереве и никто не вспомнил про него — это уже не scaffold, а долг, и он попадает в §8
следующего урока как находка. Номера уроков в правой колонке — из [`course.md`](../course.md); сами
уроки 2.1 и 6.1 ещё не написаны, поэтому привязка предварительная: когда урок появляется, удаление
становится его пунктом задания, а не обещанием.

**Во что вырастают конструкции этого урока.** Прошлых уроков у нас нет, поэтому здесь карта вперёд:
тот же принцип спиралью (каждый следующий урок усложняет конструкцию, а не проходит тему заново).
Правая колонка — не «вспомним», а «здесь конструкция начнёт вести себя иначе»:

| Конструкция урока 1 | Где усложнится и чем именно |
|---|---|
| `PUBLIC` / `PRIVATE` | 2.1: `Qt6::Quick` как публичное требование `tw_ui` даёт десятки transitive-рёбер, и `PRIVATE` у исполняемого файла становится вопросом секунд сборки; 6.1: у `tw_core` появляется инвариант «нет QtQuick в propagated-требованиях», который проверяется `deps.dot` |
| `cxx_std_20` как требование | 3.1–3.2: `concepts`, `consteval`, ranges требуют реально применённого стандарта к каждому TU — и там же ловится разница между «стандарт в кэше» и «стандарт у таргета» (§1.5, тонкость 1) |
| генераторные выражения | 7: `$<PLATFORM_ID>` решает, компилируется ли `src/platform/win` или `mac`; 11–12: те же выражения в `install(...)`/deploy-скрипте исполняются три раза на трёх ОС из одного файла |
| alias `TrafficWatcher::Core` | 8.2: тест линкуется **только** по alias — и граф превращается в механизм контроля слоёв: тест ядра физически не видит GUI (§2.4, тонкость 3) |
| `INTERFACE`-таргет как переносчик свойств | 8.2: `TrafficWatcher::TestSupport` (заголовки фейков без собственной библиотеки); 10: `TrafficWatcher::Warnings` — и там же становится видна цена утечки флагов в экспортируемый пакет (§2.4, тонкость 4) |
| `install(TARGETS …)` и фаза install | 11: тот же блок определяет содержимое `.msi`/`.dmg`/`.tar.gz`; 15: эти же команды вызывает CI, и ошибка фазы превращается в красный прогон ночью |

## 1. Модель: проект — это граф таргетов

### 1.1 Механика

CMake строит направленный граф. Вершины — таргеты, рёбра — зависимости через `target_link_libraries`.
Каждый таргет несёт список свойств, часть которых помечена как `INTERFACE_*` — то есть «это нужно не только
мне, но и тому, кто от меня зависит».

Вот канонический минимум (сниппет для чтения — в проект ты напишешь его сам в §7.2):

```cmake
add_library(tw_core STATIC engine.cpp states.cpp)
target_compile_features(tw_core PUBLIC cxx_std_20)        # (1)
target_include_directories(tw_core PUBLIC  include)       # (2)
target_include_directories(tw_core PRIVATE src)           # (3)
target_link_libraries(tw_core    PUBLIC  Qt::Core)        # (4)
target_link_libraries(tw_core    PRIVATE Qt::Concurrent)  # (5)

add_library(TrafficWatcher::Core ALIAS tw_core)           # (6)

add_executable(tw_app main.cpp)
target_link_libraries(tw_app PRIVATE TrafficWatcher::Core) # (7)
```

Разберём, что физически происходит при сборке `tw_app`:

Имена `engine.cpp`/`states.cpp` взяты из будущего домена (модуль 6): сегодня в этой строчке у тебя будет
один `src/core/mode.cpp` из §0.2. Смысл примера от этого не меняется — важно, что список источников живёт
в `add_library`, а не в переменной выше по дереву.

- **(1)** `cxx_std_20` — не «включить флаг», а требование к стандарту языка. CMake выберет максимальное из
  требований таргета и всех его зависимостей и подставит флаг компилятора сам (`/std:c++20`, `-std=c++20`).
- **(2)** `include/` станет публичной частью API: любой, кто ссылается на `tw_core`, получит `-I.../include`
  автоматически.
- **(3)** `src/` увидит только сам `tw_core`. Это и есть граница «публичное/внутреннее».
- **(4)** `Qt::Core` — PUBLIC: если в открытом заголовке есть `#include <QObject>`, потребителю тоже нужен путь
  к QtCore. Иначе он упадёт на компиляции, а не на линке.
- **(5)** `Qt::Concurrent` — PRIVATE: используется только в `.cpp`. Потребитель не получает ни путь, ни объект в линке.
- **(6)** Alias даёт «правильное» имя с namespace. Опечатка в `TrafficWatcher::Cor` — ошибка configure, а не
  загадочная ошибка линкера.
- **(7)** `tw_app` получает (1), (2), (4) бесплатно и **не** получает (3) и (5).

### 1.2 Почему сделано именно так

Потому что флаг компилятора — это следствие того, **что именно** данный файл включает. Раньше это знание
приходилось поддерживать вручную: автор `CMakeLists.txt` должен был помнить, что `tests/` тоже нужен путь к
QtCore. Модель требований переносит знание в место определения: библиотека сама говорит, что нужно её
потребителю. Отсюда три свойства, которые мы и покупаем:

1. **Локальность правки.** Изменил внутреннюю реализацию с `QtConcurrent` на `std::thread` — тронул одну
   строчку `PRIVATE`, граф не перестроился у потребителей.
2. **Проверяемость границ.** Свойство «ядро не знает про GUI» становится фактом, который видно в
   `deps.dot` и который можно защищать автоматической проверкой (модуль 10), а не уговором.
3. **Переиспользуемость.** Тот же `tw_core` линкуется в приложение, в тест и в headless-консольный прогон
   без копирования флагов — потому что флаги едут вместе с таргетом.

### 1.3 Что будет, если нарушить

Нарушение модели — это не «некрасиво», а конкретные отказы:

| Что делаем | Симптом | Почему так происходит |
|---|---|---|
| Вешаем include-путь глобально (`include_directories` на верхнем уровне) | тест ядра компилируется, но линкует весь GUI; чужой `3rdparty` собирается с нашими `/W4 /WX` | свойство записывается в **директорию** и достаётся всем последующим таргетам, независимо от того, нужны ли им эти заголовки |
| Ставим `PUBLIC` «на всякий случай» | время сборки растёт: правка заголовка влечёт ре-билд всех потребителей; `Qt::Quick` просочился в тесты | мы объявили эти пути и либы частью API, и CMake честно транслирует их вниз по графу |
| Храним список файлов в переменной и передаём через `PARENT_SCOPE` | родитель не собирается без знания имён файлов ребёнка; `file(GLOB)` молча игнорирует добавленный файл | список источников — свойство таргета, а не строка в кэше; он должен создаваться там, где лежат файлы |

### 1.4 Мини-практика 1 (3 минуты)

Собери мини-проект из двух таргетов в `$env:TEMP\cmk\`:

```
CMakeLists.txt        # project() + add_library(a STATIC a.cpp) + add_executable(m main.cpp)
a.cpp, include/A.h, main.cpp
```

1. `target_include_directories(a PUBLIC include)` → собери, убедись, что `main.cpp` видит `#include <A.h>`.
2. Замени на `PRIVATE` → переконфигурируй в **чистый** build-каталог и посмотри сообщение об ошибке.
   Прочитай его целиком: это ошибка **компиляции** `main.cpp`, а не `find_package` и не линковка.
3. Команда `cmake --build <dir> -- -v` (или `--verbose`) покажи себе, какой набор `-I` реально получил
   `main.cpp`. Дальше по курсу эта команда — основной инструмент диагностики.

### 1.5 Тонкости распространения

**Тонкость 1.** `cxx_std_20` — это «не меньше 20», а не «ровно 20», и в графе **побеждает максимум**.
Если `tw_core` требует `cxx_std_20`, а будущая `tw_legacy_bridge` — `cxx_std_14`, то потребитель,
линкующий оба, соберётся под C++20. Проверить: `--verbose` и один флаг `/std:` на строку компиляции —
он один, и он взят из самого большого требования. Следствие, которое дорого стоит: библиотека, заявленная
как совместимая с C++14, в этом графе **никогда** не собирается под C++14, и её несовместимость
всплывёт у того, кто её подключит. Совместимость со старым стандартом — это отдельный прогон
(отдельный пресет или CI-джоба), а не свойство графа. Вопрос 11 в файле ответов — ровно про этот
механизм; отвечать на него теперь надо с продолжением: **кто** в нашем проекте обязан проверить
библиотеку на минимальном стандарте и когда.

**Тонкость 2.** Требования распространяются, а способ их компиляции — нет. `POSITION_INDEPENDENT_CODE`
свойственен таргету, а не графу: статическая `tw_core`, которую завтра линкуют в общую библиотеку
(модуль 14 — плагины симуляции), обязана быть собрана с PIC, иначе на Linux и macOS падает **линковка**
`ld: error: relocation R_X86_64_32 ...`, а на Windows — где такого понятия нет — собирается без
замечаний. Отсюда правило на курс: у потенциально статических библиотек PIC включаем явно
(`set_target_properties(tw_core PROPERTIES POSITION_INDEPENDENT_CODE ON)`), а у `INTERFACE`-таргета,
где собственного кода нет и ставить флаг не на что, —
`set_property(TARGET tw_headers PROPERTY INTERFACE_POSITION_INDEPENDENT_CODE ON)`, чтобы требование
унаследовал потребитель. Эта ошибка — из породы «у меня работает», и ловится она только матрицей ОС
(модуль 12), а не внимательностью. Тот же класс, кстати, у `CMAKE_POSITION_INDEPENDENT_CODE`: он задаёт
**значение по умолчанию** для новых таргетов, поэтому порядок `project()` / `set()` / `add_library()` в
файле меняет результат — ещё одна причина, почему у нас настройки стоят до `add_subdirectory`.

## 2. `PRIVATE` / `PUBLIC` / `INTERFACE`: ключевые слова как вопрос про API

### 2.1 Механика

| Ключевое слово | Кто получает требование | Когда оно правильное |
|---|---|---|
| `PRIVATE` | только этот таргет | нужно для компиляции/линковки **этих** `.cpp`, в открытые заголовки не входит |
| `PUBLIC` | этому таргету и всем, кто на него ссылается | часть API: открытый заголовок включает этот путь / эту библиотеку / требует этот стандарт |
| `INTERFACE` | только потребителям | сам таргет не компилируется: header-only библиотека, «пакет свойств» (_warnings_, options) |
| `IMPORTED` | — | таргет создан `find_package`/`add_library(IMPORTED)`, его свойства только читаются |
| `ALIAS` | — | второе имя существующего локального таргета, обычно `Namespace::Name` |

Три вопроса, на которые надо ответить перед выбором (это и есть «тест на честность»):

1. Открою ли я это имя в заголовке из `include/`? Если нет — `PRIVATE`.
2. Сломается ли сборка потребителя, если я это уберу? Если нет — `PRIVATE`.
3. Знает ли потребитель о моей внутренней библиотеке? Если да — я случайно сделал деталь реализации API.

### 2.2 Почему `PUBLIC` по умолчанию — плохая привычка

`PUBLIC` означает «это часть моего контракта». Контракт дорог: он расширяет поверхность, при изменении
которой нужно пересобирать и перепроверять чужой код. В Qt-проекте цена особенно видна: `Qt::Quick` в
публичных требованиях ядра — это (а) гарантированная сборка GUI-стека ради теста одной функции,
(б) невозможность запустить ядро headless, (в) `QT_QPA_PLATFORM` в каждом тесте. Именно это требование
мы фиксируем ADR-0007/0008 и проверяем на уроке 6.1.

### 2.3 `include/` против `src/`: почему это про время, а не про аккуратность

Публичный заголовок лежит в `include/trafficwatcher/core/Engine.h`, потребитель пишет
`#include <trafficwatcher/core/Engine.h>`. Что это даёт практически:

- **Одна строчка вместо трёх.** `target_include_directories(... PUBLIC include)` — и префикс пути уже часть имени
  заголовка; нельзя «забыть добавить ещё один путь».
- **Граница видна файловой системой.** `#include "engine_p.h"` из приложения не сломается на компиляции, только
  если путь был добавлен глобально; с `include/` он сломается — и это правильное поведение.
- **Установка тривиальна.** `install(TARGETS ... FILE_SET HEADERS ...)` (CMake ≥ 3.23) ставит именно публичную
  часть, и наш будущий `find_package(TrafficWatcher)` увидит ровно тот API, который мы обещали.
- **Переименование безопасно.** Имя namespace в путях (`trafficwatcher/`) — это API-контракт; в Qt6 оно же
  попадает в URI QML-модуля. Отсюда ADR-0002 на имена.

Мини-практика 2 (2 минуты). Добавь в свой мини-проект `add_library(TrafficWatcher::A ALIAS a)` и
опечатайся в имени при линковке. Сравни текст ошибки с тем, что даёт просто `a` (ответ: для имени без
namespace CMake не знает, опечатка это или внешний таргет, и ошибка появится позже — на линковке).
Затем проверь утверждение тонкости 3: вынеси `a` в `src/CMakeLists.txt` (`add_subdirectory(src)`),
алиас оставь там же и попробуй линковать `TrafficWatcher::A` из корневой `add_executable` — ошибка
configure появится сразу, и она про область видимости, а не про имя.

### 2.4 Тонкости ключевых слов

**Тонкость 3.** У `ALIAS` есть область видимости, и о ней вспоминают ровно один раз — когда проект
перестаёт быть однофайловым. Таргет и его алиас видимы в каталоге, где объявлены, **и во всех
вложенных**; в родительском или соседнем поддереве — нет. Пока `add_subdirectory(tests)` идёт из
корня, а `tw_core` объявлен там же, разницы ты не увидишь. Она появится, когда библиотеку начнут
объявлять внутри `src/core/CMakeLists.txt`, а линковать из `tests/unit/CMakeLists.txt`: ошибка вида
`... is not a target` при полностью корректном имени. Правильное решение — не `GLOBAL`-таргет
(он легально разрешает линковать то, что должно быть видно только соседу), а порядок: alias объявляется
там же, где и цель, и потребители всегда ниже по дереву. `GLOBAL` остаётся для `IMPORTED`-обёрток из
`find_package` — вернёмся в модуле 2.

**Тонкость 4.** `INTERFACE`-таргет с флагами — это обязательство перед **чужими** сборками.
`TrafficWatcher::Warnings` (§4.3) мы подключаем как `PRIVATE`, и пока всё живёт в build-директории,
невидно. Но если однажды `tw_core` начнёт экспортироваться (`install(EXPORT …)`, а это модуль 11 для
плагинов M3), свойства уедут в пакет вместе с ним, и потребитель с компилятором, который не знает
`/permissive-`, получит наши флаги в свою сборку. Защита — `$<BUILD_INTERFACE:...>` внутри таких
свойств: требование действует в графе этой сборки и не экспортируется. Проверить без установки
пакета нельзя, поэтому правило фиксируем сразу: **в `INTERFACE_*` всё, что не является частью API,
оборачивается в `$<BUILD_INTERFACE:>`,** и в этом уроке это относится к флагам, но не к
`cxx_std_20` и не к include-путям — они как раз часть обязательства.

## 3. Пять фаз: почему у ошибки есть адрес

### 3.1 Механика

```
configure  читает CMakeLists, выполняет find_package/if(), пишет CMakeCache.txt   cmake --preset dev
generate   порождает файлы сборки для генератора                                  (сразу после configure)
build      компилирует и линкует                                                   cmake --build --preset dev
install    раскладывает по CMAKE_INSTALL_PREFIX                                    cmake --install build/dev
test       прогоняет тесты по контракту CTest                                      ctest --preset dev
```

Каждая фаза видит только то, что ей доступно. Отсюда правило диагностики: **сообщение об ошибке всегда
относится к фазе, в которой оно напечатано** — и чинить надо в этой фазе, а не там, где «неудобно».

| Фаза | Что она может знать | Типичная ошибка этой фазы | Где чинить |
|---|---|---|---|
| configure | содержимое файлов, кэш, окружение пресета | `Could not find a package configuration file provided by "Qt6"` | `CMAKE_PREFIX_PATH`/`QT_DIR` в пресете, а не в `CMakeLists.txt` |
| generate | результат configure | `No generator was provided and generator is required` | вызов с `-G` или пресетом |
| build | наличие файлов, компилятор | `undefined reference to ...` | `target_link_libraries`, порядок/наличие зависимости |
| install | собранные артефакты | `install TARGETS given target "x" which does not exist` | `EXPORT`/`NAMELINK`-политика, опечатка в имени таргета |
| test | собранные бинарники | тест падает только в CTest, но не из IDE | свойства теста: `WORKING_DIRECTORY`, `ENVIRONMENT` (модуль 8.3) |

### 3.2 Почему «деплой» живёт на фазе install

Зависимости Qt (DLL, плагины, QML-импорты) нельзя вычислить надёжнее, чем «то, что реально слинковалось и
куда положилось». На фазе configure мы этого ещё не знаем. Поэтому в Qt6 деплой описывается как
install-time скрипт — `qt_generate_deploy_qml_app_script()` (модуль 11), — а не как генерация `.bat` на
configure, как это было в `44ffd1b`. Разница не в стиле, а в том, какая информация доступна в момент
исполнения: скрипт, сгенерированный на configure, всегда врёт про новые плагины.

Мини-практика 3 (2 минуты). В мини-проекте напиши `find_package(NoSuchPackage REQUIRED)` и запусти
configure. Найди в выводе фразу `CMake Error at CMakeLists.txt:N (find_package)`. Теперь убери её и
дополни ошибку компиляции в `main.cpp`. Сравни: в первом случае build-файлы вообще не создались — это
значит, что чинить надо пресет/окружение, а не код.

### 3.3 Out-of-source: почему обязательно

Всё состояние configure (кэш, generate-файлы, `compile_commands.json`) привязано к build-директории.
Запуск `cmake .` кладёт `CMakeCache.txt` рядом с кодом, и тогда: (а) одна конфигурация на дерево вместо
матрицы «ОС × компилятор × config», (б) IDE индексирует генерируемые файлы как исходники, (в) `git status`
загрязнён сгенерированными файлами. `.gitignore` у нас уже закрывает `cmake-build-*/`, `build/`, `out/` —
держим все конфигурации внутри этих каталогов, иначе ignore-правила перестают работать.

## 4. Конфигурации и генераторные выражения

### 4.1 Механика: кто выбирает конфигурацию

| Генератор | Модель | Когда известна конфигурация | `CMAKE_BUILD_TYPE` |
|---|---|---|---|
| Makefiles, Ninja | single-config | на configure | заполнен |
| **Ninja Multi-Config** | multi-config | на build (`--config`) | **пуст** |
| MSBuild (Visual Studio) | multi-config | на build / в IDE | **пуст** |
| Xcode | multi-config | на build / в IDE | **пуст** |

Отсюда главное следствие урока: код вида

```cmake
if(CMAKE_BUILD_TYPE STREQUAL "Debug")      # на MSBuild/Xcode — всегда false
  target_compile_definitions(tw_core PRIVATE TW_VERBOSE_LOG)
endif()
```

не «иногда не срабатывает», а **никогда** не сработает на многоконфигурационном генераторе. Причина: `if()`
выполняется один раз на configure, когда конфигурация ещё не выбрана. Мы же целимся в то, чтобы один и тот
же `CMakeLists.txt` работал на Windows (MSVC), Linux (Make/Ninja) и macOS (Xcode/Ninja), поэтому условие
нужно то, которое вычисляется **позже** — для каждого таргета и каждой конфигурации отдельно.

### 4.2 Генераторное выражение — это отложенное условие

`$<...>` записывается в свойство как текст и вычисляется CMake на generate-фазе, зная конкретный
таргет × конфигурация × язык. Три класса, закрывающие 95% задач:

```cmake
# 1) условия — аналог if(), но позже и без ветвления в файле
$<$<CONFIG:Debug>:TW_VERBOSE_LOG>
$<$<OR:$<CONFIG:Release>,$<CONFIG:MinSizeRel>>:QT_NO_DEBUG_OUTPUT>
$<$<AND:$<CXX_COMPILER_ID:GNU>,$<PLATFORM_ID:Linux>>:-fno-plt>

# 2) интроспекция графа — значения становятся известны только к концу configure
$<TARGET_FILE:tw_core>  $<TARGET_FILE_DIR:tw_app>  $<INSTALL_PREFIX>  $<COMPILE_LANGUAGE:CXX>

# 3) конвенции Qt — пути, которые знает только deploy-механика
$<QT_DEPLOY_QML_IMPORT_PATH>  $<QT_QML_SOURCE_FILES_WITH_PREFIX:/qt/qml>
```

Правило большого пальца, которое экономит споры:

> Флаги, определения, include-пути, зависящие от конфигурации/компилятора/ОС, — пишем генераторным
> выражением внутри `target_*`. Решения уровня «существует ли эта библиотека / этот каталог / применять ли
> эту политику» — оставляем в `if()`, потому что они принимаются один раз и влияют на структуру файла.

Пример осознанного `if()`: `if(WIN32) add_subdirectory(src/platform/win) else() ... endif()` — здесь мы
выбираем **состав графа**, а не флаг. Выбор состава таргетов не может быть отложен до generate.

### 4.3 Как мы будем с этим работать (наш план, а не твоя задача сегодня)

Дальше по курсу появится `cmake/TwCompilerWarnings.cmake` с `INTERFACE`-таргетом
`TrafficWatcher::Warnings`: набор `-Wall -Wextra -Wshadow -Wold-style-cast -Wconversion` (GNU/Clang) и
`/W4 /permissive-` (MSVC), подключаемый каждой библиотекой одной строкой
`target_link_libraries(tw_core PRIVATE TrafficWatcher::Warnings)`.

Почему `INTERFACE`-таргет, а не функция `add_warnings(all)`: требования тогда живут в графе, и их видно в
`deps.dot`; функция же — это скрытая магия, результат которой не отобразишь.
Почему `-Werror`/`/WX` вынесен в `option(TW_PEDANTIC)`, включаемую только CI-пресетом: предупреждение —
это информация, а не ошибка, пока его не увидел человек. Жёсткий гейт нужен в одном месте с фиксированным
компилятором; локально он превращает обновление тулчейна в неделю рефакторинга чужих предупреждений.
Это решение — ADR-0003, и аргументы «против» в нём обязательны.

Мини-практика 4 (3 минуты). В мини-проекте добавь
`target_compile_definitions(a PRIVATE $<$<CONFIG:Debug>:FROM_GENEX>)` и собери Debug и Release одним
`cmake --build . --config Debug` / `--config Release`. Затем убедись, что `if(CMAKE_BUILD_TYPE)`-вариант
на том же генераторе не даёт ничего. Именно этот эксперимент стоит прогнать один раз, чтобы тема
«multi-config» перестала быть абстракцией.

Два продолжения той же практики — на тонкости §1.5 и §4.4:

1. Дай `a` требование `cxx_std_14`, а `m` — `cxx_std_20` (или наоборот), собери с `--verbose` и найди
   флаг стандарта в строке компиляции каждого файла: он окажется один и тот же, максимальный. Это
   проверка тонкости 1 на своей машине.
2. Увидеть результат выражения без компилятора можно так:
   `file(GENERATE OUTPUT "genex-$<CONFIG>.txt" CONTENT "[<$<CONFIG:Debug>:only-debug>]")` — в
   build-каталоге появятся отдельные файлы на каждую конфигурацию, и в них видно, что в Release от
   элемента остаётся пустота (она и удаляется из списка опций). Тем же способом проверяется, что
   `SHELL:`-пара «флаг + значение» не раскололась на два элемента.

### 4.4 Тонкости выражений

**Тонкость 5.** Пустой результат выражения **удаляется из списка**, и этим надо пользоваться осознанно.
`$<$<CONFIG:Debug>:-fno-omit-frame-pointer>` в Release превращается в пустоту, и CMake не передаёт
компилятору ничего — это хорошо. Плохо начинается, когда условной делают не весь элемент, а его
часть: `target_compile_options(a PRIVATE -Xlinker $<$<CONFIG:Debug>:-debug>)` оставляет в Release
висячий `-Xlinker`, который съест следующий аргумент линковки, — и ошибка появится в совершенно другом
месте (или не появится: просто библиотека перестанет линковаться с нужной опцией). Правило:
**условие оборачивает аргумент целиком, включая флаг-ключ**, а для пар вида «флаг + значение»
используют `SHELL:` — `"SHELL:-Xlinker -debug"`, чтобы CMake считал пару одним элементом и не
схлопнул повторяющиеся значения.

**Тонкость 6.** Выражение вычисляется **для пары «таргет × конфигурация»**, а не один раз на таргет, где
оно написано. Отсюда два следствия. Первое: `$<CONFIG:…>` внутри `PUBLIC`-свойства `tw_core`
означает конфигурацию того, для кого сейчас генерируется сборка, — то есть у `tw_app` в Debug и у
теста в Release одно и то же свойство даст разные флаги. Читать такие места надо не там, где они
записаны, а в `--verbose`-логе конкретной цели. Второе: выражения не раскрываются там, где нужна
строка — в `if()`, `string()`, `list()` они остаются текстом (`if("$<CONFIG:Debug>" STREQUAL "Debug")`
— всегда ложь). Поэтому граница из §4.2 проходит не по стилю, а по фазе: знание нужно на configure —
только `if()` и переменные; знание про конкретную сборку — только выражение. Полный список классов
выражений — в `cmake-generator-expressions(7)` (`cmake --help-property-list` их не показывает), и этот
раз документ лучше один раз прочитать целиком, чем искать по симптому.

## 5. `CMakePresets.json`: почему знание должно лежать в репозитории

### 5.1 Механика

Пресет — именованный набор параметров одной из четырёх операций (configure/build/test/install) в файле
`CMakePresets.json` в корне проекта. Вызов: `cmake --preset <имя>`, `cmake --build --preset <имя>`,
`ctest --preset <имя>`, `cmake --install --preset <имя>`. Схема версионирована; актуальная для нас — v6
(проверь поддержку своей версии: `cmake --help-presets`, и версию, которую понимает CLion 2026.1).

```jsonc
{
  "version": 6,
  "configurePresets": [
    {
      "name": "qt6-base", "hidden": true,                 // (1) шаблон, не вызывается напрямую
      "binaryDir": "${sourceDir}/build/${presetName}",    // (2) одна build-директория на пресет
      "cacheVariables": {
        "CMAKE_CXX_STANDARD": "20",                       // (3) требования тулчейна, а не кода
        "CMAKE_PREFIX_PATH": "$env{QT_DIR}",              // (4) путь к Qt из окружения
        "BUILD_TESTING": "ON",
        "CMAKE_EXPORT_COMPILE_COMMANDS": "ON"             // (5) база для clangd/clang-tidy
      }
    },
    {
      "name": "win-msvc", "inherits": "qt6-base",         // (6) матрица без дублирования
      "generator": "Ninja Multi-Config",
      "environment": { "QT_DIR": "C:/Qt/6.10.2/msvc2022_64" },
      "vendor": { "jetbrains.com/clion": { "toolchain": "MSVC" } }  // (7) IDE берёт то же знание
    }
  ],
  "buildPresets": [{ "name": "win-msvc-debug", "configurePreset": "win-msvc", "configuration": "Debug" }],
  "testPresets":  [{ "name": "win-msvc-debug", "configurePreset": "win-msvc", "configuration": "Debug",
                     "output": { "outputOnFailure": true } }]
}
```

На что смотреть в этом файле как на источник правил:

- **(1)+(6)** `hidden` + `inherits` превращают матрицу «ОС × компилятор × конфигурация × сборка Qt» в
  наследование, а не в копипасту. Это то, что потом делает CI-файл длиной 20 строк (урок 1.2, модуль 12).
- **(2)** `binaryDir` с именем пресета — почему у нас может одновременно существовать `build/win-msvc` и
  `build/win-mingw`, и почему удаление одной не ломает другую.
- **(4)** путь к Qt — **не** в `CMakeLists.txt`. Причина не в стиле: у Qt-пути четыре разных значения
  (моя машина, VDS-воркер, CI-контейнер, ноутбук напарника), и ни одно из них не является свойством
  исходного кода. Один хардкод в модуле `QtSetup.cmake` — и сборка на чужой машине невозможна без правки
  файла в git.
- **(7)** `vendor.jetbrains.com/clion` — IDE читает тот же файл, что и CLI и CI. Это и есть ответ на вопрос
  «почему у меня собирается, а в CI нет»: раньше это были три разных места с тремя наборами флагов.

### 5.2 Почему `CMakeUserPresets.json` игнорируется

Правило: общее знание (генератор, флаги, имена пресетов) — в репозиторий; личное (путь к моей копии Qt,
моя архитектура, моя обёртка компилятора) — в `CMakeUserPresets.json`, который **не** коммитится
(у тебя это уже в `.gitignore`, строка 33). Он наследует общие пресеты, поэтому CI и локальная сборка
расходятся только тем, чем должны.

### 5.3 Что будет, если нарушить

| Нарушение | Симптом через месяц |
|---|---|
| флаги/пути живут в `CMakeLists.txt` | сборка на второй ОС требует правки файла; ветка «починим CI» живёт вечно |
| пресетов нет, все вызывают `cmake` вручную с `-D` | никто не может повторить прогон, включая тебя; CI придётся описывать заново, и он будет собирать не то, что собираешь ты |
| в multi-config пресете задан `CMAKE_BUILD_TYPE` | конфигурация выбирается дважды — из пресета и из генератора, и результат зависит от порядка; `ctest --preset` ищет тесты не в той директории |
| `CMAKE_EXPORT_COMPILE_COMMANDS` не включён | `clang-tidy`/`clangd` работают «вслепую», без флагов; модуль 10 упирается в это сразу |

Про последнюю строку честно: исторически compile-commands генерировали только Makefiles/Ninja; для
MSBuild-генераторов поддержка появилась недавно (CMake 4.x, отдельная опция/команда). Проверь поведение на
своём CMake 4.3.2 и запиши результат в ADR-0001 — от этого зависит, на каком генераторе мы гоняем линтер в CI.

Мини-практика 5 (1 минута). `cmake --list-presets` в каталоге с файлом пресетов. Затем создай **один**
configure-пресет с `CMAKE_CXX_STANDARD=17` и второй, наследующий его, с `20`, и посмотри в
`build/<name>/CMakeCache.txt`, какое значение победило и почему (ответ: дочерний `cacheVariables`
перезаписывает родительский, потому что наследование — это слияние словарей, а не «кто первый сказал»).

Замерено на этой машине (PowerShell), не «вообще»:

| Компонент | Факт | Что делать |
|---|---|---|
| `cmake` | **4.3.2** | оставляем; знай, что `find_package(Qt5)` на CMake 4 падает — поддержка `cmake_minimum_required` < 3.5 удалена, поэтому старая ветка на этой машине не конфигурируется |

| Компилятор | Visual Studio в стандартных путях не найдена, `cl.exe` вне PATH, `vswhere.exe` нет | нужен **MSVC 2022 (v143)**: `winget install Microsoft.VisualStudio.2022.BuildTools` с workload «Desktop development with C++»; либо GCC 13+/Clang 17+ |
| MinGW | только **GCC 8.1** | блокер для C++20: concepts — GCC 10, `<ranges>` — GCC 11, `<format>` — GCC 13. Годится как второй, проверочный билд, не как основной |
| `ninja` | нет в PATH | поставить (`choco install ninja` / компонент Qt-installer); CLion поставляет свой, но CI и консольный прогон требуют системный |

Версии появления фич в компиляторах я привожу по памяти — перед выбором тулчейна сверь с таблицей поддержки
и запиши в ADR-0001. Само решение от этого не меняется: **GCC 8.1 не годится как основной тулчейн курса**.

**Проверка 1 — тулчейн умеет C++20** (один файл, без проекта):

```cpp
#include <concepts>
#include <format>
#include <ranges>
template <std::integral T> constexpr auto twice(T v) { return v * 2; }
int main() { auto s = std::format("{}", std::views::iota(0, 3) | std::ranges::distance()); return twice(s) - 6; }
```

Смотри на то, что именно проверяет каждая строка: `concepts` — наличие библиотечных концептов,
`std::integral` и constrained-шаблон — работу constraints, `<ranges>`+`std::ranges::distance` — pipeline-синтаксис
и ADL-closures, `<format>` — самый поздний из трёх, он требует и свежий компилятор, и самую свежую
стандартную библиотеку. Если файл компилируется — модуль 3 реально проходим. Если нет — узнаём это сегодня, а не на уроке 3.2.

**Проверка 2 — Qt 6.10 виден CMake**: пустой проект-однострочник с
`find_package(Qt6 REQUIRED COMPONENTS Quick)`, сконфигурированный **из пресета**, а не запуском из IDE.
Так ты убеждаешься, что цепочка `QT_DIR → CMAKE_PREFIX_PATH → find_package` работает без участия человека.

### 7.2 Репозиторий

5. `CMakeLists.txt` (сейчас 2 строки): `cmake_minimum_required(VERSION 3.28)` и

8. Скелет приложения, а не «пустой каркас»: `include/trafficwatcher/core/Mode.hpp` + `src/core/mode.cpp`

   `src/app/main.cpp` (`QGuiApplication`, QML ещё нет) → `tw_app`, линкуется только к `TrafficWatcher::Core`.

   вырастет в уроке 2.1. Никаких `include_directories`/`link_libraries` верхнего уровня, никаких
   `set(CMAKE_CXX_STANDARD ...)` вне пресетов, никакого `file(GLOB)`.
9. Контейнер для тестов (не сами тесты): `include(CTest)` в верхнем `CMakeLists.txt`, `tests/CMakeLists.txt`,

- [ ] `cmake --preset <win-...>`, затем `cmake --build --preset <...>` проходят с нуля: удалил `build/` →
      зелёный прогон без единого ручного `-D`.
- [ ] `cmake --graphviz=build/deps.dot build/<presetName>` показывает `tw_app → tw_core → Qt6::Core`
      (если в комбинации с пресетом опция не сработает на твоём CMake — используй явный build-каталог и
      запиши это в ADR-0001). `.dot` открыть глазами: это самый быстрый способ увидеть propagated requirements.
- [ ] CLion подключён **через пресет** (Profile → CMake options = «Use preset»), а не ручными полями.
- [ ] `ctest --preset ...` зелёный: тривиальный тест из п.9 найден и прошёл (первый зелёный лот CTest).

      дальше каждый урок будет менять именно его.
- [ ] В `Mode.hpp` и в `main.cpp` стоит однострочная пометка «строительный код; заменяется в уроке 6.1 /

## 8. Подмеченные ошибки в текущем состоянии репозитория

1. `CMakeLists.txt:2` — `project(TrafficLight ...)`: имя проекта ≠ имя репозитория и будущего бинарника.
   В Qt6 имя проекта попадает в URI QML-модуля (`qt_add_qml_module`), в `CPACK_PACKAGE_NAME` и в
   target-namespace. Менять потом — менять API. Реши заодно: `TrafficWatcher` для бренда и таргетов,
   `trafficwatcher` для include-путей и URI — и зафиксируй в ADR-0002.
2. `cmake_minimum_required(VERSION 3.16)` — легально на CMake 4.3, но ниже требований Qt 6.10 (тот сам
   требует ≥ 3.22; сверь точное число по выводу `find_package`).
3. Нет `include(CTest)`/`enable_testing()` и нет `CMakePresets.json`. Без них модули 8 и 12 придётся
   дописывать задним числом во все файлы проекта.
4. `.gitignore:10` — `*.cmake` (задание 6). Пока папки `cmake/` нет, проблема невидима: это самый
   «дешёвый» из всех багов и самый дорогой по времени обнаружения.
5. Нет `.editorconfig` / `.clang-format` / `.qmllint.ini`: форматирование без конфига = диффы, в которых не
   видно содержательных правок. `.clang-format` и `.qmllint.ini` заводим на уроке 2.1, `.editorconfig` можно сейчас.
6. Кириллические коммиты отображаются как `╨Ю╤Б╨╜╨╛╨▓╨╜` — это кодировка консоли и `i18n.*`. Починить сейчас:
   те же строки поедут в логи CI и в заметки CDash (модуль 12), и разбирать по ним «красный ночной прогон»
   будет невозможно.
7. В истории нет ни тега, ни версии. `project(VERSION 0.1.0)` заодно даст корректный источник номера
   версии для `CPACK_PACKAGE_VERSION` и для `TW_VERSION_*`-определений — вместо старого способа
   «`-DPROJECT_VERSION=...` только в Debug-конфиге».

## 9. От чего мы уходим: 10 минут про Qt5-стиль

Полный разбор старого проекта — в [`legacy-description.md`](../legacy-description.md). Здесь только
механизм: почему те же самые приёмы были нормой и перестали ею быть.

| Приём в `44ffd1b` | Почему он работал тогда | Почему он перестаёт работать у нас |
|---|---|---|
| `include_directories`/`add_definitions` на верхнем уровне, списки файлов через `PARENT_SCOPE` | один таргет-приложение: «всем» и «мне» совпадали | появляется `core` + тесты + платформенный слой: требования начинают течь туда, где их не просили (§1.3) |
| `set(CMAKE_CXX_STANDARD 17)` в `cmake/Defines.cmake` | одно значение для всех, всегда | стандарт становится требованием таргета: `cxx_std_20` в ядре, конкретный feature-set в тестах; глобальная переменная не участвует в графе |
| `find_package(Qt5)`, `Qt5::Core`, путь к Qt внутри модуля | одна машина, один Qt, один компилятор | три ОС, два кита, CI: путь обязан приходить из пресета, а имена целей — быть versionless (`Qt::Core`) |
| `qmlRegisterType` + `.qrc` + ручной `.qmldir` | другой механики не было | `qt_add_qml_module` + `QML_ELEMENT` дают регистрацию на сборке, `qmlcachegen`, qmllint-автодополнение и работу в статической сборке (модуль 2) |
| `if(WIN32)`/`if(MSVC)` по дереву + `/W4 /WX` всегда | один компилятор, один «правильный» набор флагов | multi-config и матрица компиляторов: флаги — генераторными выражениями (§4), `-Werror` — только в CI-пресете (§4.3) |

Три вещи из старого кода стоит сохранить как инстинкт: генераторные выражения уже использовались правильно;
`cmake/*.cmake` были разнесены по ответственностям; контроллер, модель и UI-компоненты были разделены.
