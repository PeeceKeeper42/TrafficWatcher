## 0. Чему учит урок и как с ним работать

После урока ты умеешь:

1. **Предсказать команду компиляции** конкретного файла до запуска сборки: какие `-I`/`/I`, какой
   `/std:`, какие определения он получит — и объяснить, откуда каждое из них приехало.
2. **Выбрать `PRIVATE`/`PUBLIC`/`INTERFACE` по признаку API**, а не по признаку «чтобы слинковалось», и
   назвать цену ошибки в секундах сборки и в связанных слоях.
3. **Определить фазу по тексту ошибки** (configure / generate / compile / link / install / test) и чинить
   в том файле, который за эту фазу отвечает.
4. **Объяснить, почему `if(CMAKE_BUILD_TYPE STREQUAL "Debug")` молчит** на multi-config генераторе, и
   написать то же самое генераторным выражением.
5. **Перенести знание о тулчейне в пресет** так, чтобы один и тот же файл читали консоль, CLion и CI.
6. **Назвать блокеры своей машины по замерам** и снять их до того, как они станут причиной «урок не
   собирается».

Отдельное правило урока, не входящее в список целей: про каждый созданный файл ты называешь, в каком
уроке он умрёт (§0.2). Строительный код без записанного срока жизни — это долг, а не каркас.

Как устроен урок. Теоретический раздел всегда идёт по одной цепочке: **механика** (как работает на самом
деле) → **почему сделано именно так** (какую проблему покупает) → **что будет, если нарушить** (конкретный
симптом, таблицей) → **мини-практика** (2–5 минут в терминале). Внутри раздела стоят абзацы
**Тонкость N.** — неочевидное поведение уровня middle, у которого есть проверяемое следствие. Новые
конструкции получают **паспорт** (§2.5 `AGENTS.md`): полная сигнатура, формы аргументов, где применима,
где неприменима, best practice со следствием, справка middle и команда проверки. В конце урока все
паспорта свёрнуты в таблицу (§15) — по ней урок перепробегается за пять минут.

Задание тоже двухслойное: §9.1 — что должно получиться и почему, §9.2 — **прямые шаги** «создай файл, в
нём должно быть …», каждый со своей командой проверки, §9.3 — приёмка. Шаг не считается закрытым, пока
его проверка не выполнена.

Термины, которые дальше идут без перевода:

| Термин | Что это |
|---|---|
| **Таргет** | именованная единица результата сборки: библиотека, исполняемый файл, объектная библиотека или `INTERFACE`-набор свойств. Создаётся `add_library` / `add_executable` |
| **Требование (usage requirement)** | то, что нужно таргету для компиляции и линковки: include-пути, определения, флаги, стандарт языка, другие таргеты |
| **Распространение (propagation)** | требование, помеченное `PUBLIC`/`INTERFACE`, автоматически достаётся всем, кто линкует этот таргет |
| **Свойство таргета** | именованное значение (`INCLUDE_DIRECTORIES`, `COMPILE_FEATURES`, `POSITION_INDEPENDENT_CODE`); часть свойств имеет `INTERFACE_`-двойника — «это для потребителей» |
| **Генератор** | программа, которой CMake отдаёт сборку: Ninja, Makefiles, Visual Studio, Xcode. Определяет, одно- или многоконфигурационный проект |
| **Кэш** | `CMakeCache.txt` в build-каталоге: итоговые значения переменных. Источник правды при повторном configure |
| **Пресет** | именованный набор параметров одной операции (configure / build / test / package / workflow) в `CMakePresets.json` |
| **Строительный код** | временная заглушка, нужная чтобы графу и первому тесту было на чём существовать; имеет записанный урок удаления |

Мини-практика 0 (1 минута, исполняется на этой машине прямо сейчас):

```powershell
cmake --version                     # замерено сегодня: 4.3.2
cmake --help-command add_library    # точная сигнатура твоей версии, а не чужой
cmake --help-manual-list            # полка руководств: 27 строк вывода на этом CMake
```

Смысл: `--help-command`, `--help-property`, `--help-variable`, `--help-policy`, `--help-module`,
`--help-manual` печатают документацию **той версии, которая у тебя стоит**. Это ответ на вопрос «где
взять точную форму»: не в чужом блоге и не в памяти ассистента. Все сигнатуры в паспортах ниже сверены
этими командами на CMake 4.3.2; если у тебя другая версия — перепроверяй той же командой.

### 0.1 Зачем это нужно именно сейчас, если впереди M2 и M3

Требования вех формулируются не классами, а свойствами графа. Пять строк ниже — это то, что дешевле
заложить сегодня, чем переписывать через полгода:

| Требование из [`readme.md`](../readme.md) | Где оно обеспечивается технически |
|---|---|
| M3: ядро симуляции считается **headless** на воркере | у `tw_core` в propagated-требованиях нет `Qt::Quick`/`Qt::Gui`; это видно в `--graphviz` за секунду |
| M3: детерминированность и replay | ядро линкуется в тест без GUI-слоя: тест физически не может дёрнуть отрисовку |
| M1: тест ядра собирается быстрее приложения | у тестового таргета одна зависимость — `TrafficWatcher::Core`, а не «весь проект» |
| M2/M3: три ОС и два тулчейна | путь к Qt и флаги живут в пресете, а не в `CMakeLists.txt`; матрица = наследование пресетов |
| M3: долгие прогоны и sanitizers | ещё один configure-пресет с другими `cacheVariables`, без правок в коде |

Каждая строка стоит сегодня нескольких строк CMake. Цена промедления — не «некрасиво», а переписывание
половины файлов в момент, когда в них уже есть домен.

## 1. Граф: вершины, рёбра и свойства

### 1.1 Механика

CMake строит направленный граф. Вершины — таргеты, рёбра — зависимости, объявленные
`target_link_libraries`. Каждый таргет несёт набор свойств; часть свойств имеет `INTERFACE_`-двойника, и
именно двойник означает «это нужно не только мне, но и тому, кто от меня зависит».

Минимальный граф этого урока выглядит так (сниппет для чтения; в проект ты напишешь его сам по шагам
5–6 из §9.2):

```cmake
add_library(tw_core STATIC core/mode.cpp)
target_compile_features(tw_core PUBLIC cxx_std_20)          # (1)
target_include_directories(tw_core PUBLIC
  $<BUILD_INTERFACE:${PROJECT_SOURCE_DIR}/include>)         # (2)
target_link_libraries(tw_core PUBLIC Qt::Core)              # (3)

add_library(TrafficWatcher::Core ALIAS tw_core)             # (4)

add_executable(tw_app app/main.cpp)
target_link_libraries(tw_app PRIVATE TrafficWatcher::Core Qt::Gui)  # (5)
```

Что физически происходит при сборке `tw_app`:

- **(1)** `cxx_std_20` — не «включить флаг», а требование к языку. CMake берёт максимум из требований
  таргета и его зависимостей и сам подставляет флаг компилятора (`/std:c++20`, `-std=c++20`).
- **(2)** `include/` становится публичной частью API: любой, кто линкует `tw_core`, получает путь к
  заголовкам автоматически. `$<BUILD_INTERFACE:>` подставляет содержимое, когда таргет используется
  внутри этой же сборки (и при `export()`); в файл, который создаёт `install(EXPORT)`, оно не уедет —
  там работает `$<INSTALL_INTERFACE:>` (§4.5).
- **(3)** `Qt::Core` публично, потому что QtCore участвует в сигнатурах открытого заголовка. Потребителю
  нужен путь к его заголовкам, иначе он упадёт на **компиляции**, а не на линковке.
- **(4)** alias даёт имя с namespace. Опечатка `TrafficWatcher::Cor` — ошибка configure, а не загадочная
  ошибка линкера через минуту.
- **(5)** `tw_app` получает (1), (2), (3) бесплатно. `Qt::Gui` перечислен явно, потому что
  `QGuiApplication` включён в `main.cpp` самого приложения, а не в заголовок ядра.

Откуда в графе берётся `Qt::Core`: это **IMPORTED**-таргет, его создаёт `find_package(Qt6 …)` на configure.
Своего кода у него нет, есть описание готового артефакта и набор требований, которые он передаёт
потребителю. Qt6 объявляет и имена с версией (`Qt6::Core`), и безверсионные (`Qt::Core`) — про это
[`course.md`](../course.md), модуль 0. Какое имя выбрать для проекта — решение ADR-0002; проверяется
оно просто: после `find_package` таргет либо существует (`if(TARGET Qt::Core)`), либо нет.

### 1.2 Почему сделано именно так

Потому что флаг компиляции — следствие того, **что именно** включает данный файл. Раньше это знание
поддерживалось вручную: автор `CMakeLists.txt` должен был помнить, что тестам тоже нужен путь к QtCore.
Модель требований переносит знание в место определения: библиотека сама говорит, что нужно её
потребителю. Отсюда три свойства, которые мы покупаем:

1. **Локальность правки.** Заменил внутреннюю реализацию с `QtConcurrent` на `std::thread` — тронул одну
   строку `PRIVATE`; у потребителей граф не перестроился.
2. **Проверяемость границ.** «Ядро не знает про GUI» становится фактом, который видно в `deps.dot` и
   который можно защищать автоматической проверкой (модуль 10), а не уговором на ревью.
3. **Переиспользуемость.** Тот же `tw_core` линкуется в приложение, в тест и в headless-прогон без
   копирования флагов: флаги едут вместе с таргетом.

### 1.3 Что будет, если нарушить

| Нарушение | Симптом | Механизм |
|---|---|---|
| `include_directories()` на верхнем уровне | тест ядра компилируется, но тянет GUI; чужой `3rdparty` собирается с нашими `/W4 /WX` | свойство записывается в **директорию** и достаётся всем последующим таргетам независимо от их нужд |
| `PUBLIC` «на всякий случай» | правка одного заголовка пересобирает всех потребителей; `Qt::Quick` просочился в тесты | мы объявили пути и библиотеки частью API, и CMake честно транслирует их вниз по графу |
| список файлов в переменной + `PARENT_SCOPE` | родитель не собирается без знания имён файлов ребёнка; `file(GLOB)` молча игнорирует новый файл | список источников — свойство таргета; он должен создаваться там, где лежат файлы |
| `target_link_libraries(tw_app …)` без keyword | граф выглядит правильно, но граница не проверяема | прямая форма означает «публично» (см. паспорт §1.5), и `--graphviz` не показывает, что это случайность |

### 1.4 Мини-практика 1 (3 минуты)

Собери мини-проект из двух таргетов в `$env:TEMP\cmk1\` (файлы создаёшь ты; это упражнение, не проект):

```
CMakeLists.txt   # project() + add_library(a STATIC a.cpp) + add_executable(m main.cpp)
a.cpp, include/A.h, main.cpp
```

1. `target_include_directories(a PUBLIC include)` → собери, убедись, что `main.cpp` видит `#include <A.h>`.
2. Замени на `PRIVATE` → переконфигурируй в **чистый** build-каталог и прочитай ошибку целиком. Это
   ошибка **компиляции** `main.cpp`, а не `find_package` и не линковки: фаза видна по тексту.
3. `cmake --build <dir> -- -v` покажет, какой набор `-I`/`/I` реально получил `main.cpp`. Эта команда —
   основной инструмент диагностики на весь курс.

На этой машине шаг 3 сегодня не исполняется: компилятора и генератора нет (§7). Выполни его после
установки тулчейна и запиши результат в ADR-0001 — иначе мини-практика останется прочитанной, а не
проверенной.

### 1.5 Тонкости и паспорта раздела

**Тонкость 1.** Повторные вызовы `target_link_libraries` для одного таргета **дописывают** элементы в
порядке вызовов, а не перезаписывают. В справке команды это сказано прямо: «Repeated calls for the same
`<target>` append items in the order called». Следствие: порядок линковки статических библиотек
значим, и «перенести строку повыше, чтобы читалось лучше» может поменять результат линковки. С CMake
3.13 (политика `CMP0079` в новом поведении) таргет не обязан быть создан в том же каталоге, где вызов —
поэтому требования можно объявлять рядом с кодом, а не только в родительском `CMakeLists.txt`.
Проверка: `cmake --help-command target_link_libraries`, абзацы про repeated calls и `CMP0079`.

**Тонкость 2.** `ALIAS` — это имя, а не объект. В справке `target_link_libraries` и
`target_include_directories` сказано: `<target>` должен быть создан `add_*` и **не может быть ALIAS**;
`set_target_properties` добавляет: «Alias Targets do not support setting target properties». Следствие:
попытка «настроить alias» (`set_target_properties(TrafficWatcher::Core PROPERTIES …)`) — ошибка
configure, и чинить её надо в исходном таргете. Зато alias ловит опечатки в имени потребителя сразу.
Проверка: `cmake --help-command set_target_properties`.

#### Паспорт конструкций раздела

**`add_library`** — команда, фаза configure, создаёт вершину графа-библиотеки.

```cmake
add_library(<name> [<type>] [EXCLUDE_FROM_ALL] <sources>...)
add_library(<name> OBJECT <sources>...)
add_library(<name> INTERFACE)
add_library(<name> INTERFACE [EXCLUDE_FROM_ALL] <sources>...)
add_library(<name> INTERFACE SYMBOLIC)            # versionadded 4.2
add_library(<name> <type> IMPORTED [GLOBAL])
add_library(<name> ALIAS <target>)
```

- **Зачем:** объявляет библиотеку и фиксирует список её источников; `<type>` = `STATIC`/`SHARED`/`MODULE`/
  `OBJECT`, по умолчанию зависит от `BUILD_SHARED_LIBS`.
- **Формы аргументов:** семь сигнатур выше. `INTERFACE` без источников — чистый переносчик требований;
  `INTERFACE` с источниками (3.19+) — библиотека, у которой есть заголовки, но нет своего артефакта;
  `INTERFACE SYMBOLIC` (4.2+) — символическая цель без требований и без артефакта, её можно экспортировать,
  устанавливать и проверять через `if(TARGET)`: так выражают «необязательный компонент пакета».
  `IMPORTED` — готовый чужой артефакт, `ALIAS` — второе имя существующего таргета.
- **Где применима:** `tw_core` (STATIC + свой код), `TrafficWatcher::Core` (ALIAS),
  `TrafficWatcher::Warnings` (INTERFACE, урок 10), `tw_tests_support` (STATIC, урок 8).
- **Где неприменима:** готовый `.lib`/`.a` без исходников — это `IMPORTED` с `IMPORTED_LOCATION`, а не
  `STATIC` со списком несуществующих файлов: во втором случае ошибка прилетит на build, а не на configure.
- **Best practice:** источники — явным списком в команде, не `file(GLOB)` и не переменная из другого
  каталога. Иначе добавленный файл не попадёт в сборку до следующего configure, а список источников
  ребёнка перестанет жить рядом с его кодом (§1.3).
- **Справка middle:** имя с `::` легально только для `ALIAS` и `IMPORTED`. Поэтому `TrafficWatcher::Core`
  даёт ошибку configure при опечатке, а `tw_core` — задержанную ошибку линкера. `EXCLUDE_FROM_ALL` не
  запрещает линковать цель, она просто не входит в `ALL`.
- **Проверка:** `cmake --help-command add_library` (разделы Normal / Object / Interface / Imported / Alias).

**`add_executable`** — команда, фаза configure, создаёт вершину графа-исполняемого файла.

```cmake
add_executable(<name> <options>... <sources>...)
```

- **Зачем:** объявляет исполняемый файл; имя таргета логическое и глобально уникальное, имя файла
  строится по правилам платформы (`<name>.exe` на Windows).
- **Формы аргументов:** `<options>` = `WIN32` (ставит свойство `WIN32_EXECUTABLE`), `MACOSX_BUNDLE`
  (ставит `MACOSX_BUNDLE`), `EXCLUDE_FROM_ALL`. Источники можно опустить и добавить позже через
  `target_sources()` (3.11+); в списке источников допустимы генераторные выражения (3.1+).
- **Где применима:** `tw_app` сегодня; `tw_core_smoke` (тестовый исполняемый файл) на шаге 8; headless-
  прогон симуляции в модуле 14.
- **Где неприменима:** `PUBLIC`-требования у исполняемого файла — мёртвый код: потребителей у него нет,
  распространять некому. И `WIN32` «чтобы не было консоли» не ставят в уроке 1: нам нужен видимый вывод
  при старте, а подсистема Windows понадобится только при упаковке (модуль 11).
- **Best practice:** один `add_executable` на один результат; флаги и пути — через `target_*`, а не
  через глобальные команды. Иначе исполняемый файл начнёт нести требования, которые ему не нужны.
- **Справка middle:** `WIN32` меняет подсистему линковки (`/SUBSYSTEM:WINDOWS`), а не «вид окна»:
  приложение без консоли и без окна — это чёрный экран и тишина в логах. Проверяется свойством
  `WIN32_EXECUTABLE`, а не запуском.
- **Проверка:** `cmake --help-command add_executable`, `cmake --help-property WIN32_EXECUTABLE`.

**`find_package`** — команда, фаза configure, приводит в граф чужие IMPORTED-вершины.

```cmake
find_package(<PackageName> [<version>] [REQUIRED] [COMPONENTS <components>...])   # типовая форма
find_package(<PackageName> [<version>] [EXACT] [QUIET] [MODULE]
  [REQUIRED|OPTIONAL] [[COMPONENTS] <component>...]
  [OPTIONAL_COMPONENTS <component>...]
  [REGISTRY_VIEW {64|32|64_32|32_64|HOST|TARGET|BOTH}]
  [GLOBAL] [NO_POLICY_SCOPE] [BYPASS_PROVIDER] [UNWIND_INCLUDE])                 # базовая форма
```

- **Зачем:** находит внешний пакет и загружает его описание; результатом становятся переменная
  `<PackageName>_FOUND` и IMPORTED-таргеты, которые можно линковать.
- **Формы аргументов:** типовая форма (её рекомендует сама справка) и базовая; полная форма — только
  Config-режим, с `NAMES`, `CONFIGS`, `HINTS`, `PATHS`, `PATH_SUFFIXES`. Режимы два: Module (ищет
  `Find<PackageName>.cmake`) и Config (ищет `<PackageName>Config.cmake` / `<lowercase>-config.cmake`).
  `REQUIRED` останавливает configure при неудаче; после `REQUIRED` слово `COMPONENTS` можно опустить.
- **Где применимо:** `find_package(Qt6 6.10 REQUIRED COMPONENTS Core Gui)` в корне TrafficWatcher;
  `find_package(Qt6 COMPONENTS Quick QuickControls2 Test)` в уроке 2.1; `find_package(GTest)` — нет,
  тесты курса идут на QTest (урок 8).
- **Где неприменимо:** путь к пакету нельзя зашивать в `CMakeLists.txt` (`set(CMAKE_PREFIX_PATH …)`):
  это личное знание, его место — пресет или окружение. И `QUIET` без `REQUIRED` для Qt: configure
  пройдёт, а ошибка прилетит позже и в другом месте.
- **Best practice:** минимальная версия пакета — аргументом команды, а не проверкой `if` после вызова.
  Иначе на машине со старым Qt сборка начнётся и упадёт на компиляции заголовков, а не на configure.
- **Справка middle:** Config-режим создаёт кэш-запись `<PackageName>_DIR`; именно её правят, когда пакет
  «не находится». Вызов может быть перехвачен поставщиком зависимостей (dependency provider, например
  `FetchContent`), поэтому «пакет найден» не всегда означает «найден в системе».
- **Проверка:** `cmake --help-command find_package` (разделы Typical Usage, Search Modes, Basic Signature).

## 2. `PRIVATE` / `PUBLIC` / `INTERFACE`: ключевые слова как вопрос про API

### 2.1 Механика

Ключевое слово — не «область видимости переменной», а выбор **двух свойств** сразу. На примере
`target_include_directories` (формулировка из справки команды):

| Keyword | `INCLUDE_DIRECTORIES` (мне) | `INTERFACE_INCLUDE_DIRECTORIES` (потребителю) |
|---|---|---|
| `PRIVATE` | да | нет |
| `PUBLIC` | да | да |
| `INTERFACE` | нет | да |

То же правило работает для `target_compile_features` (`COMPILE_FEATURES` / `INTERFACE_COMPILE_FEATURES`),
`target_compile_options` (`COMPILE_OPTIONS` / `INTERFACE_COMPILE_OPTIONS`) и `target_link_libraries`
(`LINK_LIBRARIES` / `INTERFACE_LINK_LIBRARIES`). Отсюда мнемоника, которая не врёт: **`PUBLIC` = «это в
моём открытом заголовке», `PRIVATE` = «это только в моём `.cpp`», `INTERFACE` = «у меня нет своего кода,
я только передаю требование»**.

### 2.2 Почему `include/` против `src/` — это про время, а не про аккуратность

Публичный заголовок — это контракт, который читает каждый потребитель. Если в нём лежит
`#include <QObject>`, то QtCore обязан быть публичным требованием: иначе потребитель упадёт на
компиляции своего файла, хотя «у меня-то собирается». Если Qt используется только в `.cpp` —
требование `PRIVATE`, и правка реализации не пересобирает потребителей.

Раскладка `include/trafficwatcher/core/` против `src/core/` делает этот выбор **видимым в дереве**: то,
что лежит в `include/`, по определению контракт. Цена нарушения измеряется в секундах: публичный
заголовок, который меняется часто, превращает каждую правку в полную пересборку всех потребителей.

### 2.3 Что будет, если нарушить

| Нарушение | Симптом через неделю | Почему |
|---|---|---|
| Qt-include в публичном заголовке, но `PRIVATE` в CMake | «у меня собирается, у напарника нет»; ошибка компиляции чужого файла | потребитель не получил путь к заголовкам Qt, хотя наш заголовок их требует |
| всё `PUBLIC` | пересборка мира на каждую правку; тесты линкуют GUI | мы объявили контрактом то, что контрактом не является |
| `INTERFACE` у таргета с собственным `.cpp` | источники не компилируются, символы не находятся | `INTERFACE`-библиотека не собирает свой код: это переносчик требований, а не библиотека |
| keyword опущен в `target_include_directories` | ошибка configure | в этой команде keyword **обязателен** (в отличие от `target_link_libraries`) |

### 2.4 Мини-практика 2 (2 минуты)

В мини-проекте из §1.4 распространение видно на путях к заголовкам — без Qt и без новых команд:

1. Создай второй каталог `internal/` и положи в него `Secret.h` с одной константой. В `include/A.h`
   оставь только то, что не требует `Secret.h`.
2. Запиши `target_include_directories(a PUBLIC include)` и
   `target_include_directories(a PRIVATE internal)`.
3. Добавь в `main.cpp` строку `#include <Secret.h>` и собери. Ожидаемо: ошибка **компиляции** `main.cpp`
   «не найден файл», хотя `a.cpp` этот же заголовок видит. Это и есть граница API в чистом виде.
4. Убери строку из `main.cpp`, добавь её в `a.cpp` — собирается. Перенеси `internal` из `PRIVATE` в
   `PUBLIC`, верни строку в `main.cpp` — снова собирается, и теперь граница сломана: потребитель видит
   внутренности библиотеки.

Шаги 3–4 проверяются сегодня только на синтаксис команды
(`cmake --help-command target_include_directories`); сам прогон — после установки тулчейна (§7).

### 2.5 Тонкости и паспорта раздела

**Тонкость 3.** Обязательность keyword различается по командам, и это ловится на configure. В
`target_include_directories`, `target_compile_features`, `target_compile_options` keyword
**обязателен** — он часть сигнатуры. В `target_link_libraries` есть историческая прямая форма
`target_link_libraries(<target> <item>...)`, и она означает «transitive by default»: всё перечисленное
кладётся в `INTERFACE_LINK_LIBRARIES`, то есть ведёт себя как `PUBLIC`. Следствие: пропущенное слово в
`target_link_libraries` — не ошибка, а тихое расширение API. Проверка:
`cmake --help-command target_link_libraries`, раздел про signatures.

**Тонкость 4.** `cxx_std_20` — это «не меньше 20», и в графе побеждает **максимум** из требований таргета
и всех его зависимостей. Следствие, которое дорого стоит: библиотека, заявленная как совместимая с
C++14, в этом графе никогда не собирается под C++14 — её несовместимость всплывёт у того, кто её
подключит. Совместимость со старым стандартом проверяется отдельным прогоном (отдельный пресет или
CI-джоб), а не свойством графа. Проверка: `cmake --build <dir> -- -v` — на строке компиляции не больше
одного флага стандарта, и он взят из самого большого требования. Флага может не быть вовсе: в
`cmake-compile-features(7)` есть примечание, что при умолчании компилятора не ниже запрошенного CMake
вправе опустить `-std=`. Поэтому «флага нет» — не доказательство, что требование не применилось;
доказательство — `static_assert` на C++20-конструкции в коде.

**Тонкость 5.** Требования распространяются, а способ компиляции — нет. `POSITION_INDEPENDENT_CODE`
свойственен таргету: статическая `tw_core`, которую завтра линкуют в общую библиотеку (модуль 14 —
плагины), обязана быть собрана с PIC, иначе на Linux/macOS падает **линковка**
(`relocation R_X86_64_32 …`), а на Windows собирается без замечаний. У `INTERFACE`-таргета своего кода
нет, поэтому требование передаётся через `INTERFACE_POSITION_INDEPENDENT_CODE`. Это ошибка класса
«у меня работает», и ловится она только матрицей ОС (модуль 12). Проверка:
`cmake --help-property POSITION_INDEPENDENT_CODE` и справка по `INTERFACE_`-двойнику
(`cmake --help-property INTERFACE_POSITION_INDEPENDENT_CODE`).

#### Паспорт конструкций раздела

**`target_link_libraries`** — команда, рисует ребро графа и решает, что уедет потребителю.

```cmake
target_link_libraries(<target> ... <item>... ...)                 # общая форма
target_link_libraries(<target>
  {INTERFACE|PUBLIC|PRIVATE} <item>...
  [{INTERFACE|PUBLIC|PRIVATE} <item>...]...)                      # наша форма
target_link_libraries(<target> <item>...)                         # прямая: transitive by default
target_link_libraries(<target>
  <LINK_PRIVATE|LINK_PUBLIC> <lib>...
  [<LINK_PRIVATE|LINK_PUBLIC> <lib>...]...)                       # compatibility only
target_link_libraries(<target> LINK_INTERFACE_LIBRARIES <item>...) # compatibility only
```

- **Зачем:** объявляет зависимость и одновременно выбирает, какие требования этого ребра станут частью
  API зависимого таргета.
- **Формы аргументов:** keyword-форма с повторами keyword в одном вызове; прямая форма без keyword
  (ведёт себя как `PUBLIC`); две legacy-формы, про каждую в справке сказано «This signature is for
  compatibility only». `<item>` бывает: имя таргета, полный путь к файлу библиотеки, обычное имя
  (`foo` → `-lfoo`/`foo.lib`), link-флаг (начинается с `-`, но не `-l`/`-L`), генераторное выражение,
  пер-конфигурационные слова `debug`/`optimized`/`general`. Для флагов линкера есть portable-обёртка
  `LINKER:`. `<target>` не может быть `ALIAS`.
- **Где применимо:** все связи слоёв: `tw_app → TrafficWatcher::Core`, `tw_core → Qt::Core`,
  тест → ядро по alias (урок 8.2).
- **Где неприменимо:** когда нужно передать **флаг компиляции**, а не зависимость: для этого
  `target_compile_options`. Линковка ради «прокинуть `-W`» превращает флаг в часть API.
- **Best practice:** всегда явное keyword-слово. Прямая форма молча означает «публично», поэтому в
  ревью она читается как «автор не выбрал», а граница по ней не проверяется: `--graphviz` покажет ребро,
  но не покажет, что оно случайное.
- **Справка middle:** повторные вызовы дописывают элементы в порядке вызовов (§1.5, тонкость 1); порядок
  значим для статических библиотек; `PUBLIC` на `OBJECT`-библиотеке ведёт себя иначе, чем на `STATIC`.
- **Проверка:** `cmake --help-command target_link_libraries`.

**`target_include_directories`** — команда, пути к заголовкам мне и/или потребителю.

```cmake
target_include_directories(<target> [SYSTEM] [AFTER|BEFORE]
  {INTERFACE|PUBLIC|PRIVATE} <dir>...
  [{INTERFACE|PUBLIC|PRIVATE} <dir>...]...)
```

- **Зачем:** наполняет `INCLUDE_DIRECTORIES` и/или `INTERFACE_INCLUDE_DIRECTORIES` — то есть решает, кто
  увидит путь в `-I`/`/I`.
- **Формы аргументов:** keyword обязателен и может повторяться; `SYSTEM` помечает пути как системные
  (предупреждения из этих заголовков подавляются); `AFTER`/`BEFORE` выбирает между добавлением в конец и
  вставкой в начало независимо от умолчания.
- **Где применимо:** `PUBLIC` на `include/` у `tw_core`; `PRIVATE` на внутренний каталог реализации;
  `INTERFACE` у таргета из одних заголовков (`TrafficWatcher::TestSupport`, урок 8).
- **Где неприменимо:** глобальный `include_directories()` вместо этого вызова — свойство уедет всем
  таргетам каталога (§1.3). И относительный путь из дочернего `CMakeLists.txt`: он разрешается от
  **текущего** source-каталога, поэтому `include` в `src/CMakeLists.txt` означал бы `src/include`.
- **Best practice:** публичный путь — абсолютный через `${PROJECT_SOURCE_DIR}` и обёрнутый в
  `$<BUILD_INTERFACE:>`; для устанавливаемого пакета рядом пишется `$<INSTALL_INTERFACE:>` с относительным
  путём. Иначе абсолютный путь твоей машины уедет в `install(EXPORT)`-файл и сломает сборку у потребителя.
- **Справка middle:** вызов **добавляет** пути; команды «удалить путь» не существует. В `-I` выигрывает
  первый найденный заголовок, поэтому порядок путей — это порядок разрешения имён, а не косметика.
- **Проверка:** `cmake --help-command target_include_directories`, `cmake --build <dir> -- -v`.

**`target_compile_features`** — команда, требование к языку, а не флаг.

```cmake
target_compile_features(<target>
  {INTERFACE|PUBLIC|PRIVATE} <feature>...
  [{INTERFACE|PUBLIC|PRIVATE} <feature>...]...)
```

- **Зачем:** объявляет, какие возможности компилятора нужны таргету; если фича требует флага
  (`-std=gnu++11`, `/std:c++20`), CMake добавляет его сам.
- **Формы аргументов:** `<feature>` — либо мета-фича стандарта `cxx_std_<NN>` (в справке показан
  `cxx_std_11`; уровни стандарта перечислены в `cmake --help-property CXX_STANDARD`: 98, 11, 14, 17, 20,
  23, 26 — проверь, что `cxx_std_20` есть в `CMAKE_CXX_COMPILE_FEATURES` твоего компилятора), либо
  одиночная фича (`cxx_constexpr`, `cxx_variadic_templates`, `cxx_final`). Если фичи нет в
  `CMAKE_CXX_COMPILE_FEATURES` — ошибка configure, а не тихая деградация.
- **Где применимо:** `PUBLIC cxx_std_20` у `tw_core`; одиночные фичи у таргетов, которым нужен конкретный
  механизм (модуль 3).
- **Где неприменимо:** `set(CMAKE_CXX_STANDARD 20)` в кэше вместо требования таргета: переменная не
  участвует в графе и не доезжает до потребителя. И одиночные фичи как способ «включить C++20»: они не
  задают стандарт целиком.
- **Best practice:** стандарт задаёт таргет. `CMAKE_CXX_STANDARD` в пресете допустим как страховка
  тулчейна, но источником истины остаётся `cxx_std_20` в графе.
- **Справка middle:** мета-фича стандарта **не гарантирует наличие конкретной возможности**: в
  `cmake-compile-features(7)` сказано «does not guarantee the existence of any particular feature.
  Diagnosis of use of unsupported features will be delayed until compile time». То есть `cxx_std_20`
  пропустит configure на компиляторе без concepts, а ошибка прилетит из твоего кода. В графе побеждает
  максимум требований (§2.5, тонкость 4).
- **Проверка:** `cmake --help-command target_compile_features`,
  `cmake --help-variable CMAKE_CXX_COMPILE_FEATURES`, `cmake --help-manual cmake-compile-features`.

## 3. Фазы: кто и когда принимает решение

### 3.1 Механика

«CMake собрал проект» — это шесть разных операций, и у каждой свой исполнитель, свой вход и свой выход.
Ошибка всегда принадлежит одной фазе, и по её тексту фаза определяется однозначно.

| Фаза | Кто исполняет | Что читает | Что пишет | Как выглядит ошибка |
|---|---|---|---|---|
| **configure** | `cmake` | `CMakeLists.txt`, пресет, `CMakeCache.txt` | кэш, `CMakeFiles/` | `CMake Error at CMakeLists.txt:4 (project)` — с номером строки и именем команды |
| **generate** | `cmake` | свойства таргетов, собранные на configure | `build.ninja` / `*.vcxproj` / `CTestTestfile.cmake` | `CMake Error` без строки `CMakeLists.txt`, часто про генераторное выражение или про отсутствующий артефакт |
| **build** | `ninja` / `msbuild` / `make` | файлы генерации | `.obj`, `.lib`, `.exe` | текст компилятора или линкера с путём к `.cpp`/`.obj` |
| **install** | `cmake --install` | `cmake_install.cmake` | файлы в префиксе установки | `file INSTALL cannot find …` |
| **test** | `ctest` | `CTestTestfile.cmake` | `Testing/Temporary/LastTest.log` | `***Failed`, `No tests were found!!!` |
| **package** | `cpack` | `CPackConfig.cmake` | архив или установщик | ошибки `CPack` |

Два следствия, которые нужно запомнить до конца курса:

1. **`if()` исполняется на configure, генераторные выражения — на generate.** Поэтому `if()` физически не
   может знать конфигурацию multi-config генератора: в момент её исполнения конфигурации ещё нет, есть
   только список `CMAKE_CONFIGURATION_TYPES` (§4).
2. **`ctest` не знает про таргеты.** Он читает текстовый файл `CTestTestfile.cmake`, который появился на
   generate. Если файла нет или в нём нет записей — `ctest` не считает это ошибкой, а сообщает, что
   тестов не найдено (§6).

Замерено на этой машине при подготовке урока: генератор по умолчанию здесь — `NMake Makefiles`
(в `cmake --help` он помечен звёздочкой), а `cmake -S . -B <dir>` в репозитории падает на
`CMakeLists.txt:4 (project)` с текстом `Running 'nmake' '-?' failed`. То есть первая же ошибка этого
проекта сегодня — не про C++ и не про Qt, а про отсутствующий инструмент генератора.

Ещё две операции относятся к configure и обе меняют то, что увидят последующие команды.
`add_subdirectory(src)` немедленно обрабатывает `src/CMakeLists.txt` и возвращает управление в
родительский файл: это создание **области видимости**, а не таргета. `include(CTest)` загружает модуль,
который создаёт опцию `BUILD_TESTING` и вызывает `enable_testing()`. Порядок этих вызовов в корневом
файле — часть задания (шаг 6 §9.2), потому что от него зависит, какие переменные и политики уже действуют.

### 3.2 Почему сделано именно так

Потому что после generate сборкой занимается **чужая программа**, и CMake в этом больше не участвует.
Знание о проекте снимается один раз и записывается в файлы, понятные ninja или msbuild. Отсюда два
выигрыша:

1. **Скорость.** Пересборка одного `.cpp` не запускает CMake вообще: ninja читает свой граф и вызывает
   компилятор. Если бы флаги вычислялись при каждой сборке, цена правки была бы на порядок выше.
2. **Адресуемость ошибки.** Фаза видна в тексте, значит чинить надо в том файле, который за неё отвечает:
   ошибку компиляции — в `.cpp` или в требованиях таргета, ошибку generate — в свойствах и генераторных
   выражениях, «тестов нет» — в `enable_testing()`/`add_test`, а не в тестовом коде.

Цена разделения: значение, которого нет на configure, нельзя получить через `if()`. Это не ограничение
реализации, а прямое следствие того, что конфигурация выбирается позже — на build.

### 3.3 Что будет, если нарушить

| Нарушение | Симптом | Настоящая причина |
|---|---|---|
| `if(CMAKE_BUILD_TYPE STREQUAL "Debug")` вокруг флагов отладки | на Visual Studio и `Ninja Multi-Config` флагов нет, но ошибки тоже нет | на multi-config генераторе `CMAKE_BUILD_TYPE` пуст на configure; условие молча ложно |
| `add_test(...)` без `enable_testing()` | `ctest` печатает `No tests were found!!!` и возвращает **0** | записи тестов не попали в `CTestTestfile.cmake`: generate их не создаёт (замерено, §6) |
| `cmake_minimum_required()` после `project()` | предупреждение про `CMP0000`, политики применились поздно | политики влияют на поведение команд, включая сам `project()`; справка требует вызывать команду первой |
| ручная правка `CMakeCache.txt` «чтобы быстрее» | значение живёт до следующего configure, потом возвращается назад | кэш — выход configure, а не его вход; источник истины — пресет или `CMakeLists.txt` |
| ожидание, что `message()` покажет путь к `.exe` | печатается пустая строка или имя таргета | путь к артефакту известен только на generate: это `$<TARGET_FILE:tgt>` |

### 3.4 Мини-практика 3 (3 минуты, исполняется сегодня)

Эта практика не требует компилятора: она показывает, что фаза configure падает **до** всякого C++.
Создай в `$env:TEMP\cmkphase\` файл `CMakeLists.txt` из двух строк — `cmake_minimum_required(VERSION 4.3.2)`
и `project(probe LANGUAGES NONE)` — и выполни:

```powershell
cmake -S $env:TEMP\cmkphase -B $env:TEMP\cmkphase\b -G Ninja
cmake -S $env:TEMP\cmkphase -B $env:TEMP\cmkphase\b2 -G "Visual Studio 18 2026"
cmake --help-manual cmake-buildsystem
```

Замеренные результаты на этой машине (коды возврата — из `$LASTEXITCODE`):

- первая команда: `CMake was unable to find a build program corresponding to "Ninja".`
  `CMAKE_MAKE_PROGRAM is not set.` → код **1**;
- вторая: `Generator Visual Studio 18 2026 could not find any instance of Visual Studio.` → код **1**,
  причём ошибка указана **в строке 2 `CMakeLists.txt`, команда `project`**;
- третья печатает руководство по системе сборки: оно объясняет, почему свойства таргетов превращаются в
  файлы генератора.

Обрати внимание на разницу: `Ninja` и `Unix Makefiles` сообщают об отсутствии `CMAKE_MAKE_PROGRAM` ещё до
`project()`, а `NMake Makefiles` и Visual Studio падают внутри `project()`. Причина в том, что разным
генераторам нужны разные инструменты и проверяют они их в разные моменты. Практический вывод: текст
«ошибка в `project()`» не означает, что виноват `project()` — чаще виноват отсутствующий тулчейн (§7).

### 3.5 Паспорта конструкций раздела

**`cmake_minimum_required`** — команда, фаза configure, задаёт версию и политики.

```cmake
cmake_minimum_required(VERSION <min>[...<policy_max>] [FATAL_ERROR])
```

- **Зачем:** останавливает configure на слишком старом CMake и неявно вызывает `cmake_policy(VERSION …)`,
  то есть выбирает, какие политики считаются `NEW`.
- **Формы аргументов:** `<min>` и `<policy_max>` — версии вида `major.minor[.patch[.tweak]]`, троеточие
  между ними пишется буквально; `<policy_max>` (3.12+) задаёт верхнюю границу политик отдельно от минимума.
  `FATAL_ERROR` принимается и игнорируется начиная с CMake 2.6.
- **Где применима:** первая строка корневого `CMakeLists.txt` TrafficWatcher; в уроке 1.3 — тот же вызов
  в `cmake/Tw*.cmake` не нужен, политики наследуются от корня.
- **Где неприменима:** внутри `function()` — справка прямо называет это нежелательным: часть эффектов
  ограничивается областью видимости функции, а политики вызывающей области при этом меняются.
  И как способ «выбрать версию CMake»: команда не устанавливает инструмент, а только проверяет его.
- **Best practice:** минимум — ровно тот, на котором ты проверял сборку, и он записан в ADR-0001.
  Иначе на машине напарника configure упадёт без объяснения, а на твоей — нет.
- **Справка middle:** CMake **4.0 удалил** совместимость с версиями старше 3.5 (`VERSION 3.4` и ниже —
  ошибка), а совместимость со старше 3.10 объявлена устаревшей и даёт предупреждение с 3.31. Поэтому
  «поднимем минимум попозже» на CMake 4 — это не отложенное решение, а уже сломанная сборка чужого проекта.
- **Проверка:** `cmake --help-command cmake_minimum_required` (разделы Policy Version и Compatibility).

**`project`** — команда, фаза configure, объявляет проект и включает языки.

```cmake
project(<PROJECT-NAME> [<language-name>...])
project(<PROJECT-NAME>
        [VERSION <major>[.<minor>[.<patch>[.<tweak>]]]]
        [COMPAT_VERSION <major>[.<minor>[.<patch>[.<tweak>]]]]
        [SPDX_LICENSE <license-string>]
        [DESCRIPTION <description-string>]
        [HOMEPAGE_URL <url-string>]
        [LANGUAGES <language-name>...])
```

- **Зачем:** задаёт `PROJECT_NAME`, `PROJECT_SOURCE_DIR`, `PROJECT_BINARY_DIR` и включает компиляторы
  указанных языков; именно здесь происходит проверка тулчейна.
- **Формы аргументов:** короткая форма со списком языков; полная — с `VERSION`, `DESCRIPTION`,
  `HOMEPAGE_URL`, `LANGUAGES`. `COMPAT_VERSION` и `SPDX_LICENSE` — **новое в 4.3**; `COMPAT_VERSION`
  требует, чтобы `VERSION` тоже был задан. Без `LANGUAGES` по умолчанию включаются `C` и `CXX`.
- **Где применима:** корень TrafficWatcher — `project(TrafficWatcher VERSION 0.1.0 LANGUAGES CXX)`;
  `LANGUAGES NONE` в мини-практике 3, чтобы проверить configure без компилятора.
- **Где неприменима:** в дочернем `CMakeLists.txt` как способ «объявить подпроект» без необходимости:
  вызов создаёт свои `PROJECT_*`-переменные и сбивает пути, от которых считаются относительные include.
  И `LANGUAGES C CXX` «на всякий случай»: это проверка ещё одного компилятора, которого может не быть.
- **Best practice:** имя проекта — продуктовое (`TrafficWatcher`), а не имя таргета; версия живёт здесь и
  потом используется CPack (модуль 11). Иначе версия пакета и версия проекта разъезжаются.
- **Справка middle:** `PROJECT_IS_TOP_LEVEL` (3.21+) отличает корневой проект от подключённого через
  `add_subdirectory`/`FetchContent`; на нём строят «не включать тесты и установку, если мы не корень».
  `CMAKE_PROJECT_NAME` — имя **корневого** проекта, `PROJECT_NAME` — текущего.
- **Проверка:** `cmake --help-command project`, `cmake --help-variable PROJECT_IS_TOP_LEVEL`.

**`enable_testing` / `include(CTest)`** — команда и модуль, фаза configure, включают тестовый контейнер.

```cmake
enable_testing()
include(<file|module> [OPTIONAL] [RESULT_VARIABLE <var>] [NO_POLICY_SCOPE])   # для include(CTest)
```

- **Зачем:** разрешает generate записывать `CTestTestfile.cmake`; без неё `add_test` не создаёт ничего.
- **Формы аргументов:** аргументов нет. Вызывается в области видимости файла; справка запрещает вызов внутри
  `function()` и внутри `block()`.
- **Где применима:** корневой `CMakeLists.txt` TrafficWatcher (шаг 6 §9.2); `include(CTest)` вместо неё —
  когда нужен ещё и CDash (модуль 12).
- **Где неприменима:** только в `tests/CMakeLists.txt`: `ctest` ищет тестовый файл в **верхнем**
  build-каталоге, поэтому вызов в одном дочернем каталоге не даёт контейнера для всего проекта.
- **Best practice:** в корневом файле — `include(CTest)` и `if(BUILD_TESTING)` вокруг тестов, либо
  `enable_testing()` явно. Модуль `CTest` создаёт опцию `BUILD_TESTING` со значением `ON` по умолчанию и
  сам вызывает `enable_testing()`, если опция не выключена. Иначе тесты нельзя отключить одним ключом кэша.
- **Справка middle:** отсутствие тестового контейнера не является ошибкой: `ctest` вернёт **0** (§6,
  тонкость 6). Поэтому «зелёный CI» без `enable_testing()` — это зелёный ноль, а не зелёные тесты.
- **Проверка:** `cmake --help-command enable_testing`, `cmake --help-module CTest`.

**`add_subdirectory`** — команда, фаза configure, создаёт область видимости и подключает её граф.

```cmake
add_subdirectory(source_dir [binary_dir] [EXCLUDE_FROM_ALL] [SYSTEM])
```

- **Зачем:** немедленно обрабатывает `CMakeLists.txt` указанного каталога; таргеты, созданные там,
  становятся частью общего графа, а переменные и свойства директории остаются в своей области видимости.
- **Формы аргументов:** `source_dir` — относительный (от текущего каталога) или абсолютный путь;
  `binary_dir` — куда класть выход (по умолчанию повторяет `source_dir`); `EXCLUDE_FROM_ALL` исключает
  каталог из сборки по умолчанию; `SYSTEM` (3.25+) помечает его заголовки как системные.
- **Где применимо:** `add_subdirectory(src)` и `add_subdirectory(tests)` в корне TrafficWatcher (шаг 6);
  `add_subdirectory(third_party … EXCLUDE_FROM_ALL)` для чужого кода в модуле 10.
- **Где неприменимо:** как способ «подключить чужой проект целиком»: для внешнего проекта есть
  `FetchContent`/`find_package`, иначе его политики и переменные попадут в твою область видимости.
  И для подключения каталога **выше** текущего без явного `binary_dir`: CMake потребует его, потому что
  иначе выход окажется вне дерева сборки.
- **Best practice:** один каталог — один `CMakeLists.txt` со своими таргетами; список источников не
  поднимается в родителя через `PARENT_SCOPE`. Иначе родитель не может собрать ребёнка, не зная имён его
  файлов, а тесты начинают фильтровать источники регулярным выражением (находка старого проекта, §11).
- **Справка middle:** вызов обрабатывается **сразу**, до продолжения родительского файла. Поэтому
  `find_package` и политики должны быть объявлены выше него: то, что написано после, ребёнку не достанется.
- **Проверка:** `cmake --help-command add_subdirectory`, `cmake --help-property EXCLUDE_FROM_ALL`.

## 4. Конфигурации и генераторные выражения

### 4.1 Механика

Генераторы делятся на два класса, и от класса зависит, где живёт слово «Debug».

| | Single-config (`Ninja`, `Unix Makefiles`, `NMake Makefiles`) | Multi-config (`Visual Studio 17 2022`, `Ninja Multi-Config`, `Xcode`) |
|---|---|---|
| Конфигурация выбирается | на **configure**, через `CMAKE_BUILD_TYPE` | на **build**, через `cmake --build --config Debug` |
| `CMAKE_BUILD_TYPE` | `Debug` / `Release` / `RelWithDebInfo` / `MinSizeRel` | пустая строка |
| `CMAKE_CONFIGURATION_TYPES` | не используется | список доступных конфигураций |
| Один build-каталог | одна конфигурация | все конфигурации сразу |
| Флаги «только для Debug» | можно `if()`, но лучше генераторное выражение | **только** генераторное выражение |

Генераторное выражение — это запись `$<...>`, которая вычисляется на **generate**, отдельно для каждой
конфигурации, языка и платформы. Формы, сверенные сегодня в `cmake --help-manual cmake-generator-expressions`:

| Форма | Что даёт | Где применяется в курсе |
|---|---|---|
| `$<BUILD_INTERFACE:...>` | содержимое при использовании внутри этой сборки и при `export()`; иначе пусто | публичные include-пути `tw_core` (урок 1) |
| `$<INSTALL_INTERFACE:...>` | содержимое при `install(EXPORT)`; иначе пусто | относительные пути в устанавливаемом пакете (модуль 11) |
| `$<CONFIG:cfgs>` | `1`, если конфигурация входит в список через запятую; сравнение **без учёта регистра** | флаги и определения только для Debug |
| `$<BOOL:string>` | `0` для пустой строки, для `0`/`FALSE`/`OFF`/`N`/`NO`/`IGNORE`/`NOTFOUND` (без учёта регистра) и для строк с суффиксом `-NOTFOUND`; иначе `1` | превратить переменную кэша в условие |
| `$<IF:condition,true_string,false_string>` | одна из двух строк; значение условия, отличное от `0`/`1`, — **ошибка** | выбор флага по условию |
| `$<PLATFORM_ID>` / `$<PLATFORM_ID:ids>` | id платформы (`Windows`, `Linux`, `Darwin`) / `1` при совпадении | платформенный слой (модуль 7) |
| `$<CXX_COMPILER_ID>` / `$<CXX_COMPILER_ID:ids>` | id компилятора (`MSVC`, `GNU`, `Clang`) / `1` при совпадении | политика предупреждений, ADR-0003 |
| `$<COMPILE_LANGUAGE:languages>` | `1`, если язык файла входит в список | флаги только для C++, не для C |
| `$<TARGET_FILE:tgt>` | полный путь к артефакту таргета | пути в тестах и deploy (модуль 11) |
| `$<JOIN:list,glue>` / `$<FILTER:list,INCLUDE\|EXCLUDE,regex>` | склейка списка / отбор элементов | списки источников и флагов в `cmake/Tw*` (урок 1.3) |

Важная деталь: `$<TARGET_FILE:tgt>` **не добавляет** зависимость от `tgt`, если выражение используется не
в `add_custom_command()`/`add_custom_target()`. Это сказано в справке прямо, и это источник ошибок
«файл не найден» в тестах, которые запускаются раньше сборки.

### 4.2 Почему сделано именно так

Потому что один и тот же граф должен обслуживать все конфигурации, не размножаясь. Альтернатива —
отдельный таргет `tw_core_debug` и `tw_core_release` — удваивает число вершин и делает распространение
требований нечитаемым. Генераторное выражение переносит выбор в тот момент, когда выбор уже известен:
на generate, для конкретной конфигурации.

Второй выигрыш — переносимость. `$<CXX_COMPILER_ID:MSVC>` вместо `if(MSVC)` работает и тогда, когда проект
подключён как подпроект и переменные окружения отличаются: выражение вычисляется в контексте таргета, а не
в контексте того, кто первым вызвал `project()`.

Цена: выражение — это строка, а не код. Опечатка внутри `$<...>` не проверяется на configure и всплывает
на generate, иногда с текстом, который не указывает на строку `CMakeLists.txt`. Поэтому сложные выражения
собирают из простых и проверяют по одному.

### 4.3 Что будет, если нарушить

| Нарушение | Симптом | Механизм |
|---|---|---|
| `if(CMAKE_BUILD_TYPE STREQUAL "Debug")` на multi-config | отладочных флагов нет, сборка «прошла» | переменная пуста на configure (§3.1) |
| `$<CONFIG:debug>` вперемешку с `Debug` в других местах | работает, но читается как ошибка | сравнение без учёта регистра; единообразие нужно для ревью, а не для CMake |
| `$<IF:$<BOOL:${OPT}>,/W4,/W0>` без кавычек | ошибка generate про список или про пустой аргумент | результат выражения — строка; в CMake-списке она должна быть одним аргументом |
| абсолютный путь в `INTERFACE_INCLUDE_DIRECTORIES` без обёртки | пакет ставится, у потребителя не собирается | путь твоей машины уехал в `install(EXPORT)`-файл |
| `$<TARGET_FILE:tw_app>` в `add_test` до появления таргета | ошибка generate «TARGET_FILE … not found» | выражение требует существующий таргет на момент generate |

### 4.4 Мини-практика 4 (3 минуты, исполняется сегодня)

Генераторные выражения вычисляются на generate, а генератора на машине нет (§7). Поэтому сегодня
проверяется **форма**, а не результат — и это тоже проверка, потому что вымышленный keyword внутри `$<...>`
опаснее вымышленного имени команды: его некому проверить до generate.

```powershell
cmake --help-manual cmake-generator-expressions | Select-String -Pattern 'genex:: \$<CONFIG' -Context 0,5
cmake --help-manual cmake-generator-expressions | Select-String -Pattern 'genex:: \$<IF' -Context 0,5
cmake --help-command target_compile_options
```

Ожидаемо: первая команда печатает «`1` if config is any one of the entries in comma-separated list
`cfgs` … case-insensitive comparison»; вторая — «Any other value for `condition` results in an error»;
третья — сигнатуру с обязательным keyword и необязательным `[BEFORE]`.

После установки тулчейна повтори эту практику на сборке: добавь
`target_compile_definitions(tw_core PRIVATE $<$<CONFIG:Debug>:TW_DEBUG>)` и убедись, что определение
попадает только в отладочную конфигурацию (`cmake --build --preset <имя> --config Debug -- -v`).

### 4.5 Паспорта конструкций раздела

**Генераторное выражение `$<...>`** — синтаксис (не команда), вычисляется на generate.

```cmake
$<condition:true_string>                 # условная подстановка
$<CONFIG:cfgs>                           # 1/0 по конфигурации
$<IF:condition,true_string,false_string> # выбор из двух строк
$<BUILD_INTERFACE:...>  $<INSTALL_INTERFACE:...>
$<TARGET_FILE:tgt>  $<PLATFORM_ID:ids>  $<CXX_COMPILER_ID:ids>
```

- **Зачем:** позволяет одному свойству таргета иметь разные значения для разных конфигураций, языков,
  платформ и способов экспорта.
- **Формы аргументов:** три семейства — informational (`$<CONFIG>`, `$<PLATFORM_ID>`, `$<TARGET_FILE:tgt>`),
  logical (`$<BOOL:…>`, `$<AND:…>`, `$<IF:…>`, `$<CONFIG:cfgs>`), output (`$<JOIN:…>`, `$<FILTER:…>`,
  `$<BUILD_INTERFACE:…>`). Выражения вкладываются; список внутри — через запятую, а не через `;`.
- **Где применимо:** include-пути `tw_core`; флаги предупреждений по компилятору (ADR-0003); определения
  только для Debug; пути к артефактам в deploy (модуль 11).
- **Где неприменимо:** в `if()`, `message()`, `set()` на configure — там выражение остаётся строкой и
  молча не вычисляется. И в `add_test(COMMAND …)` как способ «получить путь до сборки»: зависимость
  `$<TARGET_FILE:>` не создаёт.
- **Best practice:** одно выражение — одна мысль; сложные условия собирай из `$<BOOL:>` и `$<AND:>`, а не
  из трёхэтажной вложенности. Иначе ошибка generate не укажет строку, и отладка превратится в перебор.
- **Справка middle:** `$<CONFIG:>` сравнивает без учёта регистра и учитывает `MAP_IMPORTED_CONFIG_<CONFIG>`;
  `$<IF:>` требует строго `0` или `1` — любое другое значение есть ошибка, а не «ложь».
- **Проверка:** `cmake --help-manual cmake-generator-expressions` (список форм),
  `cmake --help-manual cmake-buildsystem`.

**`target_compile_definitions`** — команда, определения препроцессора мне и/или потребителю.

```cmake
target_compile_definitions(<target>
  {INTERFACE|PUBLIC|PRIVATE} <definition>...
  [{INTERFACE|PUBLIC|PRIVATE} <definition>...]...)
```

- **Зачем:** наполняет `COMPILE_DEFINITIONS` и/или `INTERFACE_COMPILE_DEFINITIONS`, то есть `-D`/`/D` на
  строке компиляции.
- **Формы аргументов:** keyword обязателен и повторяется; ведущий `-D` у элемента **снимается**, пустые
  элементы игнорируются; значение задаётся как `FOO=1`. Допустимы генераторные выражения. Повторные вызовы
  дописывают элементы в порядке вызовов.
- **Где применимо:** `TW_DEBUG` только для Debug у `tw_core`; `TW_VERSION="0.1.0"` из `PROJECT_VERSION`;
  в модуле 13 — флаг версионированного формата конфигурации.
- **Где неприменимо:** как способ передать путь к заголовкам или библиотеку: для этого есть
  `target_include_directories` и `target_link_libraries`. Определение `QT_CORE_LIB` вручную — тоже нет:
  его ставит сам Qt-таргет, и ручная копия разъедется с реальной сборкой Qt.
- **Best practice:** определения, влияющие на ABI (например, `NDEBUG`), — только `PUBLIC` и только осознанно.
  Иначе библиотека и потребитель соберутся с разным ABI, и ошибка прилетит на линковке или в рантайме.
- **Справка middle:** `INTERFACE`-элементы на `IMPORTED`-таргетах разрешены с 3.11; `<target>` не может быть
  `ALIAS`. Значение с пробелами требует кавычек, иначе CMake разберёт его как список.
- **Проверка:** `cmake --help-command target_compile_definitions`.

**`target_compile_options`** — команда, флаги компилятора мне и/или потребителю.

```cmake
target_compile_options(<target> [BEFORE]
  {INTERFACE|PUBLIC|PRIVATE} <item>...
  [{INTERFACE|PUBLIC|PRIVATE} <item>...]...)
```

- **Зачем:** наполняет `COMPILE_OPTIONS` / `INTERFACE_COMPILE_OPTIONS` — произвольные флаги компиляции.
- **Формы аргументов:** keyword обязателен; `[BEFORE]` вставляет флаги в начало списка вместо конца;
  допустимы генераторные выражения, в том числе `$<COMPILE_LANGUAGE:>` и `$<CXX_COMPILER_ID:>`.
- **Где применимо:** политика предупреждений ADR-0003 (`/W4 /WX` для MSVC, `-Wall -Wextra -Werror` для
  GNU/Clang) на `PRIVATE` таргетов проекта; флаги sanitizers отдельным пресетом (модуль 10).
- **Где неприменимо:** для стандарта языка — это `target_compile_features`, иначе флаг `-std=` не
  участвует в графе и потребитель его не получит. И для флагов **линкера**: они идут в
  `target_link_options`, а не сюда.
- **Best practice:** предупреждения — `PRIVATE` и на таргетах проекта, не на `3rdparty`. Иначе чужой код
  не соберётся с `/WX`, и ты будешь чинить не свои ошибки. Флаги, влияющие на ABI, — `PUBLIC` и в ADR.
- **Справка middle:** `INTERFACE_COMPILE_OPTIONS` у экспортируемой библиотеки уезжает к потребителю:
  `/WX` в пакете означает, что чужой проект не соберётся с твоим уровнем строгости. Проверяется чтением
  `install(EXPORT)`-файла после установки (модуль 11).
- **Проверка:** `cmake --help-command target_compile_options`,
  `cmake --help-property COMPILE_OPTIONS`.

## 5. Пресеты: знание о тулчейне живёт в файле

### 5.1 Механика

Пресет — именованный набор параметров **одной операции**. Операций пять, и у каждой свой массив в JSON:

| Массив | Кто читает | Команда | Версия схемы, с которой доступен |
|---|---|---|---|
| `configurePresets` | `cmake` | `cmake --preset <имя>` | 1 (CMake 3.19) |
| `buildPresets` | `cmake` | `cmake --build --preset <имя>` | 2 (3.20) |
| `testPresets` | `ctest` | `ctest --preset <имя>` | 2 (3.20) |
| `packagePresets` | `cpack` | `cpack --preset <имя>` | 6 (3.25) |
| `workflowPresets` | `cmake` | `cmake --workflow --preset <имя>` | 6 (3.25) |

Файлов два, формат у них одинаковый: `CMakePresets.json` — проектное знание, его коммитят;
`CMakeUserPresets.json` — личное знание (путь к Qt на твоей машине), его **не коммитят**. Справка
формулирует это прямо: «`CMakePresets.json` may be checked into a version control system, and
`CMakeUserPresets.json` should NOT be checked in». Если присутствуют оба, пользовательский файл неявно
включает проектный — во всех версиях схемы. В этом репозитории правило уже соблюдено:
`.gitignore:33` содержит `CMakeUserPresets.json` (замерено `git check-ignore -v`).

Версия схемы — это не версия CMake. Соответствие (замерено в `cmake --help-manual cmake-presets`,
раздел Versions): 1 → 3.19, 2 → 3.20, 3 → 3.21, 4 → 3.23, 5 → 3.24, 6 → 3.25, 7 → 3.27, 8 → 3.28,
9 → 3.30, 10 → 3.31, 11 → 4.3. Версия объявляется в поле `version` и ограничивает, какие ключи тебе
доступны: например, `graphviz` в configure-пресете появился только в схеме 10, а `$comment` — тоже в 10.

Наследование — основной механизм матрицы (урок 1.2). Правила из справки:

- пресет наследует **все** поля родителей, кроме `name`, `hidden`, `inherits`, `description`, `displayName`;
- при конфликте значений выигрывает **более ранний** пресет в массиве `inherits`;
- наследовать можно только из того же файла или из включённых через `include` (поле `include`, схема 4+);
- пресеты из `CMakePresets.json` **не могут** наследовать пресеты из `CMakeUserPresets.json`;
- `hidden: true` — пресет нельзя использовать в `--preset`, он не показывается в списке и не обязан иметь
  корректные `generator`/`binaryDir`; это база для наследования;
- имена уникальны внутри своего вида на объединение двух файлов, но configure-пресет и test-пресет могут
  называться одинаково.

Макросы подставляются в строковые поля (список сверен сегодня): `${sourceDir}`, `${sourceParentDir}`,
`${sourceDirName}`, `${presetName}`, `${generator}`, `${hostSystemName}` (схема 3+), `${fileDir}` (4+),
`${dollar}`, `${pathListSep}` (5+), `$env{NAME}`, `$penv{NAME}`, `$vendor{…}`.

### 5.2 Почему сделано именно так

Потому что знание «каким генератором, с каким тулчейном, в какой каталог, с какими ключами кэша» иначе
размножается по трём местам: скрипт сборки, настройки IDE, CI-джоб. Три копии расходятся на второй неделе,
и «локально зелёное» перестаёт что-либо значить. Пресет делает это знание **одним файлом**, который читают
все три потребителя.

Второй выигрыш — матрица без копипасты. `ОС × компилятор × конфигурация` в уроке 1.2 выражается
наследованием: базовый скрытый пресет несёт общее, листовые добавляют по одному отличию. Цена нарушения —
не «некрасиво», а N файлов, в которых надо синхронно поменять один флаг.

Третий выигрыш — личное не ломает общее. Путь к Qt у тебя и у напарника разный; он живёт в
`CMakeUserPresets.json` или в `toolchainFile`, а не в коммите. Иначе каждый разработчик коммитит свой путь,
и история файла превращается в спор о машинах.

### 5.3 Что будет, если нарушить

| Нарушение | Симптом | Механизм |
|---|---|---|
| путь к Qt зашит в `CMakePresets.json` | у напарника configure падает, у тебя работает | проектный файл общий, а путь личный |
| `CMakeUserPresets.json` закоммичен | конфликт слияния на каждой машине, чужой путь в общей сборке | файл по назначению локальный; справка требует `.gitignore` |
| `version: 3`, а внутри `graphviz` | `File version must be 10 or higher for graphviz preset support`, код **1** (замерено) | ключ доступен с схемы 10 |
| листовой пресет без `binaryDir` и без родителя, который его задаёт | ошибка «binaryDir must be inherited» | с схемы 3 поле можно опустить, только если оно наследуется (или пресет `hidden`) |
| одинаковые имена двух configure-пресетов в двух файлах | ошибка чтения пресетов | уникальность внутри вида на объединение файлов |
| опечатка в имени пресета в CI | `No such preset …`, код **1** (замерено) | имя — машинный идентификатор, а не подпись |

### 5.4 Мини-практика 5 (4 минуты, исполняется сегодня)

Список пресетов читается без компилятора, поэтому эта практика проверяется на машине прямо сейчас.
Создай в `$env:TEMP\presetprobe\` файл `CMakePresets.json` (это упражнение, не код проекта):

```json
{
  "version": 6,
  "configurePresets": [
    { "name": "base", "hidden": true, "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "cacheVariables": { "CMAKE_BUILD_TYPE": "Debug" } },
    { "name": "win-msvc", "inherits": "base", "displayName": "Windows MSVC Debug" }
  ],
  "buildPresets": [ { "name": "win-msvc-debug", "configurePreset": "win-msvc", "jobs": 4 } ],
  "testPresets": [ { "name": "win-msvc-debug", "configurePreset": "win-msvc",
    "output": { "outputOnFailure": true }, "execution": { "stopOnFailure": true } } ],
  "workflowPresets": [ { "name": "ci", "steps": [
    { "type": "configure", "name": "win-msvc" },
    { "type": "build", "name": "win-msvc-debug" },
    { "type": "test", "name": "win-msvc-debug" } ] } ]
}
```

Выполни из этого каталога и сравни с замеренным выводом:

```powershell
cmake --list-presets          # Available configure presets: "win-msvc" - Windows MSVC Debug
cmake --list-presets=all      # четыре списка: configure, build, test, workflow
ctest --list-presets          # Available test presets: "win-msvc-debug"
cmake --workflow --list-presets   # Available workflow presets: "ci"
cmake --preset nosuch         # CMake Error: No such preset …: "nosuch" + список доступных, код 1
```

Обрати внимание: скрытый `base` в списке **не показан**, но `win-msvc` получил от него генератор,
`binaryDir` и `CMAKE_BUILD_TYPE`. Это и есть механизм матрицы в миниатюре.

Раскрытие `${presetName}` проверяется без компилятора — даже на упавшем configure. Замерено сегодня:

```powershell
cmake --preset win-msvc                      # падает на отсутствующем Ninja, код 1
Get-ChildItem build -Directory               # win-msvc
Select-String -Path build/win-msvc/CMakeCache.txt -Pattern 'CMAKE_CACHEFILE_DIR','CMAKE_BUILD_TYPE'
```

Каталог создан и назван именем **использованного** пресета, хотя строка `binaryDir` написана в базе.
В кэше: `CMAKE_CACHEFILE_DIR:INTERNAL=…/build/win-msvc` и `CMAKE_BUILD_TYPE:UNINITIALIZED=Debug`.
То есть неудачный configure всё равно оставляет доказательство раскрытия макросов — этим способом
матрицу урока 1.2 можно проверить до установки тулчейна.

В репозитории TrafficWatcher сегодня обе команды списка падают одинаково:
`Could not read presets from C:/Projects/TrafficWatcher: File not found: …/CMakePresets.json`,
код **1** (замерено для `cmake` и для `ctest`). Это ожидаемое состояние до шага 7 задания, а не поломка
инструмента.

### 5.5 Паспорта конструкций раздела

**`configurePresets[i]`** — key пресета (JSON-объект), читается на configure.

```json
{ "name": "win-msvc", "hidden": false, "inherits": ["base"],
  "generator": "Ninja", "binaryDir": "${sourceDir}/build/${presetName}",
  "toolchainFile": "…", "installDir": "…", "condition": { "…": "…" },
  "cacheVariables": { "CMAKE_BUILD_TYPE": "Debug" },
  "environment": { "PATH": "…" },
  "warnings": { "dev": true, "deprecated": true, "uninitialized": true },
  "errors": { "dev": true, "deprecated": true },
  "graphviz": "build/deps.dot" }
```

- **Зачем:** задаёт генератор, build-каталог, ключи кэша и окружение одной именованной конфигурации.
- **Формы аргументов:** обязательны `name`; `generator` и `binaryDir` обязательны, если не наследуются
  (кроме `hidden`). `cacheVariables` — карта: значение строкой, булевым, `null` (сброс унаследованного)
  или объектом `{type, value}`. `warnings`/`errors` — объекты с полями `dev`, `deprecated`
  (+ `uninitialized`, `unusedCli`, `systemVars` только у `warnings`); `errors.dev: true` запрещает
  `warnings.dev: false`. `graphviz` — строка пути, схема **10+**.
- **Где применимо:** `win-msvc` и `win-msvc-release` в уроке 1; матрица `ОС × компилятор` в 1.2;
  ASan-пресет в модуле 10; тот же пресет читает CI в модуле 12.
- **Где неприменимо:** личные пути (Qt, компилятор) — им место в `CMakeUserPresets.json` или
  `toolchainFile`. И `cmakeExecutable`: справка помечает поле как зарезервированное для IDE, сам CMake
  его не использует.
- **Best practice:** общий знаменатель — в скрытый базовый пресет, отличия — в листовые. Иначе матрица
  1.2 превратится в копипасту, и флаг, поправленный в одном листе, разъедется с остальными.
- **Справка middle:** макросы вычисляются в контексте **используемого** пресета, даже если поле
  унаследовано: `${presetName}` из базы даст имя листа. Поэтому `binaryDir` базы с `${presetName}` —
  это способ получить отдельный каталог на каждый лист без дублирования поля.
- **Проверка:** `cmake --help-manual cmake-presets` (раздел Configure Preset), `cmake --list-presets`.

**`buildPresets[i]`** — key пресета, читается на build.

```json
{ "name": "win-msvc-debug", "configurePreset": "win-msvc",
  "inheritConfigureEnvironment": true, "jobs": 4, "targets": ["tw_app"],
  "configuration": "Debug", "cleanFirst": false, "verbose": true,
  "nativeToolOptions": ["-k", "0"] }
```

- **Зачем:** связывает сборку с configure-пресетом и задаёт, что и как собирает нативный инструмент.
- **Формы аргументов:** обязателен `name`; `configurePreset` обязателен, если не наследуется.
  `configuration` — для multi-config генераторов; `targets` — строка или массив строк;
  `jobs` — число; `cleanFirst`, `verbose` — булевы; `nativeToolOptions` — массив аргументов, которые
  уйдут нативному инструменту после `--`.
- **Где применимо:** `win-msvc-debug` / `win-msvc-release` в уроке 1; сборка только тестового таргета
  перед быстрым прогоном (урок 8); `--clean-first` в CI-джобе «чистая сборка» (модуль 1).
- **Где неприменимо:** `configuration` на single-config генераторе: конфигурация уже выбрана на configure
  через `CMAKE_BUILD_TYPE`, и ключ здесь ничего не меняет. И `CMAKE_BUILD_TYPE` внутри build-пресета —
  это поле configure-пресета.
- **Best practice:** имя build-пресета несёт конфигурацию (`…-debug`), а имя configure-пресета — платформу
  и тулчейн. Иначе по имени команды не видно, что именно собирается, и в CI легко прогнать не ту конфигурацию.
- **Справка middle:** `jobs: 0` эквивалентен `--parallel` без числа; тот же эффект даёт пустая строка в
  `CMAKE_BUILD_PARALLEL_LEVEL` через поле `environment`. С CMake **4.3** отрицательные значения `jobs`
  не принимаются независимо от версии схемы. `inheritConfigureEnvironment` по умолчанию true — окружение
  configure-пресета доезжает до сборки, поэтому путь к компилятору достаточно объявить один раз.
- **Проверка:** `cmake --help-manual cmake-presets` (раздел Build Preset), `cmake --build` без аргументов
  (печатает usage и возвращает 1). Вызова `cmake --build --help` **не существует**: замерено, что он
  отвечает `Error: …/--help is not a directory`.

**`testPresets[i]`** — key пресета, читается на test.

```json
{ "name": "win-msvc-debug", "configurePreset": "win-msvc",
  "configuration": "Debug", "inheritConfigureEnvironment": true,
  "output": { "outputOnFailure": true, "verbosity": "default", "quiet": false,
              "shortProgress": false, "debug": false, "outputLogFile": "…" },
  "filter": { "include": { "name": "…", "label": "smoke", "useUnion": false },
              "exclude": { "name": "…", "label": "slow" } },
  "execution": { "stopOnFailure": true, "enableFailover": false } }
```

- **Зачем:** задаёт, какие тесты и с какой подробностью запускает `ctest` в каталоге configure-пресета.
- **Формы аргументов:** `output` — булевы и строковые поля, каждое эквивалентно ключу `ctest`
  (`outputOnFailure` → `--output-on-failure`, `verbosity` → `--verbose`/`--extra-verbose`);
  `filter.include`/`filter.exclude` — regex по имени и по лейблу, плюс `index` и `fixtures`;
  `execution` — **только** `stopOnFailure` и `enableFailover`.
- **Где применимо:** быстрый прогон `smoke`-лейбла в уроке 1; разделение unit/component/integration по
  лейблам в уроке 8; долгие прогоны с отдельным пресетом в уроке 15.
- **Где неприменимо:** защита от пустого прогона. Ключа `noTests` в `execution` **нет** (сверено со
  списком полей), и неизвестный ключ не обязательно приведёт к ошибке: замерено, что
  `"execution": {"noTests": "error"}` принимается молча и игнорируется. Флаг `--no-tests=error`
  передаётся в командной строке (§6, тонкость 6).
- **Best practice:** `outputOnFailure: true` в проектном пресете всегда. Иначе CI покажет «Failed» без
  текста assertions, и разбор начнётся с воспроизведения на своей машине.
- **Справка middle:** `ctest --preset` берёт build-каталог из configure-пресета; если каталога ещё нет,
  прогон не падает, а печатает `No tests were found!!!` и возвращает **0** (замерено). Список полей
  раздела Test Preset в справке 4.3.2 не содержит `jobs`, хотя раздел Versions упоминает его для схемы 11:
  источник истины — список полей и JSON-схема, а не пересказ.
- **Проверка:** `cmake --help-manual cmake-presets` (раздел Test Preset), `ctest --help`,
  `ctest --list-presets`.

## 6. Тестовый контейнер: что именно запускает `ctest`

### 6.1 Механика

Тест в CMake — это **запись в текстовом файле**, а не объект в графе. Цепочка такая:

1. `enable_testing()` (или `include(CTest)`) на configure разрешает создание тестового контейнера.
2. `add_test(NAME … COMMAND …)` на configure описывает тест; `set_tests_properties` навешивает свойства.
3. На generate эти записи превращаются в `CTestTestfile.cmake` в build-каталоге (и в дочерних каталогах,
   если тесты объявлены там).
4. `ctest` читает `CTestTestfile.cmake`, запускает команды как **обычные процессы** и считает код возврата:
   `0` — Passed, ненулевой — Failed. Про таргеты, компилятор и Qt он не знает ничего.
5. Лог прогона пишется в `Testing/Temporary/LastTest.log` внутри build-каталога.

Отсюда два факта, которые проверяются руками (§6.4): файл можно написать самому, и `ctest` его выполнит;
и отсутствие файла не является ошибкой — `ctest` сообщает, что тестов не найдено, и возвращает **0**.

Свойства теста — отдельный слой знаний. `LABELS` (3.10+) — список текстовых меток, по которым `ctest -L`
и `ctest -LE` отбирают тесты; `TIMEOUT` — секунды, после которых процесс убивается; `WILL_FAIL` — инверсия
критерия (ненулевой код считается успехом). Всё это читается в `cmake --help-property <имя>`.

### 6.2 Почему сделано именно так

Потому что тестовый контур должен переживать сборку. Если бы `ctest` зависел от графа таргетов, прогон
требовал бы работающего компилятора и полного configure — а CI нужно уметь запускать тесты на уже
собранном артефакте, в том числе на другой машине и в другом джобе. Текстовый файл — это контракт между
generate и test, и он переносим.

Второй выигрыш — лейблы как единица бюджета. В уроке 8 виды тестов (unit/component/integration) получают
разные бюджеты времени, а в уроке 15 долгие прогоны уезжают на отдельного воркера. Разделение делается
отбором по лейблу, а не переписыванием `CMakeLists.txt`: `ctest -L unit` против `ctest -L integration`.

Цена: `ctest` не проверяет, что тест вообще существует и что он что-то утверждает. Пустой отбор для него
равносильн «всё хорошо». Это и есть тонкость 6.

### 6.3 Что будет, если нарушить

| Нарушение | Симптом | Механизм |
|---|---|---|
| `add_test` без `enable_testing()` | `ctest`: `No tests were found!!!`, код **0** | generate не создал записи тестов |
| `enable_testing()` только в `tests/CMakeLists.txt` | контейнера нет в верхнем build-каталоге | `ctest` ищет тестовый файл наверху (справка `enable_testing`) |
| тест возвращает ненулевой код «по дизайну» | `***Failed`, хотя проверка прошла | критерий — код возврата; нужен `WILL_FAIL` или обёртка |
| тест без `TIMEOUT` зависает | прогон висит до таймаута CI-джоба | `TIMEOUT` не задан, `ctest` ждёт процесс |
| опечатка в `-L smoke` | `No tests were found!!!`, код **0** | отбор пуст, а пустой отбор не ошибка (тонкость 6) |
| `set_tests_properties` для теста из другого каталога | ошибка configure «test not found» | свойства ставятся в каталоге создания теста; для другой области видимости есть `DIRECTORY` (3.28+) |

### 6.4 Мини-практика 6 (5 минут, исполняется сегодня целиком)

Компилятор не нужен: `ctest` работает с текстовым файлом. Создай каталог `$env:TEMP\ctestprobe\` и файл
`CTestTestfile.cmake` в нём — от руки, без CMake-проекта (это упражнение, не код проекта):

```cmake
add_test(probe_true  "C:/Program Files/CMake/bin/cmake.exe" -E true)
add_test(probe_false "C:/Program Files/CMake/bin/cmake.exe" -E false)
set_tests_properties(probe_true PROPERTIES LABELS "smoke")
```

Путь к `cmake.exe` подставь свой: `(Get-Command cmake).Source`. Дальше — замеренные сегодня результаты:

```powershell
ctest --test-dir $env:TEMP\ctestprobe -N              # Total Tests: 2, код 0
ctest --test-dir $env:TEMP\ctestprobe --output-on-failure
#   1/2 probe_true … Passed; 2/2 probe_false … ***Failed
#   50% tests passed, 1 tests failed out of 2; код 8
ctest --test-dir $env:TEMP\ctestprobe -L smoke        # 100% tests passed … out of 1, код 0
ctest --test-dir $env:TEMP\ctestprobe -R nosuchtest   # No tests were found!!!, код 0
ctest --test-dir $env:TEMP\ctestprobe -R nosuchtest --no-tests=error   # то же сообщение, код 8
ctest --test-dir $env:TEMP\ctestempty -N              # каталог без файла: Total Tests: 0, код 0
```

Что здесь увидено своими руками: критерий успеха — код возврата процесса; лейбл работает как отбор;
**пустой отбор зелёный**; `--no-tests=error` превращает его в красный. Лог `LastTest.log` появится в
`$env:TEMP\ctestprobe\Testing\Temporary\` — открой его и найди вывод `probe_false`.

### 6.5 Тонкость и паспорта раздела

**Тонкость 6.** Пустой прогон тестов — зелёный прогон. Замерено сегодня на CTest 4.3.2: каталог без
`CTestTestfile.cmake`, каталог с файлом без записей и отбор `-R`, который ничего не нашёл, — во всех трёх
случаях `ctest` печатает `No tests were found!!!` (или `Total Tests: 0` для `-N`) и возвращает **0**.
С `--no-tests=error` те же случаи возвращают **8**; `--no-tests=ignore` возвращает **0**. Следствие:
CI-джоб «собрал и прогнал тесты» может быть зелёным, не выполнив ни одного теста, — например, после
опечатки в имени лейбла или если `enable_testing()` потерялся при рефакторинге. Защита — флаг
`--no-tests=error` в командной строке прогона; в test-пресете соответствующего ключа нет (§5.5).
Проверка: `ctest --help` (строка `--no-tests=<[error|ignore]>`) и команды из §6.4.

#### Паспорт конструкций раздела

**`add_test`** — команда, фаза configure, создаёт запись теста.

```cmake
add_test(NAME <name> COMMAND <command> [<arg>...]
         [CONFIGURATIONS <config>...]
         [WORKING_DIRECTORY <dir>]
         [COMMAND_EXPAND_LISTS])
```

- **Зачем:** описывает тест, который `ctest` запустит как отдельный процесс; запись попадает в
  `CTestTestfile.cmake` на generate.
- **Формы аргументов:** современная форма `NAME … COMMAND …`; `<command>` — имя исполняемого **таргета**
  (CMake сам подставит путь к артефакту) или внешняя программа с аргументами. `CONFIGURATIONS` ограничивает
  тест списком конфигураций, `WORKING_DIRECTORY` задаёт каталог запуска, `COMMAND_EXPAND_LISTS` разворачивает
  списки в аргументах. Есть и старая форма `add_test(<name> <command> …)` — без поддержки генераторных
  выражений в свойствах.
- **Где применимо:** `tw_core_smoke` на шаге 8 задания; QTest-исполняемые файлы в уроке 8; headless-прогон
  симуляции как тест в модуле 14.
- **Где неприменимо:** как способ «запустить сборку перед тестом»: `add_test` не создаёт зависимостей
  сборки. И как место для логики проверки: команда — это процесс, а не CMake-код; `if()` внутри теста
  не исполняется.
- **Best practice:** имя теста — с namespace и поведению, а не по номеру (`core.mode.label_solid`), и
  `COMMAND` — имя таргета, а не путь к `.exe`. Иначе тест переживёт перенос артефакта и не сломается при
  смене конфигурации, а отбор по regex останется осмысленным.
- **Справка middle:** тесты создаются только если вызван `enable_testing()`; свойства тестов, созданных
  формой `NAME`, поддерживают генераторные выражения, и ставить их можно в каталоге создания теста.
  Имя теста может содержать произвольные символы (политика `CMP0110`).
- **Проверка:** `cmake --help-command add_test`, `cmake --help-command enable_testing`.

**`set_tests_properties`** — команда, фаза configure, свойства уже созданных тестов.

```cmake
set_tests_properties(<tests>...
                     [DIRECTORY <dir>]
                     PROPERTIES <prop1> <value1>
                     [<prop2> <value2>]...)
```

- **Зачем:** навешивает на тесты метки, таймауты, окружение и критерии успеха — то, по чему `ctest`
  отбирает и оценивает прогоны.
- **Формы аргументов:** список имён тестов, затем обязательное `PROPERTIES` и пары имя/значение.
  `DIRECTORY <dir>` (3.28+) позволяет ставить свойства в области видимости другого каталога.
  Значения допускают генераторные выражения для тестов, созданных формой `add_test(NAME)`.
- **Где применимо:** `LABELS "unit;smoke"` и `TIMEOUT 10` у `tw_core_smoke`; `WILL_FAIL` у негативных
  проверок парсера в модуле 13; `ENVIRONMENT` для тестов, которым нужен путь к данным.
- **Где неприменимо:** для несуществующего теста — справка прямо говорит, что CMake сообщит об ошибке.
  И для свойств **таргета**: `LABELS` есть и у таргета, но это другой объект; путаница даёт молча
  не работающий отбор.
- **Best practice:** лейблы — из таксономии урока 8 (`unit`, `component`, `integration`, `slow`), а не
  произвольные слова. Иначе отбор в CI и бюджеты времени нельзя выразить одним regex.
- **Справка middle:** `TIMEOUT 0` означает «без таймаута», а не «мгновенно»; `WILL_FAIL` инвертирует
  критерий, но превышение `TIMEOUT` и системные падения (сегфолт, abort) остаются провалом.
- **Проверка:** `cmake --help-command set_tests_properties`, `cmake --help-property LABELS`,
  `cmake --help-property TIMEOUT`, `cmake --help-property WILL_FAIL`.

| тест падает, хотя проверка прошла | процесс вернул ненулевой код, а критерий `ctest` — именно код | `WILL_FAIL` либо исправить код возврата (§6.1) | замерено на `probe_false` |

Правило работы с таблицей: сначала определи фазу по тексту (§3.1), потом ищи строку. Чинить ошибку
компиляции правкой пресета — значит менять не тот файл: пресет управляет configure, а не тем, что
написано в `.cpp`.

## 9. Задание

### 9.1 Результат: что должно появиться и почему

Пункты 1–4 и 5–7 правят код приложения и его граф; пункты 8–10 — окружение и решения. Соотношение
сознательное: урок про инструмент, но инструмент проверяется на приложении (§2.3 `AGENTS.md`).

1. **`include/trafficwatcher/core/Mode.hpp`** — строительный публичный заголовок ядра: `enum class Mode`,
   `constexpr`-функция `label()` и объявление функции, в сигнатуре которой есть тип из QtCore. Почему:
   графу нужен контракт, а требованию `PUBLIC` — причина, видимая в коде (§2.2).
2. **`src/core/mode.cpp`** — определение этой функции, non-inline, с использованием QtCore. Почему:
   без трансляционной единицы библиотека пуста, а ребро `tw_core → Qt::Core` декоративно.
3. **`src/app/main.cpp`** — `QGuiApplication`, вызов функции ядра, использование её результата, `exec()`.
   Почему: это первый наблюдаемый факт распространения требований — приложение получает QtCore, не
   объявляя его сам (§1.1, пункт 5).
4. **`tests/unit/test_core_smoke.cpp`** — проверка `label(Mode::Solid)` и ненулевого результата функции
   ядра; при провале — ненулевой код возврата. Почему: первый тест должен утверждать поведение, а не
   «запустился и не упал» (§6.1).
5. **`src/CMakeLists.txt`** — граф: `tw_core` (STATIC), `cxx_std_20` PUBLIC, публичный include через
   `$<BUILD_INTERFACE:>`, `Qt::Core` PUBLIC, alias `TrafficWatcher::Core`, `tw_app` PRIVATE. Почему:
   границы слоёв становятся фактом, который видно в `deps.dot` (§1).
6. **`tests/CMakeLists.txt`** — тестовый таргет `tw_core_smoke`, линковка **только** по alias,
   `add_test(NAME …)` и свойства `LABELS`/`TIMEOUT`. Почему: тест не должен получать GUI-требования, а
   отбор по лейблу понадобится в уроке 8 (§6).
7. **Корневой `CMakeLists.txt`** — порядок: `cmake_minimum_required` → `project` с `VERSION` →
   `include(CTest)` → `find_package(Qt6 …)` → `add_subdirectory`. Почему: политики и пакеты должны
   существовать до того, как их увидят дочерние каталоги (§3.5).
8. **`CMakePresets.json` и `CMakeUserPresets.json`** — configure/build/test пресеты; личный путь к Qt —
   только в пользовательском файле. Почему: одно знание на консоль, CLion и CI (§5).
9. **`.gitignore`** — исключения для `cmake/*.cmake` и `CTestConfig.cmake`, при этом
   `CMakeUserPresets.json` остаётся проигнорированным. Почему: иначе урок 1.3 и модуль 12 потеряют
   свои файлы (§10, находка 4).
10. **ADR 0001–0004** — тулчейн, имена и namespace, политика предупреждений, layout; и заполненный файл
    ответов. Почему: решение без записи — не решение ([`course.md`](../course.md), принцип 4).

## 10. Подмеченные ошибки: текущее состояние репозитория

Находки ниже — результат замера сегодняшнего дерева, а не пересказ ожиданий. Формат: адрес → что не так
→ цена → что делать.

1. **`CMakeLists.txt:1–2` — комментарии про версии не подтверждены замером.** Строки утверждают
   «version 4.5.0 latest btw for 19.11.2026» и «version 3.31.9 legacy latest», тогда как `cmake --version`
   на этой машине печатает **4.3.2**. Цена: комментарий в файле сборки читается как факт, и следующий
   разработчик поднимет минимум до версии, которой нет. Делать: удалить оба комментария, версии и команду
   их замера записать в ADR-0001 (шаг 9).
2. **`CMakeLists.txt:3` — патч-версия в минимуме.** `cmake_minimum_required(VERSION 4.3.2)` означает, что
   CMake 4.3.0 и 4.3.1 **не пройдут** configure, хотя функционально совместимы. Цена: искусственный
   блокер для машины напарника и для CI-образа. Делать: минимум — `4.3` (или `3.31`, если решишь
   поддерживать legacy-ветку), а точная проверенная версия фиксируется в ADR-0001 и в
   `cmakeMinimumRequired` пресета.
3. **`CMakeLists.txt:4` — `project()` без `VERSION`.** `PROJECT_VERSION` пуст, значит CPack (модуль 11)
   получит пустую версию пакета, а `install(EXPORT)` — пустую совместимость. Цена: переписывать версию
   в трёх местах вместо одного. Делать: `project(TrafficWatcher VERSION 0.1.0 LANGUAGES CXX)` (шаг 6).
   Имя проекта, в отличие от старого состояния, уже продуктовое — находка 13 из
   [`legacy-description.md`](../legacy-description.md) закрыта, это видно в той же строке.
4. **`.gitignore:10` — правило `*.cmake` шире, чем нужно.** Замерено: `git check-ignore -v` показывает,
   что `cmake/TwTest.cmake` и `CTestConfig.cmake` игнорируются именно этой строкой. Цена: урок 1.3
   потеряет свои модули `cmake/Tw*`, а модуль 12 — конфиг CDash; файлы будут писаться и не попадать в
   коммит, причём молча. Делать: исключения `!cmake/*.cmake` и `!CTestConfig.cmake` (шаг 1). Предсказание
   этой находки уже было в [`legacy-description.md:61`](../legacy-description.md) — теперь оно подтверждено.
5. **В `CMakeLists.txt` нет `include(CTest)`/`enable_testing()`.** Тестовый контейнер не создаётся, и
   `ctest` в этом проекте сегодня вернёт **0**, не выполнив ни одного теста (механика замерена в §6.4).
   Цена: зелёный CI-джоб без тестов. Делать: `include(CTest)` в корне (шаг 6) и `--no-tests=error` в
   прогоне (DoD).
6. **Нет `src/`, `include/`, `tests/`, `cmake/`, `CMakePresets.json`** (замерено `git ls-files` и
   `Test-Path`). Цена: собирать и запускать нечего; `cmake -S . -B …` падает на отсутствующем генераторе,
   а `cmake --list-presets` — на отсутствующем файле. Делать: шаги 2–8.
7. **Нет `.editorconfig`, `.clang-format`, `.qmllint.ini`** (замерено `Test-Path`). Цена: стиль и
   статический анализ не зафиксированы, ревью будет спорить о форматировании. Это не блокер урока 1:
   файлы появятся в уроках 1.3 и 10. Здесь находка записана, чтобы не забыть.
8. **`docs/lessons/01-cmake-target-model.md:94`, `:1003`, `:1133` — описание входного состояния
   устарело.** Канонический урок утверждает, что `CMakeLists.txt` состоит из двух строк с
   `VERSION 3.16` и `project(TrafficLight …)`. Замерено сегодня: файл из четырёх строк,
   `VERSION 4.3.2`, `project(TrafficWatcher LANGUAGES CXX)`. Цена: читатель канона ищет в репозитории
   то, чего там нет, и теряет доверие к остальным замерам урока. Делать: обновить три адреса в
   каноническом уроке отдельной правкой. В этом варианте они не тронуты: файл написан для сравнения,
   и менять канон во время сравнения нельзя.
