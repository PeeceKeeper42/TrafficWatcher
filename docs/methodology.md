## 2. Как устроен урок

Номера §2.x ниже — разделы этого файла; на контракт ассистента ссылки всегда с префиксом `AGENTS.md`.

### 2.1 Из каких практик взята форма

Самостоятельный ученик бросает материал, если не понимает, зачем он, и не может проверить себя сам.
Отсюда набор приёмов, который независимо использовали шесть популярных форматов обучения
программированию и четыре принципа методики.

| Формат | Как устроен урок у них | что взято отсюда |
|---|---|---|
| **Google / Android Codelabs** ([codelabs.developers.google.com](https://codelabs.developers.google.com/), [разбор формата](https://developers.curioswitch.org/codelabs/writing-a-codelab/)) | YAML-front-matter (`id`, `summary`, `status`, `feedback link`); первый шаг — введение с «What you'll build / What you'll learn / What you'll need»; каждый шаг — H2 с первой строкой `Duration: MM:SS`; врезки двух видов (совет и предупреждение); в конце self-check, решение отдельным шагом, «Next steps», «Learn more» | карточка урока с артефактом на выходе; результат назван до теории; ровно два вида врезок; self-check и «дальше» как обязательные разделы |
| **The Odin Project** ([theodinproject.com](https://www.theodinproject.com/)) | «Learning Outcomes» списком «by the end you should be able to …», затем Lesson, затем **Assignment** — один проект, затем Practice, Extra Resources, «Points to Ponder» | цели проверяемым глаголом; задание — один проект, а не десять мелких пунктов; вопросы вынесены из тела урока (у нас — `answers/`) |
| **CS50** ([cs50.harvard.edu/x](https://cs50.harvard.edu/x/)) | один материал в трёх длинах: lecture → walkthrough → shorts → section; problems с distribution-кодом и отдельной спецификацией; staff solution открывается после сдачи; рубрика и FAQ по типичным ошибкам | многоуровневая подача (обзор → разбор → детали); спецификация задания отдельно от объяснения; эталон **после** приёмки; диагностика как FAQ |
| **freeCodeCamp / Exercism** ([freecodecamp.org/learn](https://www.freecodecamp.org/learn/), [exercism.org](https://exercism.org/)) | маленький шаг с автоматической проверкой; подсказки слоями; model solution только после попытки; карта концептов, ведущая от одной идеи к следующей | у каждого шага своя проверка с ожидаемым выводом; одна подсказка на вопрос, свёрнутая; решение не показывается до попытки |
| **The Rust Book** ([doc.rust-lang.org/book](https://doc.rust-lang.org/book/)) | собираемый код с первой страницы, «Try it yourself», разбор ошибок отдельными разделами, «Summary» в конце каждой главы | практика раньше объяснения; разбор отказа как содержательный раздел; обязательный итог |
| **MDN / официальные туториалы Qt** ([developer.mozilla.org/Learn](https://developer.mozilla.org/en-US/docs/Learn), [doc.qt.io](https://doc.qt.io/qt-6/gettingstarted.html)) | «Prerequisites» до первого шага, пошаговая сборка приложения, в конце «What you've learned» | блок «что должно быть установлено и собрано до урока»; перечень освоенного в конце |

Из формы codelab сознательно не взято `Duration: MM:SS` у каждого шага: оценка времени до прохождения
шага — число, которое нечем проверить, и оно попадает в урок как обещание вместо инструмента. Время
фиксировать принято, но как замер после (§2.10, §6).

| Принцип | Что требует в уроке | чем это грозит без него |
|---|---|---|
| **Backward design** ([Understanding by Design](https://en.wikipedia.org/wiki/Understanding_by_Design)) | приёмка определяется раньше теории: DoD и рубрика известны из карточки и не меняются в блоке задания | теория пишется «по теме», задание — по остатку места в файле, цели невозможно проверить |
| **Gradual release of responsibility** («I do → we do → you do», [NSW Dept. of Education](https://education.nsw.gov.au/teaching-and-learning/curriculum/explicit-teaching/explicit-teaching-strategies/gradual-release-of-responsibility)) | в каждом блоке практики три слоя: разбор готового → упражнение с пропусками → самостоятельная проверка | между демонстрацией и большим заданием пропасть: ученик должен сам догадаться, как перенести показанное |
| **Worked example effect и completion problems** ([обзор с первоисточниками](https://mike-taylor.org/2025-11-15/the-right-kind-of-difficulty-why-worked-examples-beat-practice-for-novices/), [когнитивная нагрузка](https://en.wikipedia.org/wiki/Cognitive_load)) | дырявые примеры: часть строк дана, часть вставь и предскажи вывод | решение с нуля требует удержать в голове весь механизм сразу; с готовым решением не происходит извлечения знания |
| **Retrieval practice + spacing + interleaving** ([Carpenter et al., 2022](https://www.teachertoolkit.co.uk/wp-content/uploads/2022/10/s44159-022-00089-1.pdf)) | self-check с немедленной проверкой и вопросы из прошлых уроков с интервалами примерно 1 / 3 / 10 | конструкция «пройдена», но через месяц не воспроизводится; спираль остаётся обещанием |

### 2.2 Скелет урока

Файл `docs/lessons/NN-<slug>.md`. Восемь обязательных блоков, порядок фиксирован; два блока —
опциональные.

| # | Блок | Бюджет | Что обязательно |
|---|---|---|---|
| 1 | **Карточка урока** | 6–10 строк | модуль/урок и ссылка на [`course.md`](course.md); веха; артефакт на выходе **одной командой**; «на входе» — prerequisites: что уже собрано и работает; какие ADR порождает; ссылка на `answers/NN-*.md`. Времени в карточке нет: оценку «сколько займёт урок» нечем проверить (§2.10), часы — только как замер по закрытому модулю (§6) |
| 2 | **Цели и доказательства** | таблица 4–6 строк | цель глаголом, который можно проверить («предсказать», «выбрать по признаку», «найти фазу по тексту ошибки», «переписать `if()` выражением»), плюс колонки «где отрабатывается» и «чем доказывается» — номер шага задания или номер вопроса |
| 3 | **Проблема урока** | 10–20 строк, **без теории** | конкретный симптом из этого репозитория или из будущей вехи → что за ним стоит → «к концу урока будет так: …». Это и есть ответ на «зачем сейчас», и он звучит один раз |
| 4 | **Вход → выход** | 2–3 таблицы | три строки состояния приложения (вход — замер, выход — что появится, наследство следующему уроку); срок жизни строительного кода; таблица усложнения конструкций прошлых уроков ≥3 строк (в уроке 1 — карта вперёд) |
| 5 | **Практикум** | 3–5 циклов; цикл ≤25 минут и ≤120 строк | структура каждого цикла — §2.3 |
| 6 | **Задание** | 80–150 строк | один проект на приложение; Definition of Done чекбоксами; блок прямых шагов (§2.4); «чего не делаем»; ≥2/3 пунктов правят код приложения |
| 7 | **Приёмка** | 30–50 строк | рубрика трёх уровней по каждому пункту DoD (§2.5); self-check из 3 вопросов с ответом под `<details>`; exit ticket на две строки |
| 8 | **Справка и «дальше»** | ≤120 строк | сводная таблица конструкций урока; глоссарий урока (3–6 терминов, которые дальше идут без перевода); диагностика «симптом → настоящая причина → где чинить»; находки в репозитории со ссылками `файл:строка`; «что читать», где один пункт обязателен — разбор чужого кода (§2.11); следующий урок и какие ADR созрели |
| опц. | **Контраст с прошлым** | ≤10% объёма | таблица «было → стало → что это даёт» (Qt5/C++17/`44ffd1b`), ближе к концу |
| опц. | **Инвентарь окружения** | только замеры | версии, пути, тайминги, полученные командами; догадки помечены словом «проверь» |

Общий объём — 500–900 строк. Урок читается в два прохода: сначала блоки 1–2 и 7 (карточка, цели,
приёмка — перед тем как садиться за задание), затем полный пробег. Это требование, а не пожелание: блок 8
существует именно для первого прохода. Блок, в котором нет ни проверяемой команды, ни проверяемого
признака, из урока убирается, а не «дописывается потом».

### 2.3 Цикл практикума: пять частей, одна длина

Теория не идёт отдельным томом перед практикой: она живёт внутри цикла. Цикл = одна идея, и он закрыт,
только когда выполнены все пять частей.

1. **Показ («я делаю»)** — рабочий фрагмент со сквозной нумерацией (1)…(n); по каждому пункту — что он
   делает и почему именно так. Фрагмент собирается из классов этого приложения (`TickEngine`,
   `TrafficLightState`, `IClock`, `LightBulb`), а не из `Foo`/`Bar`.
2. **Дырявый пример («делаем вместе»)** — тот же фрагмент или его потребитель с 2–4 пропусками: вставить
   конструкцию, предсказать команду компиляции, назвать, на какой фазе упадёт. У пропуска есть проверка
   одной командой.
3. **Самостоятельная проверка («ты делаешь»)** — 2–5 минут в терминале на своей машине: выполнить и
   увидеть ожидаемый вывод.
4. **Ловушка / тонкость** — что конкретно сломается, замедлится или станет непроверяемым, если сделать
   иначе. Оформляется абзацем `**Тонкость N.**` или `**Ловушка.**` (см. §2.6 про врезки).
5. **Чекпойнт** — одна строка: `команда` → ожидаемый вывод. Цикл без чекпойнта не закрыт, а следующий
   цикл нельзя начинать, если предыдущий не прошёл: ошибка перестаёт быть однослойной.

Следствие из порядка: без части 2 часть 3 превращается в «попробуй угадать», а без части 5 в уроке
не остаётся ничего, кроме пересказа документации: поведение своих инструментов проявляется только в
чекпойнте. Файлы, которые создаёт практика, лежат внутри рабочей области.

### 2.4 Задание: один проект, прямые шаги, границы объёма

Блок 6 делится на три части, и все три обязательны.

1. **Что должно получиться** — пункты про результат с причиной («в репозитории появится X, потому что
   иначе Y не проверяется»).
2. **Прямые шаги** — последовательность «создай `path/to/file`, в файле должно быть: …; проверка:
   `команда` → ожидаемый вывод». Порядок шагов — тот, при котором ошибка остаётся однослойной:
   заголовок → реализация → объявление таргета → родительский `CMakeLists.txt` → пресеты → тесты и CI.
   Шаг формулирует требования к содержимому, а не готовый код. Проверка без ожидания проверкой не
   считается.
3. **Чего не делаем** — явный anti-scope: что в этом уроке не трогаем и в каком уроке это появится
   (например: «QML и `qt_add_qml_module` — не здесь, урок 2.1»). Причина: без этой строки middle-читатель
   дотягивает урок до следующего модуля и получает разбор того, чего ещё не проходил.

### 2.5 Приёмка: рубрика, self-check, exit ticket

Три инструмента в одном блоке — каждый закрывает свой риск.

| Инструмент | Форма | Что проверяет |
|---|---|---|
| **Рубрика DoD** | таблица: критерий / «зачтено» / «зачтено с оговоркой» / «не зачтено» | не «работает», а в каком объёме: команда, вывод, файл, свойство графа — построчно |
| **Self-check** | 3 вопроса, ответ под свёрнутым `<details>` прямо в уроке | немедленное извлечение знания: свойства, фазы, имена ключей — то, что путается при первом прогоне |
| **Exit ticket** | 2 строки: «самое непонятное», «что проверю в следующем уроке» | без него следующий урок пишется вслепую: непонятное остаётся между учеником и его заметками; заполняется после задания, а не до |

Рубрика не заменяет `answers/`: self-check — короткая проверка на месте (с ответом), вопросы в
`answers/` — развёрнутый ответ своими словами, без обращения к тексту урока (§3).

### 2.6 Врезки: два вида, не больше

| Врезка | Когда | Содержание |
|---|---|---|
| `**Проверь.**` | после утверждения, которое можно подтвердить на этой машине | команда + ожидаемый вывод |
| `**Ловушка.**` | после конструкции, где типичная ошибка выглядит как работающий код | симптом → настоящая причина → что менять |

Формы «интересно, что…» и «обрати внимание, как…» без команды и без симптома в урок не пишутся: они
читаются как вставка и не оставляют ничего, что можно проверить.

### 2.7 Паспорт конструкции: справка в блоке 8, ссылка в тексте цикла

Каждая конструкция, появившаяся в уроке впервые, обязана получить карточку-паспорт из семи полей:
полная сигнатура (с квадратными скобками у необязательных аргументов и указанием категории — команда /
свойство / переменная / key пресета / класс Qt), зачем, допустимые формы аргументов, где применима в этом
проекте, где **неприменима**, best practice с конкретным следствием, справка middle и команда, которой
проверяется точная формула (`cmake --help-command <cmd>`, `cmake --help-property <prop>`,
`cmake --help-variable <var>`, `cmake --help-manual <man>`, `ctest --help`, страница Qt-доков).

Карточки собираются **блоком 8**, одной таблицей или списком; в тексте цикла стоит одна строка-ссылка:
«`target_include_directories` → справка, строка 3». Причина: паспорт — справочник, и в середине
нарратива он ломает чтение; при этом он обязателен, потому что на ревью спрашивают точную форму, а не
понимание. Объём карточек — не больше ~25% блока 8: десять карточек в уроке из трёх конструкций значит,
что часть из них выдумана. Сигнатура сверяется командой проверки на этой машине, а не памятью; сомнение
в версии опции пишется словами «проверь у себя».

### 2.8 Тонкости и спираль

Тонкости уровня middle (3–6 на урок) живут внутри циклов, часть 4. К уже пройденной конструкции
тонкость возвращается глубже: свойство → механизм распространения → почему механизм устроен именно так;
тот же слой второй раз не преподаётся. Нет неочевидного проверяемого следствия — нет тонкости:
выдуманная тонкость стоит времени на её опровержение.

Спираль обеспечивается не только таблицей усложнения (блок 4), но и интервальными вопросами в
`answers/`: не менее трёх вопросов из уроков с интервалами примерно 1 / 3 / 10 (см. §3).

### 2.9 Чек-лист оформления урока

- [ ] блок 1 содержит артефакт одной командой и prerequisites; оценок времени урока в нём нет;
- [ ] у каждой цели из блока 2 есть доказательство — шаг задания или вопрос;
- [ ] блок 3 объясняет «зачем» один раз, и теория в нём не начинается;
- [ ] блок 4 содержит вход/выход и таблицу усложнения ≥3 строк;
- [ ] каждый цикл практикума дошёл до чекпойнта с ожидаемым выводом, ни один цикл не больше 25 минут;
- [ ] в практикуме минимум два дырявых примера (часть 2 цикла);
- [ ] задание — один проект, ≥2/3 пунктов правят код приложения, есть «чего не делаем»;
- [ ] у DoD есть рубрика трёх уровней;
- [ ] self-check из трёх вопросов со скрытыми ответами;
- [ ] все паспорта конструкций собраны в блоке 8, сигнатуры сверены командой проверки на этой машине;
- [ ] в блоке 8 есть глоссарий урока: термины, которые в следующих уроках идут без перевода;
- [ ] в блоке 8 «что читать» содержит хотя бы один разбор чужого кода (исходники Qt, KDAB, CMake) с явной
      ссылкой, что именно читать (§2.11);
- [ ] 3–6 тонкостей, каждая с проверяемым следствием;
- [ ] история про Qt5/C++17 — ≤10% объёма и не в начале;
- [ ] ссылки ведут на реально существующие файлы и разделы; вымышленных API нет;
- [ ] создан `answers/NN-<slug>.md` с пустыми слотами `> Ответ:` и ≥3 интервальными вопросами.

### 2.10 Откуда взяты числа

900 строк, цикл ≤25 минут, доля истории ≤10% — значения, выведенные из практики перечисленных форматов
(шаг codelab ≈ 5–15 минут, урок The Odin Project ≈ 45–90 минут чтения с практикой), а не из замеров этого
курса. Это границы объёма материала, а не обещание «урок на столько-то часов»: после первых двух уроков,
написанных по этой форме, их заменяют собственными замерами (§6).

Длительность урока не оценивается нигде — ни в карточке, ни в задании. Причина: оценку «сколько это
займёт» делает человек, который ещё не знает, чего он не знает, и потому систематически занижает её;
следствие — урок бросают на середине со ссылкой на график, либо цифрой заменяют результат. Замер после
закрытия модуля даёт то же знание без выдумки: колонка «часы (факт)» в §6 заполняется по факту и остаётся
пустой, пока модуль не закрыт.

### 2.11 Курсовые ритуалы

Пять действий, которые повторяются из модуля в модуль и не учат теме, а делают курс завершаемым.
Конкретика — вопросы защиты по блокам и упрощения по модулям — в [`course.md`](course.md), здесь — форма.

| Ритуал | Когда | Форма | Что происходит без него |
|---|---|---|---|
| **Тег + заметка модуля** | закрытие модуля | annotated tag `m<NN>-done`, в теле три строки: что развязало, что сломалось, что беру дальше | курс остаётся приватным: через месяц не восстановить, почему выбор был такой, и нечего показать на собесе |
| **Разбор чужого кода** | один раз в урок, в блоке 8 | ссылка на реальный файл (исходники Qt, фрагмент разбора KDAB, чужой `CMakeLists.txt`) + вопрос «почему здесь так, а не иначе» | уровень middle — это умение читать не свой код; на одном своём проекте оно не тренируется |
| **Защита блока** | закрытие блока I–IX | три вопроса блока устно, вердикт по шкале из [`AGENTS.md`](../AGENTS.md) §3 | темы блока остаются узнаваемыми, но не воспроизводимыми: «проходили» ≠ «объясню без текста» |
| **План/факт по часам** | закрытие модуля | число в таблице §6; оценки до начала не ставятся | непонятно, влезает ли курс в жизнь, и где именно он раздулся |
| **План Б** | пункт DoD не закрыт после двух отдельных попыток с разными гипотезами | упрощение из таблицы `course.md`, оформленное ADR со статусом `Заменено` | модуль стоит молча: без записи о том, что именно упрощено, упрощение превращается в дыру в знаниях |

Триггеры — события (закрытие модуля, две неудачные попытки), а не срок: «два вечера без прогресса» —
это снова оценка времени, поэтому считается попытками и пунктами DoD.

## 3. Файл ответов

Создаётся вместе с уроком, без исключений; урок без него не оформлен. Форма — `AGENTS.md` §3, плюс три
требования к составу вопросов:

- **три слоя вопросов:** (а) проверка понимания по материалу урока, (б) перенос на свой код — «что
  сломается, если…», свой пример, цифра, (в) **интервальные** вопросы прошлых уроков, минимум три, с
  указанием урока-источника;
- **подсказки только спойлером** (`<details>` между вопросом и слотом `> Ответ:`), одна на вопрос, и
  только направлением (раздел, команда, имя свойства), а не формулировкой ответа;
- слот пустой — оценка не пишется: отсутствие ответа фиксируется в чате.

```markdown
## 7

<текст вопроса: что проверить и какой объём ответа принимается>

<details>
<summary>Подсказка — открывать только если застрял</summary>

<направление: раздел урока, команда, имя механизма>

</details>

> Ответ:
>
```

Ниже заполненного ответа допускается только блок оценки (`AGENTS.md` §3): вердикт «зачтено / зачтено с
оговоркой / не зачтено» и строки «Фактическая ошибка», «Формулировка», «Что делать дальше». Текст ответа
не правится, не переносится и не удаляется ни при каких условиях.

## 4. Соглашения

- **Голос:** документы пишутся от лица владельца проекта («я делаю так»); в теоретических разделах
  уроков допустимо обращение к читателю на «ты».
- Один урок — один коммит (или ветка) + рабочие файлы в репозитории.
- **Урок не закрыт, пока не видно, как изменилось приложение:** блок 4 заполнен, и ≥2/3 пунктов задания
  правят код приложения, а не только конфигурацию и документы.
- **И пока не названо, что усложнилось из прошлого урока:** строка из таблицы усложнения, где конструкция
  меняет поведение, — обязательная часть отчёта о закрытии.
- Урок закрыт, когда выполнены все пункты DoD **и** заполнен `answers/NN-*.md`.
- **Модуль закрыт, когда есть тег модуля с заметкой и проставленные факты-часы; блок закрыт после устной
  защиты по трём вопросам** (§2.11, вопросы — в [`course.md`](course.md)). Без этого закрытие считается
  локальным делом одного человека: курс не становится ничьим, кроме моего, и не проверяется извне.
- Фича без описанного теста, который упадёт при её поломке, не считается сделанной.
- Нетривиальное решение без ADR не считается принятым.
- Модули поставки и инфраструктуры (11–12, 19) не опережают блоки I–III: сначала стабильный
  `ctest --preset`, потом автоматизация.
- **Модуль привязан к вехе:** 13–14 — M2, 15–16 — M3, 17 — M4, 18 — M5, 19 обслуживает все вехи. Тема не
  переезжает между вехами молча: переезд меняет строку «Веха» в [`course.md`](course.md), а если вместе с
  ним меняются критерии приёмки модуля — переезд оформляется решением (ADR или правка существующего).
- Очередь ADR и гейты качества по вехам — в [`course.md`](course.md) и [`adr/readme.md`](adr/readme.md).
- **Рабочая область — только репозиторий этого проекта.** Проверки, мини-практики и временные файлы живут
  внутри него; файлы и окружение вне рабочей области ассистент не меняет (`AGENTS.md` §1, п. 5).

## 5. Обязательства ассистента

Полный список — в [`../AGENTS.md`](../AGENTS.md). Ключевое:

- код **не пишет** (только `docs/`, `answers/`, сниппеты в чате и в уроке как иллюстрация); правит
  `AGENTS.md` только по отдельной команде владельца;
- **вне рабочей области не работает:** файлы вне `C:\Projects\TrafficWatcher`, временные каталоги
  (`$env:TEMP`), пользовательские конфиги и переменные окружения не создаёт, не меняет и не удаляет;
  нужную проверку делает внутри репозитория или переносит в инструкцию пользователю;
- с каждым уроком **обязан** создать `answers/NN-<имя-урока>.md` со всеми вопросами, пустыми слотами
  `> Ответ:` и без дублирования вопросов в теле урока;
- теория ведётся циклами §2.3, урок обязан иметь блоки 1–8; отсутствие любого из них — урок не оформлен;
- каждая новая конструкция получает паспорт из семи полей, сигнатуры сверены командой проверки на этой
  машине; выдуманных API не бывает — сомнение помечается словом «проверь на своей версии»;
- каждый урок усложняет конструкции предыдущих (≥3 строк таблицы) и содержит 3–6 тонкостей с проверяемым
  следствием;
- **не ставит оценок времени в уроки** (ни в карточку, ни в задание) и помнит про курсовые ритуалы §2.11:
  при закрытии урока напоминает про тег модуля, часы-факт и защиту блока;
- право на запись по `docs/` ограничено матрицей `AGENTS.md` §1.1: в ADR — только форматирование; в
  `answers/` — только оценка под ответом; текст владельца не переписывается и не удаляется; `course.md` —
  только по отдельному вопросу с буквальным согласием; `legacy-description.md` — только чтение;
- после записи файл перечитывается: опечатки, смешение алфавитов, разорванные ссылки, тон по
  `AGENTS.md` §2.2.
